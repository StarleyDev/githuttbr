# CI 실행

푸시했고, 이제 기다립니다. 브라우저로 넘어가 저장소를 찾고, Actions를 열고, 내 실행을
찾고, 빨갛게 된 작업을 열고, 로그 끝까지 스크롤합니다. **CI 실행**은 그 과정을 코드
옆에 둡니다. 한 페이지가 각 워크플로가 최근에 어땠는지 알려 주고, 원격의 실행을 최신순으로
나열하며, 실패한 실행을 깨진 테스트에서 바로 엽니다 — 파일과 줄까지, 편집기로 한 번의
클릭. 다시 실행하거나 멈추는 버튼은 카드에 있습니다.

이미 GitHuttBr에 준 토큰으로 호스트 자체의 API와 통신합니다. 내 컴퓨터에서는 아무것도
실행되지 않습니다 — 그것은 [로컬 CI](local-ci.md)를 보세요.

![CI 실행 페이지: 워크플로마다 최근 실행이 있는 카드, 실패·실행 중 필터, 실행 중인 실행의 진행률, 깨진 테스트와 작업이 열린 실패한 실행](../../screenshots/ci-runs.webp)

## 여는 방법

**도구 → CI 실행…**, 또는 명령 팔레트(⌘K)의 *CI 실행*. 위키나 인사이트처럼 이 페이지도
저장소의 탭 위에 열리며, `origin`이라는 원격을 읽습니다 — `origin`이 없으면 첫 번째
원격을 읽습니다.

## 페이지에 보이는 것

| 부분 | 무엇인가 |
|---|---|
| **워크플로 카드** | 워크플로마다 카드 하나: 무엇이 그것을 시작하는지, 마지막으로 끝난 실행 10개의 통과율(90 %부터 초록, 70 %부터 주황, 그 아래는 빨강), 그 실행들을 색 사각형으로 — 가장 오래된 것이 왼쪽이라 최신이 “지금” 옆에 옵니다 — 평균 시간, 그리고 가장 느린 작업 또는 마지막 실행의 결과. 카드를 클릭하면 그 워크플로의 실행만 나열하고, 다시 클릭하면 모두 보여 줍니다 |
| **모든 브랜치 / 현재 브랜치** | 원격의 모든 실행, 또는 체크아웃한 브랜치의 실행만 |
| **실패 / 실행 중** | 각각이 남길 실행 수가 붙은 빠른 필터. 다른 필터가 남긴 것을 세므로, 그 숫자가 곧 클릭하면 보이는 것입니다 |
| **필터** | 불러온 실행을 제목, 워크플로, 브랜치, 작성자, 커밋 또는 이벤트로 좁힙니다 |
| **실행 카드** | 커밋 제목(또는 워크플로 이름), 이어서 브랜치, 워크플로와 실행 번호, 무엇이 시작했는지(push, pull request, schedule, 수동…), 누가 시작했는지, 커밋 — 커밋을 클릭하면 복사됩니다. 실행이 풀 리퀘스트에 속하면 **PR #n**이 그 풀 리퀘스트의 페이지를 엽니다. 오른쪽에는 현재 상태, 걸린 시간, 얼마 전인지 |
| **실행 중인 실행** | *실행 중 · 5단계 중 3단계*, 진행 막대, 지금까지의 시간. 단계는 실행 중인 작업의 것이며, 단계가 없는 호스트(GitLab, Forgejo)에서는 대신 작업을 셉니다 |
| **실패한 테스트** | 실패한 실행은 최신 것이 저절로 열리고, 로그가 가리키는 테스트를 보여 줍니다: 작업, 테스트, 오류의 첫 줄, **경로:줄** — 그것이나 *편집기에서 열기*를 클릭하면 그 줄로 갑니다. 풀 리퀘스트의 [체크 탭](hosting.md#체크-탭)과 같은 읽기 방식입니다 |
| **작업** | 그 아래에 각 작업과 상태, 소요 시간이 나오며, 호스트에 스테이지가 있으면(GitLab, Azure) 스테이지별로 묶입니다. *단계와 로그 보기*가 작업의 단계와 로그 끝부분을 엽니다 — 실패한 작업에는 항상 있고, 다른 작업에서는 마우스를 올리면 나타납니다 |
| **단계** | 작업의 각 단계와 상태, 소요 시간 — GitHub, Azure, Forgejo가 보고하며, GitLab에는 단계가 없습니다 |
| **로그** | 끝난 작업 로그의 끝부분, 색상 유지. 마지막 512 KB만 가져오며 — 실패가 있는 곳 — 앞부분이 생략되면 페이지가 알려 줍니다 |

페이지에 대기 중이거나 실행 중인 것이 있는 동안, 목록은 15초마다 호스트에 다시 묻고,
열린 실행과 실행 중인 모든 실행의 작업도 함께 묻습니다 — 단계 수는 거기서 옵니다.
소요 시간은 매초 올라갑니다. 2분 동안 새로운 답이 없으면 — 예를 들어 배포 승인을
기다리는 실행 — 1분에 한 번으로 느려지고, 무언가 움직이면 바로 다시 빨라집니다. 모두
끝난 목록은 새로 고침을 누를 때까지 아무것도 묻지 않으며, 창이 숨겨져 있는 동안에도
묻지 않습니다.

호스트가 제목 없이 보내는 실행 — 모든 GitLab 파이프라인, 예약된 Azure 빌드 — 은 커밋이
그래프에 있으면 그 커밋의 제목으로 이름 붙습니다. 로컬 저장소에서 비용 없이 읽습니다.
그렇지 않으면 번호로 이름 붙습니다.

## 재실행, 취소, 시작

| 버튼 | 보이는 때 | 하는 일 |
|---|---|---|
| **실패 재실행** | 실행이 실패했거나 취소됐을 때 | 통과하지 못한 작업만 다시 실행합니다 |
| **재실행** (↻) | GitHub에서 실행이 끝났을 때 — 카드에 마우스를 올리면 카드에 | 모든 작업을 다시 실행합니다 |
| **브라우저에서 열기** | 카드에 마우스를 올렸을 때 | 호스트 사이트의 그 실행 |
| **취소** | 실행이 대기 중이거나 실행 중일 때 | 먼저 묻습니다: 진행 중인 작업이 중단되고 그 작업 결과는 사라집니다 |
| **워크플로 실행** | 호스트가 수동으로 시작할 수 있을 때 | 워크플로와 브랜치를 고르면, 그 브랜치가 푸시된 것처럼 시작되고 몇 초 뒤 목록에 나타납니다 |

호스트마다 허용하는 것:

| 호스트 | 목록과 작업 | 단계 | 로그 | 전체 재실행 | 실패 재실행 | 취소 | 수동 시작 |
|---|---|---|---|---|---|---|---|
| **GitHub** (및 Enterprise Server) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ — 워크플로에 `workflow_dispatch` 트리거가 필요합니다 |
| **GitLab** (및 자체 관리형) | ✓ — 파이프라인, 스테이지별 작업 | — | ✓ | — | ✓ (*Retry*) | ✓ | ✓ — 브랜치에서 `.gitlab-ci.yml`을 실행합니다 |
| **Azure DevOps** | ✓ — 빌드, 스테이지별 작업 | ✓ (태스크) | ✓ | — | ✓ | ✓ | ✓ — 저장소의 어떤 빌드 정의든 |
| **Forgejo / Gitea** | ✓ Actions runs API가 있는 서버에서 | ✓ | ✓ 서버가 토큰에 제공할 때 | — | — | — | — |
| **Bitbucket** | — | | | | | | |

## 그래프의 배지

같은 CI가 그래프의 각 커밋 옆에 작은 배지로도 나타납니다: 초록, 빨강, 또는 실행 중이면
시계. 마우스를 올리면 작업이, 클릭하면 호스트 페이지가 열립니다. 배지의 출처는 다음과
같습니다.

| 호스트 | 출처 |
|---|---|
| GitHub | 커밋의 check run — Actions만이 아니라 GitHub에 보고하는 모든 CI |
| GitLab | 모든 파이프라인 작업을 포함하는 커밋의 상태. 수동 작업(예: 배포)이 배지를 시계에 묶어 두지 않습니다 |
| Azure DevOps | 저장소의 최근 빌드 100개, 커밋으로 대응 |
| Forgejo / Gitea | 커밋의 결합 상태 — Forgejo Actions와 모든 외부 CI |
| Bitbucket Data Center | 커밋의 빌드 상태 |

모든 답은 기억됩니다 — “여기에는 CI가 없음”까지 — 그리고 커밋은 답이 바뀌었을 수 있을
때만 다시 묻습니다: 실행 중에는 45초마다, 끝난 뒤에는 10분마다, CI가 한 번도 없었던
커밋은 점점 드물게. 그래서 바쁜 그래프도 호스트의 시간당 허용량 안에 머뭅니다.

## 제한

- **카드는 페이지가 나열한 실행만 압니다.** 적용 중인 브랜치 필터의 마지막 실행
  50개입니다 — 드물게 실행되는 워크플로는 사각형이 열 개보다 적을 수 있고, 현재
  브랜치로 바꾸면 모든 카드를 다시 계산합니다. 가장 느린 작업은 페이지가 끝난 실행의
  작업을 읽은 뒤에 나타납니다(저절로 열리는 실패한 실행이면 충분합니다). 그전까지
  카드는 마지막 실행의 결과를 보여 줍니다.
- **실패한 테스트는 로그 텍스트에서 읽습니다.** Vitest, Jest, pytest를 인식합니다.
  다른 러너, 빌드 오류, 잘린 로그에는 작업 목록만 나옵니다. 러너가 체크아웃 밖에 쓴
  경로는 열 수 없습니다.
- **PR #n은 호스트가 알려 주는 것에 달려 있습니다.** GitHub는 포크가 아닌 같은
  저장소의 실행에만 풀 리퀘스트를 알려 줍니다. GitLab은 머지 리퀘스트 파이프라인에,
  Azure는 PR 빌드에 알려 줍니다. Forgejo 실행에는 링크가 없습니다.
- **로그는 끝부분이며, 작업이 끝난 뒤에만 있습니다.** GitHub와 Forgejo는 작업이 끝난
  뒤에 로그를 내줍니다. 실행 중에는 페이지가 출력이 아니라 진행 중인 단계를 보여
  줍니다. GitLab과 Azure는 실행 중인 작업의 지금까지의 로그를 줍니다 — 더 읽으려면
  다시 여세요.
- **토큰에 CI 권한이 필요합니다.** GitHub 세분화된 토큰은 나열에 *Actions: read*,
  재실행·취소·시작에 *Actions: write*가 필요하고, 클래식 토큰은 `repo`가 필요합니다.
  GitLab 토큰은 나열에 `read_api`, 버튼에 `api`가 필요합니다. Azure 토큰은
  *Build: read*(버튼에는 *Build: read & execute*)가 필요하며, 없으면 페이지와 배지가
  실패하지 않고 비어 있습니다.
- **Azure 배지는 빌드 100개까지만 거슬러 갑니다.** 더 오래된 커밋에는 배지가 없지만,
  CI 실행 페이지에는 그 빌드가 여전히 나열됩니다.
- **Azure의 재실행은 “실패 재시도”입니다.** 스테이지가 있는 YAML 파이프라인에서
  동작합니다. 클래식 파이프라인은 거부할 수 있으며, 페이지는 호스트의 답을 보여 줍니다.
- **워크플로를 시작할 때 입력값을 묻지 않습니다.** 기본값 없는 필수 입력이 있는 GitHub
  워크플로나 GitLab 파이프라인은 호스트가 자체 메시지와 함께 거부합니다.
- **Forgejo는 읽기 전용이며, 최신 서버에서만 됩니다.** 오래된 Forgejo와 Gitea 서버에는
  실행을 나열하는 API가 없습니다. 페이지는 호스트가 지원되지 않는다고 말하고, 그래프
  배지는 커밋 상태를 통해 계속 동작합니다. 토큰이 볼 수 없는 저장소는 “지원 안 됨”이
  아니라 접근 오류로 나옵니다.
- **Bitbucket에는 실행 페이지가 없습니다.** Data Center에서 CI는 상태만 보고하는 외부
  시스템(Jenkins, Bamboo…)이며, 그 상태가 그래프 배지입니다. bitbucket.org Pipelines는
  지원되지 않습니다.
- **원격 하나.** 페이지는 `origin`을 읽습니다. 포크의 다른 원격에 있는 실행은 나열되지
  않습니다.
