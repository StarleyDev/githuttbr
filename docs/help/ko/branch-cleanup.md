# 브랜치 정리

체크아웃한 풀 리퀘스트마다 로컬 브랜치가 남습니다. PR이 병합되고 서버가 그 브랜치를
지워도 로컬 브랜치는 남습니다 — 영원히. 리뷰를 수백 번 하고 나면 브랜치 목록은 대부분
죽은 브랜치이고, 살아 있는 것을 찾으려면 그것들을 모두 스크롤해서 지나가야 합니다.

브랜치 정리는 작업이 이미 다른 곳에서 안전한 로컬 브랜치를 나열하고, 잃을 것이 없는
브랜치에 체크하고, 되돌릴 수 있는 한 번의 작업으로 삭제합니다. “다른 곳”은 마지막
페치 시점의 원격 추적 브랜치와 기본 브랜치를 뜻합니다.

![정리 대화 상자: 사라짐, 병합됨, squash 병합됨 브랜치에 체크, 여기에만 있는 작업은 제외](../../screenshots/branch-cleanup.webp)

## 사용 방법

1. 도구 → **로컬 브랜치 정리…**(또는 <kbd>⌘K</kbd>).
2. 마지막 페치가 오래됐다면 먼저 **페치 및 prune**을 누르세요. prune을 하는 페치가
   돌기 전까지는 서버가 지운 브랜치도 여기서는 살아 있는 것처럼 보입니다.
3. 팀이 풀 리퀘스트를 squash 병합한다면 **squash 병합 확인**을 누르세요(아래 참고).
4. 체크를 확인한 뒤 **삭제**. 확인 창은 한 번뿐이며, 몇 개의 브랜치가 사라지는지와
   다른 어디에도 없는 커밋을 가진 브랜치의 이름을 모두 알려 줍니다.

삭제는 실행 취소 항목이 하나인 한 번의 작업입니다: **실행 취소**는 지운 각 브랜치를
가리키던 바로 그 커밋에 다시 만들고, upstream(`branch.<name>.remote`와 `.merge`)도
되돌립니다. 그 사이 같은 이름의 브랜치가 다른 커밋에 생겼다면 — 같은 PR을 다시
체크아웃한 경우 — 실행 취소는 그것을 건드리지 않고, 지운 브랜치를 그 옆에
`<name>-restored-<short sha>`로 되돌리며, 그렇다고 알려 줍니다.

성공 메시지와 실행 취소 항목은 각 브랜치를 가리키던 커밋과 함께 나열합니다
(`feature/x (was abc1234)`). `git branch -D`가 출력하는 형식입니다: 실행 취소 기록은
앱이 열려 있는 동안만 남으며, 이 한 줄이면 브랜치를 손으로 다시 만들 수 있습니다.

## 브랜치가 목록에 나오는 이유

| 칩 | 의미 |
|---|---|
| **사라짐** | 서버가 지운 upstream을 추적하는 브랜치 — 병합된 풀 리퀘스트가 흔히 남기는 흔적입니다. |
| **병합됨** | 그 위의 모든 커밋이 이미 기본 브랜치에 있습니다. 툴팁이 그것을 가진 사본을 알려 줍니다 — 로컬에만 있으면 `main (local, not pushed)`. |
| **squash 병합됨** | **squash 병합 확인**으로 찾은 것: 내용은 기본 브랜치에 있지만 개별 커밋은 없습니다. |
| **방치됨** | 고른 개월 수(기본 3) 동안 커밋이 없습니다. **방치된 브랜치도 표시**에 체크했을 때만 나옵니다. |
| **커밋 N개가 여기에만 있습니다** | 어떤 원격 추적 브랜치에도, 기본 브랜치에도 없는 커밋. 브랜치를 지우면 그것들도 사라집니다. |
| **아직 커밋 없음** | 기본 브랜치의 끝을 정확히 가리킵니다 — 아마 만들고 쓰지 않은 브랜치입니다. |

“병합됨”은 기본 브랜치의 원격 사본(`origin/main`)과 로컬 사본 모두를 기준으로
판단합니다 — 한 달 동안 아무도 풀하지 않은 로컬 `main`이라도 그 사이의 병합을 숨길 수
없습니다.

## squash 병합

squash 병합은 풀 리퀘스트의 변경을 `main`에 새 커밋 하나로 올립니다. 브랜치 자신의
커밋은 결코 도착하지 않습니다. git이 보기에 그런 브랜치는 버려진 작업처럼 보입니다:
**사라짐**, *커밋 N개가 여기에만 있습니다*.

자체 커밋이 있는 사라진 브랜치가 나열되면, **squash 병합 확인**은 다른 질문을 합니다:
이 브랜치를 `main`에 병합하면 뭔가 바뀌는가? 모두에 대해 메모리에서 `git merge-tree`를
한 번 실행하고 — 체크아웃도, 인덱스도 없이 — 병합해도 `main`의 트리가 그대로인
브랜치는 **squash 병합됨** 칩을 받고 병합된 브랜치처럼 체크됩니다. 확인 창은 그
내용이 `main`에 있고 커밋은 없다고 알려 줍니다.

확인은 삭제 순간에 잠금 아래에서 다시 실행됩니다: 더는 통과하지 못하는 브랜치는
삭제되지 않고 거부됩니다.

## 체크되는 것, 절대 체크되지 않는 것

대화 상자를 열 때 체크되는 것: **사라졌거나 병합된** 브랜치 중 **자체 커밋이 없는**
것 — 확인 뒤에는 squash 병합된 것도. **사라짐 + 병합됨 선택**으로 그 선택을 되돌릴 수
있습니다.

자동으로는 절대 체크되지 않고, **표시된 항목 모두 선택**으로도 절대 선택되지 않는 것:
여기에만 있는 커밋을 가진 브랜치. 한 행씩 체크하세요. 그러면 확인 창이 빨갛게 바뀌고
커밋 수와 함께 그것을 나열합니다. 방치되기만 한 브랜치와 기본 브랜치 끝에 있는
브랜치도 체크되지 않습니다. 목록이 보여 주지 않는 행 — 필터로 숨겨졌거나 처음 400행
뒤에 있는 행 — 이 선택에 포함되면, 확인 창이 그 수를 알려 줍니다.

삭제는 브랜치마다 확인 창이 보여 준 정확한 고유 커밋 수만 받아들입니다. 그때까지
브랜치에 커밋이 더 생겼다면 — 또는 **다시 실행** 때 실행 취소 뒤로 늘었다면(예를 들어
prune이 원격 사본을 지운 경우) — 거부하고 남겨 두며, 성공이라고 하지 않고 그렇다고
보고합니다.

절대 나열되지 않고, 요청해도 삭제가 거부하는 것:

- 현재 브랜치;
- 어느 워크트리에서든 체크아웃되어 있거나 리베이스 중인 브랜치;
- 기본 브랜치;
- [보호된 브랜치](repo-settings.md). [저장소 설정](repo-config.md)의 `release/*` 같은
  패턴도 포함합니다.

원격에서는 아무것도 바뀌지 않습니다. 로컬 브랜치만 삭제합니다.

## 제한

- **squash 병합은 확인하기 전까지 git에 보이지 않습니다.** **squash 병합 확인**을
  하지 않으면 squash 병합된 브랜치는 *커밋 N개가 여기에만 있습니다*와 함께 **사라짐**
  으로 보이고, 체크되지 않습니다.
- **squash 확인은 놓칠 수 있습니다.** “이 내용이 이미 `main`에 있는가?”에 답합니다.
  나중에 `main`이 같은 줄을 다시 바꿨거나 병합할 때 squash를 편집했다면, 병합이 뭔가를
  바꾸므로 브랜치는 체크되지 않은 채로 남습니다. 내용을 잃는 방식으로 잘못 “예”라고
  하는 일은 없습니다: 내용은 정의상 `main`에 있습니다. [충돌 레이더](conflict-radar.md)
  처럼 `git gc`가 치우는 느슨한 트리 객체를 씁니다.
- **페치하지 않은 원격은 오래된 상태입니다.** “사라짐”은 마지막 페치에서 옵니다.
  **페치 및 prune** 없이는 한 시간 전에 서버에서 지운 브랜치도 아직 살아 보이고, 새
  병합도 아직 `origin/main`에 없습니다.
- **방치됨은 날짜일 뿐입니다.** 조용한 석 달은 작업이 안전한지에 대해 아무것도
  말해 주지 않으므로, 방치된 행은 절대 체크되지 않습니다.
- **“다른 곳”은 마지막 페치 시점의 원격 추적 참조**이지, 지금 이 순간의 서버가 아니며
  태그도 아닙니다. 태그만 붙잡고 있는 커밋은 고유한 것으로 세고, 다른 사람의 원격
  브랜치에 있는 커밋은 세지 않습니다.
- 고유 커밋 수는 500에서 멈추고 *500+*로 표시합니다. 확인 창의 합계는 하한입니다 —
  *최소 N* — 쌓인 브랜치들이 커밋을 공유하기 때문입니다.
- 실행 취소는 브랜치와 그 upstream을 복원하지만, reflog나 다른 `branch.<name>.*`
  설정은 복원하지 않습니다.
- 긴 목록에서 대화 상자는 처음 400행을 보여 주고, 나머지는 필터로 찾습니다.
  **사라짐 + 병합됨 선택**은 보이든 안 보이든 모든 행에 적용됩니다.
