# 풀 리퀘스트 페이지

활발한 저장소에는 풀 리퀘스트가 스무 개씩 동시에 열려 있습니다. 사이드바에도
나오지만, 하나에 한 줄로는 알 수 있는 게 적습니다. 어느 것이 누구 것인지, 어느
것이 나를 기다리는지, 어느 것이 빨갛게 됐는지. 알아내려면 하나씩 열어서 읽고,
돌아가고, 다음 것을 열어야 했습니다. **풀 리퀘스트 페이지**는 이런 질문에 한
화면으로 답하고, 풀 리퀘스트를 연 뒤에는 **‹ ›**로 돌아가지 않고 같은 목록의
다음 항목으로 넘어갑니다.

![“pix”로 검색한 풀 리퀘스트 페이지: 일치 항목이 강조되고, 내 것에는 “나” 표시, 실패한 CI와 초안 하나](../../screenshots/pull-requests.webp)

## 여는 방법

- 사이드바 **풀 리퀘스트** 머리글의 **목록 아이콘**(*모든 풀 리퀘스트 보기*).
- 명령 팔레트(⌘K)의 *풀 리퀘스트…*, 또는 **도구 → 풀 리퀘스트…**.

위키나 [CI 실행](ci-runs.md)처럼 이 페이지도 저장소의 탭 위에 열립니다.

## 탭

| 탭 | 담긴 것 |
|---|---|
| **열림** | 초안을 포함한 모든 열린 풀 리퀘스트 |
| **초안** | 열린 것 중 초안으로 표시된 것만 |
| **병합됨** | 병합된 풀 리퀘스트. 탭을 처음 열 때 읽습니다 |
| **닫힘** | 병합 없이 닫힌 것(거절, 포기). 병합됨과 함께 읽습니다 |

열림과 초안 옆의 개수는 사이드바가 이미 가진 목록에서 가져옵니다. 병합됨과
닫힘은 둘 중 하나를 열 때만, 세션당 한 번 요청합니다. **새로 고침**은 다시
요청합니다.

## 필터

| 필터 | 남기는 것 |
|---|---|
| **검색** | 제목, 설명, 브랜치 또는 번호에 입력한 모든 단어가 들어 있는 풀 리퀘스트. `#482`나 `482`로 그 번호를 찾고, 일치 부분은 제목에서 강조됩니다 |
| **작성자** | 작성자 한 명 — 각자 이 탭에서 몇 개인지 함께 표시됩니다. **나**가 맨 위입니다 |
| **리뷰어** | 요청받은 리뷰어 한 명, 또는 **나에게 리뷰 요청됨** |
| **대상 브랜치** | 그 브랜치로 들어가는 풀 리퀘스트 |
| **내 것** | *작성자: 나*의 바로 가기 |
| **내 리뷰 대기** | *리뷰어: 나에게 리뷰 요청됨*의 바로 가기 |
| **CI 실패** | head의 검사가 실패한 풀 리퀘스트 |

필터 아래 줄에는 탭의 풀 리퀘스트 중 몇 개가 표시되는지, 어떤 필터가 켜져
있는지가 나오고, **필터 지우기**로 모두 해제할 수 있습니다.

필터는 저장소별로 **앱이 실행되는 동안** 유지됩니다. 페이지를 떠났다 돌아와도
그대로입니다. 재시작 후에는 일부러 저장하지 않습니다. 일주일 뒤 “내 것, CI 실패”
필터가 조용히 돌아오면, 숨기라고 하지 않은 풀 리퀘스트가 숨겨지기 때문입니다.

### “나”는 누구인가

“나”는 이 저장소의 호출이 호스트에 로그인하는 계정입니다. 저장소가
[연결된](profiles.md) 프로필, 없으면 활성 프로필이며, 호스트에 직접 물어서
정합니다. 토큰이 자신이 누구인지 말할 수 없거나(사용자 스코프 없음) 토큰이
없으면 **나**, **내 것**, **내 리뷰 대기**는 제공되지 않습니다.

## 목록

| 열 | 표시 내용 |
|---|---|
| **#** | 번호와 열림·초안·병합됨·닫힘 아이콘 |
| **제목** | 제목, *초안* 배지, 아직 리뷰를 요청받은 사람 — 나라면 강조 색으로 |
| **작성자** | 호스트가 주는 경우 그 사진, 아니면 이니셜. 내 것에는 **나** |
| **브랜치** | 소스 → 대상 |
| **검사** | head 검사의 요약 — `6/6`, `실패 1`, `실행 중 2`. 마우스를 올리면 개수 |
| **업데이트** | 마지막으로 바뀐 지 얼마나 됐는지. 마우스를 올리면 날짜 |

행은 최근 활동 순으로 정렬됩니다. 클릭하면 풀 리퀘스트 자체 페이지
([호스팅과 풀 리퀘스트](hosting.md))가 열립니다. 그런 페이지가 없는 호스트에서는
행이 브라우저에서 풀 리퀘스트를 엽니다.

[포크 체크아웃](hosting.md#포크-원본-저장소에-있는-내-풀-리퀘스트)에서는 원본 저장소에 있는 내 풀 리퀘스트도
목록에 나오며 *owner/repo에서*로 표시됩니다.

## 풀 리퀘스트에서 목록 넘기기

![필터링된 목록에서 연 풀 리퀘스트: ‹ 1 / 4 ›와 거쳐 온 필터](../../screenshots/pull-request-nav.webp)

페이지에서 연 풀 리퀘스트는 제목 위에 띠를 보여 줍니다.

- **← 풀 리퀘스트**는 목록으로 돌아갑니다. 필터는 떠날 때 그대로입니다.
- **‹ k / n ›**은 열어 온 목록의 이전 또는 다음 풀 리퀘스트로 이동합니다.
  클릭한 시점의 필터링된 목록과 그 순서 그대로입니다. 툴팁은 각 화살표가
  이어지는 풀 리퀘스트를 알려 줍니다.
- **Alt+← / Alt+→**로 키보드에서도 같은 일을 합니다. **설정 → 단축키**에서
  바꿀 수 있습니다. 커서가 텍스트 필드에 있을 때(Option+←가 단어 단위로 이동하는
  곳)와 터미널에 포커스가 있을 때는 동작하지 않습니다.

이동은 페이지를 그 자리에서 바꾸므로, 풀 리퀘스트 열 개를 넘겨도 탭에 아이콘이
열 개 남지 않습니다. 목록에서 다른 행을 열어도 바뀝니다.

**다른 곳에서** — 사이드바나 알림에서 — 연 풀 리퀘스트는 페이지의 기본 순서
(열림, 필터 없음)로 저장소의 열린 풀 리퀘스트를 넘깁니다. 그 목록에도 없는 것,
예를 들어 스택의 병합된 단계는 목록으로 돌아가는 길만 보여 줍니다.

## 풀 리퀘스트의 브랜치로 이동

풀 리퀘스트에서 작업하려면 그 브랜치를 체크아웃해야 합니다. 그리고 브랜치가
수천 개인 저장소에서는 브랜치 목록에서 이름으로 찾는 것이 느린 부분입니다. 풀
리퀘스트 페이지에서는 **브랜치** 필드가 그 일을 대신합니다.

- **브랜치 이름은 링크입니다.** 클릭하면 그 브랜치를 체크아웃하고 저장소
  그래프의 브랜치 끝으로 이동합니다. 풀 리퀘스트 페이지는 탭에 열린 채로
  남습니다.
- **서버에만 있는 브랜치**는 먼저 페치합니다 — 리모트 전체가 아니라 그 브랜치
  하나만 — 그리고 그것을 추적하는 로컬 브랜치로 체크아웃합니다. 이미 로컬에 있는
  브랜치는 있는 그대로 전환합니다. 업데이트하지 않으므로, 풀 리퀘스트의 최신
  커밋이 필요하면 풀하세요.
- **이미 있는 브랜치**에는 대신 *현재*가 표시됩니다. 아무것도 체크아웃하지
  않습니다.
- 각 이름 옆의 **복사 버튼**은 이름을 클립보드에 넣습니다.
- **실행 취소**(⌘Z)는 원래 있던 브랜치로 돌아가고 체크아웃이 만든 로컬
  브랜치를 삭제합니다. 단, 그 뒤에 그 브랜치에 커밋했다면 그대로 둡니다.

머리글에도 같은 두 동작이 버튼으로 있습니다: **소스 브랜치로 이동**과 **대상
브랜치로 이동**. 이미 있는 브랜치에서도 동작하며, 그때는 저장소로 데려다줄
뿐입니다. [아이콘 색상](themes.md#아이콘-색상)을 켜면 머리글의 버튼마다 고유한 색이 붙습니다: 새로 고침은 파랑, AI 리뷰는 보라, 미리보기는 청록, 소스 브랜치는 초록, 대상 브랜치는 주황(브라우저에서 열기는 회색 그대로).

클릭하기 전에는 아무것도 조회하지 않습니다. 풀 리퀘스트를 열어도 어떤 브랜치도
읽거나 페치하지 않습니다.

하지 않는 일:

- **포크의 소스 브랜치**는 다른 저장소에 있으므로 링크가 없습니다(복사 버튼은
  남습니다). 바로 아래에 있는 **풀 리퀘스트를 로컬에서 미리보기…**가 여기서
  실행하는 방법입니다. 대상 브랜치는 여전히 링크입니다.
- **일치하는 리모트 없음.** 브랜치는 URL이 풀 리퀘스트의 저장소인 리모트에서
  찾습니다. 그곳을 가리키는 리모트가 설정되어 있지 않으면 링크는 아무것도 하지
  않고, 툴팁이 이유를 알려 줍니다.
- **삭제된 브랜치.** 병합된 풀 리퀘스트는 브랜치를 함께 지운 경우가 많습니다.
  그러면 페치가 리모트에 그 브랜치가 더 이상 없다고 알리고, 풀 리퀘스트에
  그대로 머뭅니다.
- **로컬 변경.** 체크아웃은 파괴적이지 않으므로 확인 창이 없습니다. 커밋하지
  않은 변경이 덮어써질 경우 git이 체크아웃을 거부합니다. 오류에 파일이 나오니
  커밋하거나 스태시한 뒤 다시 클릭하세요.
- **이 창.** 체크아웃은 이 저장소의 작업 트리에서 일어납니다. 브랜치가 이미 다른
  [워크트리](worktrees.md)에 체크아웃되어 있으면 대신 그 워크트리의 탭이
  열립니다.

## 커밋

사이드바는 풀 리퀘스트에 커밋이 몇 개인지는 알려 줬지만, 어떤 것인지는 알려 주지
않았습니다. 커밋을 하나씩 리뷰하려면 — 대부분의 풀 리퀘스트는 그렇게 읽도록
만들어집니다 — 브라우저로 가야 했습니다. 대화와 업데이트 사이의 **커밋** 탭이 그것을
나열합니다.

- **오래된 것부터**, 적용되는 순서대로, 작성된 날짜별로 묶어서 보여 줍니다. 날짜
  순서를 벗어나 리베이스로 들어온 커밋은 옮겨지지 않고 자기만의 날짜를 새로
  시작합니다.
- 각 행에는 작성자 사진(호스트가 주는 경우), 제목, 작성자, 경과 시간, 짧은 SHA가
  있습니다. 부모가 둘인 커밋에는 호스트가 알려 주면 **병합** 배지가 붙습니다.
- 제목 외에 내용이 더 있는 커밋 옆의 **▸**는 메시지의 나머지를 보여 줍니다.
- **복사**는 전체 SHA를 클립보드에 넣고, **브라우저에서 열기**는 호스트에서 커밋을
  엽니다 — 호스트에 그런 페이지가 있으면 풀 리퀘스트 안에서(GitHub, GitLab,
  Bitbucket Data Center), 없으면 저장소의 커밋 페이지에서.

![커밋 탭: 풀 리퀘스트의 커밋이 날짜별로 묶여 있고, 하나는 전체 메시지가 열려 있음](../../screenshots/pr-commits.webp)

**행을 클릭**하면 — 또는 Tab으로 이동해 Enter를 누르면 — 그래프에서 클릭한 것처럼
앱에서 커밋을 엽니다. 저장소 보기에서 그 커밋이 선택되고 세부 정보가 열립니다. 이
클론에 그 커밋이 **있을 때** 동작합니다. 없으면 행이 조용히 실패하는 대신 그렇다고
알리고 다음을 제안합니다.

- **PR 브랜치를 가져와서 보기** — [브랜치로 이동](#풀-리퀘스트의-브랜치로-이동)과 같은 브랜치 하나만의
  페치이며, 체크아웃은 하지 않습니다. 커밋이 함께 오면 열리고, 오지 않으면(그 뒤
  강제 푸시로 다시 쓰인 경우) 토스트가 알려 줍니다.
- **풀 리퀘스트의 커밋 가져오기** — **포크**에서 온 풀 리퀘스트의 경우. 그 브랜치는
  다른 저장소에 있지만, 대부분의 호스트는 풀 리퀘스트의 head를 대상 저장소에 전용
  ref로 비춰 둡니다 — `refs/pull/N/head`(GitHub, GitHub Enterprise Server, Forgejo),
  `refs/merge-requests/N/head`(GitLab), `refs/pull-requests/N/from`(Bitbucket Data
  Center). 앱은 그 ref 하나만, 태그 없이, 앱 전용 ref인 `refs/githuttbr/pr/<remote>/N`
  으로 페치하고, 커밋은 다른 커밋처럼 열립니다: 그래프는 그 head를 레이블 없는 줄로
  그립니다. 다시 페치하면 ref가 그때의 head로 옮겨집니다. 그 뒤의 강제 푸시로 커밋이
  빠졌다면 토스트가 알려 줍니다.
- **브라우저에서 열기** — 페치가 선택지가 아닐 때를 위해.

목록은 페이지와 함께가 아니라 탭을 처음 열 때 읽고, **새로 고침**할 때마다 다시
읽습니다. 들어오기 전까지 탭의 개수는 호스트가 그 풀 리퀘스트에 대해 준
숫자입니다. 병합되거나 닫힌 풀 리퀘스트도 같은 방식으로 커밋을 나열합니다.

하지 않는 일:

- **최대 250개의 커밋.** GitHub 자체가 풀 리퀘스트에 대해 250개까지만 나열합니다.
  앱은 모든 호스트에서 같은 숫자에서 멈추고, 더 있으면 *호스트에는 더 있습니다*라고
  알리며 호스트의 풀 리퀘스트로 가는 링크를 붙입니다. 어떤 250개인지는 호스트가
  나열하는 순서에 달려 있습니다 — 앱은 먼저 나열된 것을 남기고, 목록 위의 줄이
  어느 쪽인지 알려 줍니다.

  | 호스트 | 더 긴 풀 리퀘스트에서 보이는 것 |
  |---|---|
  | GitHub | **처음** 250개(GitHub 자체의 한도) |
  | GitLab, Azure DevOps, Bitbucket Data Center, bitbucket.org | **가장 최근 250개** |
  | Forgejo | 서버가 먼저 나열하는 쪽. 그 순서는 문서화되어 있지 않습니다 |
- **호스트가 비춰 두지 않는 포크의 head.** Azure DevOps는 병합 결과만 공개하고 풀
  리퀘스트 자체의 head는 공개하지 않으며, bitbucket.org는 둘 다 공개하지 않습니다:
  그곳에서는 행이 브라우저만 제안합니다. 비춰 두지 않는 것으로 드러난 다른 호스트에서는
  페치가 그렇다고 알려 줍니다. 필요하다면 **풀 리퀘스트를 로컬에서 미리보기…**가 Azure의
  병합 결과를 가져옵니다.
- **페치한 head는 남습니다.** `refs/githuttbr/pr/…`는 브랜치가 아닙니다: 체크아웃하거나
  푸시할 것이 없고, prune 페치도 건드리지 않으며, git이 그 커밋을 보관합니다. 지우는
  것도 없습니다 — 페이지를 닫아도, [브랜치 정리](branch-cleanup.md)로도. 없애려면
  ref를 직접 지우세요: `git for-each-ref refs/githuttbr/pr`가 목록을 보여 주고,
  `git update-ref -d <ref>`가 하나를 지웁니다.
- **이름에 `/`가 들어간 원격**은 그 ref 이름의 한 부분이 될 수 없으므로, 그곳에서는
  페치가 거부됩니다.
- **삭제된 브랜치.** 병합된 풀 리퀘스트는 브랜치를 함께 지운 경우가 많습니다. 그러면
  페치가 그렇다고 알립니다. bitbucket.org는 소스 브랜치가 사라지면 커밋을 전혀
  나열하지 않습니다.
- **스쿼시 병합.** 스쿼시 병합된 풀 리퀘스트의 커밋은 대상 브랜치에 들어간 적이
  없으므로, 브랜치가 삭제된 뒤에는 호스트에만 있습니다.
- **작성자**는 커밋에 적힌 이름으로 표시됩니다. GitLab, Azure DevOps, Bitbucket
  Data Center는 이미지가 보낼 수 없는 로그인 없이는 사진을 주지 않으므로, 그 행들은
  이니셜을 보여 줍니다.
- **Azure DevOps의 긴 메시지**는 잘릴 수 있습니다. Azure의 목록이 커밋 메시지를
  잘라 보내고, 앱은 받은 것을 보여 줍니다.
- **bitbucket.org** 풀 리퀘스트는 브라우저에서 열립니다 — 앱에 아직 그 페이지가
  없습니다 — 그래서 앱이 목록을 읽을 수는 있지만 그곳에서는 이 탭에 닿지 않습니다.

## 업데이트

월요일에 리뷰한 풀 리퀘스트는 목요일이면 앞으로 나아가 있습니다. 커밋 탭은 지금
어디에 있는지는 보여 주지만, 그 사이에 무슨 일이 있었는지는 보여 주지 않습니다: 어떤
커밋이 어떤 푸시로 왔는지, 누군가 강제 푸시로 이미 읽은 내용을 다시 썼는지, 그리고
코드가 *내가 본 버전과 비교해* 어떻게 보이는지. 커밋과 파일 사이의 **업데이트** 탭이
여기에 답합니다 — Azure DevOps 자체의 Updates 탭처럼.

풀 리퀘스트에 대한 각 푸시를 **최신순**으로 나열합니다.

- **업데이트 1 — 열림**은 풀 리퀘스트를 열 때의 푸시입니다. 이후 푸시는 차례로 다음
  번호를 받습니다.
- 각 항목에는 **언제**, **누가 푸시했는지**(호스트가 알려 주는 경우), 그리고 **추가된
  커밋** — 짧은 SHA, 제목, 작성자 — 가 나옵니다. 푸시가 브랜치에서 빼낸 커밋을
  호스트가 알려 주면, 취소선과 함께 **제거된 커밋** 아래에 나열됩니다.
- 강제 푸시나 리베이스에는 **기록 재작성됨** 표시가 붙습니다: 읽었던 커밋이 사라졌을
  수 있고, 나열된 커밋은 예전 작업의 새 복사본일 수 있습니다. Azure DevOps에서는 풀
  리퀘스트를 다른 대상 브랜치로 옮긴 푸시에 **대상 변경됨** 표시가 붙습니다.

![업데이트 탭: 최신순 푸시, “기록 재작성됨”으로 표시된 강제 푸시, 새 항목으로 표시된 것 하나](../../screenshots/pr-updates.webp)

### 업데이트 하나에서 바뀐 것

**이 업데이트의 변경 사항 보기**는 그 푸시만으로 파일 탭을 엽니다: 이전 업데이트의
head에서 이 업데이트까지의 diff — 업데이트 1이라면, 호스트가 그 지점을 알려 주는
경우(Azure DevOps, GitLab) 열 때의 대상 브랜치에서부터. 같은 파일 트리와 뷰어에
배너 — *업데이트 3의 변경 사항 표시 중 (업데이트 2 대비)* — 와, 풀 리퀘스트 전체로
돌아가는 **모든 변경 사항 보기**가 붙습니다.

![업데이트 하나의 변경 사항을 보여 주는 파일 탭, 파일 트리 위의 배너](../../screenshots/pr-update-diff.webp)

diff는 가능하면 언제나 **이 클론에서** 만듭니다: 두 head 사이의 `git diff`로, 정확하고
호스트에 묻지 않습니다. 두 head 중 하나가 없으면 앱은 먼저 풀 리퀘스트의 원격에서 둘
다 **커밋 ID로** 페치하고 — 브랜치도, 태그도, ref도 쓰지 않습니다. 강제 푸시로 바뀐
head는 더 이상 어떤 브랜치에도 없지만, 대부분의 호스트는 여전히 ID로 내줍니다 — 여기서
비교합니다. 그 페치가 실패할 때만 호스트에 묻습니다.

| 호스트 | 호스트의 비교 |
|---|---|
| Azure DevOps | `$compareTo`를 붙인 반복의 변경 사항 — 두 푸시 사이 |
| GitLab | 저장소 비교, 한 head에서 다른 head로 바로 |
| Bitbucket Data Center | 저장소 비교 — 두 head의 **공통 기준에서** |
| GitHub | Compare API(`base...head`) — 두 head의 **공통 기준에서** |
| Forgejo / Gitea | 없음: API에 두 커밋 사이의 diff가 없습니다 |

공통 기준에서 비교하면 재작성의 diff는 그 푸시가 한 일이 아닙니다: 제거한 것은 보이지
않고, 그 뒤 대상 브랜치가 받은 변경이 풀 리퀘스트의 변경처럼 보일 수 있습니다. 기록이
재작성된 업데이트를 그렇게 비교했을 때는 배너가 알려 줍니다 — *공통 기준에서
비교했습니다. 이 푸시가 제거한 내용은 표시되지 않습니다.* 아무것도 되지 않으면 배너가
그렇다고 알리고, 브랜치(포크라면 풀 리퀘스트의 head)를 페치해 여기서 비교하자고
제안합니다.

줄 댓글은 풀 리퀘스트 전체 diff에 속하므로, 업데이트 하나를 보여 주는 동안에는 줄에
**+**가 없습니다. 배너가 그렇다고 알려 줍니다. 파일을 확인함으로 체크하는 것은 평소대로
동작합니다 — 풀 리퀘스트의 파일에 표시합니다.

### 마지막 방문 이후 새로운 것

마지막으로 탭을 연 뒤 푸시된 업데이트에는 **새 항목** 배지가 붙고, 탭 자체에도 몇
개인지 나옵니다: *업데이트 5 · 새 항목 2*. 탭을 열면 확인한 것으로 표시됩니다(어떤 것이
새로웠는지 볼 수 있도록 탭에 있는 동안 배지는 남습니다). 탭을 연 채로 **새로 고침**이
더 가져오면 **확인함으로 표시**로 지울 수 있습니다. 풀 리퀘스트 페이지만 열어서는
아무것도 표시되지 않습니다. 풀 리퀘스트의 업데이트 탭을 처음 열 때는 아무것도 새롭지
않습니다 — 비교할 이전 방문이 없기 때문입니다.

업데이트는 그 개수를 위해 페이지와 함께 읽고, **새로 고침** 때 다시 읽습니다 — 게시하는
댓글이나 리뷰마다가 아닙니다.

확인한 상태는 이 컴퓨터에만, 저장소와 풀 리퀘스트별로 보관되며, 호스트에는 보내지
않습니다.

### 호스트별

| 호스트 | 업데이트의 출처 | 푸시한 사람 | 제거된 커밋 | 재작성 감지 |
|---|---|---|---|---|
| Azure DevOps | 풀 리퀘스트의 **반복(iteration)** — 각 푸시에 대한 Azure 자체의 기록 | 예 | 아니요(알려 주지 않음) | 예: `forcePush` / `rebase` |
| GitLab | 머지 리퀘스트의 **diff 버전**. 각 버전의 커밋은 그 head에서 계산 | 아니요(버전은 아무도 밝히지 않음) | 예 | 예: 더 이상 닿지 않는 이전 head |
| Bitbucket Data Center | 풀 리퀘스트의 활동: **OPENED**와 소스 브랜치를 옮긴 각 **RESCOPED** | 예 | 예, 호스트의 합계와 함께 | 예: 커밋을 제거한 rescope |
| GitHub | 타임라인의 커밋과 강제 푸시에서 **추정** — 아래 참고 | 강제 푸시만 | 아니요 | 예: 강제 푸시 이벤트 |
| Forgejo / Gitea | 타임라인의 **push** 항목. 첫 항목은 풀 리퀘스트 자체와 함께 기록됨 | 예 | 아니요 | 예: 강제 푸시 항목 |
| bitbucket.org | 사용할 수 없음 | — | — | — |

**GitHub는 일반 푸시를 기록하지 않습니다** — 강제 푸시만 기록합니다 — 그래서 업데이트는
**커밋 시각으로 추정**합니다. 업데이트는 강제 푸시 사이에서 서로 위에 쌓인 커밋의
연속입니다. 앞 커밋 위에 쌓이지 않았거나 앞 커밋보다 10분 넘게 늦게 온 커밋은 다음
업데이트를 시작합니다. 풀 리퀘스트를 연 뒤 커밋된 것은 열 때 포함됐을 수 없습니다.
그래서 한 시간 간격으로 만든 커밋을 한 번에 푸시하면 둘로 **나뉘어** 보이고, 몇 분
간격의 두 푸시는 **하나**로 보입니다. 탭은 묶음이 대략적이라고 알려 줍니다. 리베이스의
새 커밋은 타임라인이 그 강제 푸시 바로 앞에 나열할 수 있는데, 그 강제 푸시의 것으로
칩니다. 강제 푸시 전후의 head는 정확하므로, 그 **변경 사항 보기**도 정확합니다.

### 제한

- **상한.** 최신 업데이트 100개를 나열합니다. GitHub의 타임라인은 최신 끝에서부터 최대
  500개, Bitbucket Data Center의 활동(이것도 최신순)은 최대 1,000개, GitLab의 버전과
  커밋은 각각 최대 300개, Forgejo의 타임라인은 최대 500개(더 길면 최신 것)를 읽습니다.
  상한 때문에 **열 때의 업데이트**가 잘리면 번호는 더 이상 호스트의 것이 아닙니다: 탭이
  그렇다고 알리고 최신부터 거꾸로 셉니다(*최신 업데이트*, *업데이트, 최신보다 2개
  이전*).
- **Azure DevOps**는 제거된 커밋을 알려 주지 않습니다. 대신 강제 푸시나 리베이스에
  표시가 붙습니다. Azure가 커밋 목록을 잘라 낸 반복은 따로 읽고(최대 500개 커밋), 그래도
  불완전하면 업데이트가 알려 줍니다.
- **GitLab**은 푸시한 사람을 밝히지 않습니다. head가 재작성으로 사라진 버전은 그
  커밋을 찾으려고 따로 읽습니다 — 그런 버전 중 최신 10개에 대해 — 세션마다 한 번:
  버전은 바뀌지 않기 때문입니다.
- **Forgejo와 Gitea**는 강제 푸시의 커밋을 나열하지 않습니다 — 두 head뿐이며, **변경
  사항 보기**가 비교하는 것도 그것입니다 — 그리고 강제 푸시 뒤에는 열 때 무엇이 있었는지
  알려 주는 것이 없어, 서버가 열 때의 푸시 자체를 기록하지 않았다면 비어 있습니다.
  API에 두 커밋 사이의 diff가 없으므로, 그 비교에는 두 커밋 모두 이 클론에 있어야
  합니다. 타임라인 API가 없는 서버는 모든 커밋을 업데이트 하나에 보여 줍니다.
- **ID로 페치**하려면 커밋을 ID로 내주는 호스트가 필요합니다. GitHub는 아직 가진 커밋이면
  무엇이든 내주지만, 다른 호스트나 일반 git 서버는 어떤 브랜치도 가리키지 않는 커밋을
  거부할 수 있습니다 — 그때는 호스트의 비교를 씁니다. 페치한 커밋은 ref 없이 이 클론에
  남고, git이 때가 되면 정리합니다.
- **Bitbucket Data Center의 비교**는 서버의 구조화된 diff를 읽어 unified 형식으로
  그립니다. 아주 큰 파일은 잘린 채로 올 수 있습니다.
- 재작성된 head는 **호스트에서** 영영 **사라졌을** 수 있습니다(Azure와 GitLab은 보관하고,
  다른 곳은 정리할 수 있습니다). 그러면 어느 쪽도 비교할 수 없고, 배너가 그렇다고
  알려 줍니다.
- **bitbucket.org** 풀 리퀘스트는 브라우저에서 열리며, 업데이트 탭이 없습니다.

## 파일 읽기

파일이 이백 개인 풀 리퀘스트는 전체 경로 이백 개로 읽기 어렵습니다. **파일** 탭의
목록에는 커밋 패널과 같은 **경로 / 트리** 전환이 있고, 그 선택은 앱 전체에서
같습니다. **트리**에서는 파일이 폴더 아래에 놓이고(`src/main/ipc` 같은 연쇄는 한
행입니다), 각 폴더는 합계 **+/−**와 그 안의 파일 중 몇 개를 확인했는지(*3/5*)를
보여 줍니다. 폴더의 체크박스는 안의 모든 파일을 확인함으로 표시하거나 모두 지웁니다.
체크 표시는 이 컴퓨터에만 저장되고 호스트로는 절대 보내지 않습니다. 체크 표시는
파일 diff의 버전을 기억하므로, 푸시가 확인한 파일을 바꾸면 노란 점(*확인한 뒤
변경됨*)과 함께 다시 확인하지 않은 상태가 됩니다. diff가 없는 파일(바이너리, 너무
큰 파일)은 상태와 줄 수로만 비교합니다. 리뷰 대화가 있는 파일 옆에는 말풍선 개수가 표시되어(폴더는 안의 개수를 합칩니다) 긴 목록에서도 댓글이 있는 파일이 눈에 띕니다. 오래된 대화도 셉니다. 폴더를 클릭하거나 그 위에서 ←/→를 누르면
접힙니다. ↑/↓(또는 j/k)는 화면의 파일을 차례로 지나며 각 diff를 엽니다. 접은
폴더는 앱을 종료할 때까지 풀 리퀘스트별로 기억되며, 그 안의 파일을 열면 그곳까지
가는 길이 펼쳐집니다. 트리는 호스트가 파일을 나열하는 순서가 아니라 이름순입니다.

![트리 보기의 파일 탭: 합계 변경과 확인한 개수가 붙은 폴더, 하나는 접혀 있음](../../screenshots/pr-files-tree.webp)

**이미지.** 풀 리퀘스트가 추가하거나 삭제하거나 바꾸는 그림(png, jpg, gif, webp, bmp, ico,
avif, svg)에는 읽을 텍스트 diff가 없으므로, 탭은 대신 그림을 보여 줍니다. 커밋에서 보는 것과
같은 보기로, 새 그림, 이전 그림, 또는 이전과 이후를 나란히 놓고 슬라이더로 비교합니다. 이름이
바뀐 그림은 베이스의 이전 경로와 헤드의 새 경로를 비교하고, 업데이트 하나의 diff에서는 그
업데이트의 두 헤드를 비교합니다. 바이트는 커밋이 이 클론에 있으면 여기서 가져오고(무료이고
빠릅니다), 없으면 저장소의 프로필로 호스팅에서 가져옵니다. 한계: 32 MB를 넘는 그림은
미리 보지 않습니다. 줄 댓글은 그림에 달리지 않습니다(SVG는 텍스트 diff와 그 댓글을 아래에
유지합니다). **Git LFS**에 저장된 그림은 클론에 포인터만 있으므로 호스팅에서 읽습니다.
GitLab, Azure DevOps, Forgejo는 이를 해석하지만 GitHub API는 포인터만 주므로, 거기서는 탭이
호스팅으로 안내합니다. 호스팅이 병합 베이스를 알려 주지 않는 경우(그때는 대상 브랜치의 끝을
대신 씁니다), 메모가 “이전”에 대상 브랜치의 나중 변경이 들어 있을 수 있다고 알려 줍니다.
클론도 호스팅도 바이트를 줄 수 없으면 탭이 그렇게 말하고, 풀 리퀘스트의 브랜치를 가져오거나
호스팅에서 열도록 제안합니다.

![풀 리퀘스트가 바꾼 그림을 이전과 이후로 나란히 놓은 모습](../../screenshots/pr-image-diff.webp)

**경로와 편집기.** diff 위의 막대에는 파일 경로를 복사하는 버튼과 **⋯** 메뉴가 있고, 목록에서
파일이나 폴더를 오른쪽 클릭해도 같은 메뉴가 열립니다. 메뉴는 경로, 이름이 바뀐 파일의 이전
경로, 폴더의 경로를 복사하고, 파일을 [편집기](editor.md)(또는 다른 앱)에서 열거나 파일
관리자에서 표시합니다. 뒤의 두 동작은 풀 리퀘스트의 버전이 아니라 **작업 사본**에 대해
동작합니다. 작업 사본에 있는 파일에만 쓸 수 있고(PR이 삭제하는 파일이나 브랜치에 없는 파일은
이유를 알려 줍니다), 체크아웃된 브랜치가 PR의 브랜치가 아니면 어느 브랜치의 파일을 열게
되는지 메뉴가 알려 줍니다.

**돌아오기.** 풀 리퀘스트를 떠나 저장소, 다른 탭, 다음 PR로 가도, 돌아오면 떠날 때 그대로
있습니다. 같은 탭, 같은 열린 파일, 같은 스크롤 위치, 그리고 보내지 않은 모든 텍스트(댓글,
답글, 줄 댓글, 편집)가 남아 있습니다. 이는 풀 리퀘스트를 닫거나 앱을 끝낼 때까지
유지됩니다. 메모리에만, 최근 풀 리퀘스트 50개에 대해 보관하며(그 이상이면 가장 오래된
자리를 놓고, 그 안에 있던 텍스트는 다음에 여는 풀 리퀘스트 페이지로 넘어갑니다), 보내지
않은 텍스트가 있는 PR을 닫으면 먼저 묻습니다. 새로 고침에서 초안의 자리가 사라진 것으로
나타나면(답하던 토론, 편집하던 댓글, 속한 파일), 텍스트는 사라지지 않고 복사하거나 버릴
때까지 페이지 위쪽에서 기다립니다.

### diff는 어디서 오는가

리뷰는 읽는 diff만큼만 좋습니다. 호스팅 API는 그 원천으로 적합하지 않습니다. Azure DevOps는
diff를 전혀 보내지 않고 파일 목록만 보내므로 파일마다 두 번 내려받아 비교해야 합니다.
GitHub은 3000개 파일에서 멈추고 큰 파일의 패치를 빼먹습니다. GitLab은 큰 diff를 *너무 큼*으로
표시하고 아무것도 보내지 않습니다. 그래서 파일 탭은 어느 호스팅에서든 **먼저 이 클론을
읽습니다**.

1. 호스팅에 풀 리퀘스트의 두 커밋, 즉 시작점과 헤드를 묻습니다. Azure DevOps, GitLab,
   Forgejo는 병합 베이스를 알려 줍니다. Bitbucket Data Center는 줄 댓글이 묶이는 diff의
   베이스를 알려 줍니다. GitHub은 대상 브랜치만 알려 주므로, 헤드와의 병합 베이스는 여기서
   계산합니다(커밋이 없으면 GitHub의 비교로). 이미지 미리 보기도 같은 두 커밋을 씁니다.
2. 둘 다 여기 있으면 그 사이의 `git diff`가 모든 파일을 주며, 개수에 제한이 없습니다. 호스팅
   자체 페이지가 비교하는 것과 같은 두 커밋이므로, 여기의 줄 번호가 곧 거기의 줄 번호이고
   줄 댓글은 놓은 자리에 달립니다.
3. 여기 없으면 풀 리퀘스트의 원격에서 **id로** 가져옵니다. 객체만 가져오며 브랜치는 만들지도
   옮기지도 않습니다. 페이지를 열 때 한 번(새로 고침 때 다시) 가져오고, 그동안 목록 위에
   *풀 리퀘스트의 커밋을 가져오는 중…*이 표시됩니다. id로 커밋을 내주지 않는 서버(일부 Azure
   DevOps와 일반 git 서버)는 조용히 건너뜁니다.
4. 그때가 되어서야 호스팅 API를 쓰며, API가 diff를 주지 않는 파일은 빈 척하지 않고 이유를
   알려 줍니다(아래).

나중에 읽은 파일(*아직 불러오지 않음* 상태에서 연 파일, 또는 **다시 시도** 후의 파일)도
다른 파일처럼 목록에 합류합니다. 같은 뷰어로 보이고 줄 댓글도 달 수 있습니다.

Azure DevOps에서 API 경로는 탭을 열 때 처음 100개 파일을, 한 번에 3개씩 합쳐서 1분 안에
읽고, 나머지는 각 파일을 열 때 읽습니다. 제한을 받은 요청은 서버가 요구하는 대기 시간 동안
모든 읽기를 멈춥니다. 그래도 실패한 요청은 이유와 함께 그렇게 알려 줍니다. 파일이 텍스트인지는
Azure의 *binary* 플래그가 아니라 바이트로 판단합니다. Azure는 UTF-16 파일과 ASCII가 아닌
텍스트 일부에도 그 플래그를 붙이기 때문입니다. 호스팅이 풀 리퀘스트에 있는 것보다 적은
파일을 나열하면(GitHub은 3000에서 멈춥니다), 목록 위의 한 줄이 그렇다고 알려 줍니다.

### 파일에 diff가 보이지 않을 때

| 표시 | 이유 | 할 수 있는 일 |
|---|---|---|
| **바이너리** | 바이트가 텍스트가 아닙니다: 그림, 압축 파일. UTF-16과 오래된 1바이트 텍스트는 텍스트로 인식합니다. | 호스팅에서 엽니다. |
| **너무 커서 표시할 수 없음** | 바뀐 줄이 20,000줄 또는 diff가 8 MB를 넘거나, 한 버전이 4 MB를 넘습니다. 클론이 읽었다면 **+/−**는 그래도 셉니다. | 호스팅에서 엽니다. |
| **아직 불러오지 않음** | 한 번의 읽기가 보관하는 범위(diff 약 150,000줄)를 넘었거나, Azure DevOps API로 처음 100개 파일 또는 1분을 넘었습니다. | 열면 불러옵니다. 안 되면 **diff 불러오기**. |
| **불러오지 못함** | 읽기가 실패했습니다. 이유가 아래에 표시됩니다. | **다시 시도**. |
| **호스팅이 건너뜀** | 호스팅 API가 diff를 보내지 않았고, 이 클론에 풀 리퀘스트의 커밋이 없습니다. | **풀 리퀘스트를 가져와 로컬에서 보기**(id로 커밋을, 또는 포크에서 풀 리퀘스트의 헤드를). 그다음 diff는 여기서 만들어집니다. |
| **이름 또는 모드만 바뀜** | 이름 변경이나 권한 변경으로, 내용은 같습니다. | 내용에는 리뷰할 것이 없습니다. |
| **인코딩이 바뀜** | 같은 텍스트를 다르게 저장했습니다: 바이트 순서 표시 추가 또는 제거, UTF-16을 UTF-8로 변환. | 의도한 변경인지 확인합니다. 신경 쓰는 도구도 있습니다. |

목록에서 diff를 읽지 못한 파일(아직 불러오지 않음, 불러오지 못함, 호스팅이 건너뜀)은
**+0 −0** 대신 **—**를 보여 줍니다. **+0 −0**은 “아무것도 바뀌지 않음”으로 읽히기 때문입니다.
바이너리 파일과 단순 이름 변경은 실제 **+0 −0**을 보여 주고, 호스팅이 줄 수를 세어 주는
경우(GitHub은 건너뛴 패치에도 셉니다) 그 수를 보여 줍니다.

## 줄에 댓글 달기

여기서 리뷰 스레드에 답하는 것은 가능했지만 새로 시작할 수는 없어서, 제대로 된
리뷰는 여전히 브라우저로 가야 했습니다. 풀 리퀘스트의 **파일** 탭에서는 diff의
어느 줄이든 그 줄만의 댓글을 받습니다.

- **줄에 마우스를 올리고** 번호 위에 나타나는 **+**를 누르거나, **줄 자체를
  클릭**합니다(텍스트 선택을 끝내는 클릭이나 단어를 선택하는 더블 클릭은 세지
  않습니다 — 그건 읽는 것입니다). 오른쪽 클릭 메뉴 — 또는 키보드의 컨텍스트 메뉴
  키 — 에도 *N번째 줄에 댓글 달기*가 있습니다.
- **그 줄 아래**에 입력란이 열립니다. 작성한 뒤 **댓글** — 또는 ⌘/Ctrl+Enter.
  **취소**로 닫고, **Esc**로도 닫으며 무언가 입력했다면 먼저 묻습니다. 어느 쪽이든
  포커스는 그 줄로 돌아갑니다.
- 성공하면 새 스레드가 **그 줄 아래**와, 다른 모든 사람이 보게 될 대화 탭의 리뷰
  스레드에 나타납니다.

![바뀐 줄 아래에서 작성 중인 댓글과, 자기 줄 아래에 있는 이전 스레드](../../screenshots/pr-line-comment.webp)

댓글이 어느 쪽에 붙는지는 줄에 따라 정해집니다.

| 줄 | 고정 위치 |
|---|---|
| **추가됨**(초록) | 파일의 새 버전, 새 줄 번호 |
| **삭제됨**(빨강) | 옛 버전, 옛 줄 번호 |
| **변경 없음** | 새 버전(GitLab에는 요구하는 대로 두 번호를 모두 보냅니다) |

기존 스레드도 각자의 줄 아래에 그려지며, 호스트가 스레드 안에서 앱의 답글을 허용하는
곳에서는 답글 입력란도 함께 나옵니다(Forgejo는 허용하지 않습니다). 스레드는 호스트가
아직 표시된 diff에 속한다고 말할 때만 줄 위에 그려지고, 나머지는 추측한 줄 대신 대화
탭에 남습니다.

| 호스트 | 마지막 푸시 전에 작성된 스레드 |
|---|---|
| GitHub | 줄이 바뀌면 오래된 것으로 처리: 대화에만 |
| GitLab | 이전 head에 대해 작성됨: 대화에만 |
| Azure DevOps | Azure가 줄이 지금 있는 곳까지 따라감 |
| Bitbucket Data Center | 줄이 사라지면 고아가 됨: 대화에만 |
| Forgejo | Forgejo는 댓글이 오래됐는지 알려 주지 않으므로 기록된 줄 번호에 그립니다 — 푸시 뒤에는 그 줄에 다른 코드가 있을 수 있습니다 |

표시된 hunk 밖의 줄에 단 댓글은 모든 호스트에서 대화 탭에만 있습니다.

입력하고 보내지 않은 댓글은 기본 댓글 상자의 텍스트처럼 풀 리퀘스트에 남습니다. **‹ ›**,
Alt+화살표, 다른 탭으로 가도 그 자리에 그대로 있고, 돌아오면 다시 그 줄에 있습니다(위의
*돌아오기* 참고). 다른 파일을 둘러봐도 유지됩니다. 다른 줄에서 댓글을 시작하려면 먼저 첫
댓글을 보내거나 취소하세요.

하지 않는 일:

- **한 줄씩, 즉시 게시.** 줄 범위도, 댓글을 모았다가 나중에 제출하는 보류 중인
  리뷰도, 변경 제안도 없습니다. 각 댓글은 보내는 순간 독립된 스레드로 게시됩니다
  (Forgejo에서는 단일 댓글 호출이 없으므로, 그 댓글 하나만 담은 리뷰로).
- **보고 있는 diff 기준.** 파일 탭은 diff를 어느 커밋(Azure DevOps에서는 어느
  반복)에서 읽었는지 기억하고, 댓글은 그것을 기준으로 보냅니다. 그 뒤로 풀
  리퀘스트가 진행됐다면 — 푸시, 새 병합 기준 — 지금 그 번호를 가진 줄에 댓글을 달지
  않고 *이 diff를 불러온 뒤 풀 리퀘스트가 바뀌었습니다*로 거부하며, **새로 고침**이
  새 diff를 보여 줍니다. GitHub에서는 대신 읽었던 커밋을 기준으로 게시하고, 그 줄이
  바뀌었으면 GitHub가 오래된 것으로 표시합니다. 그래도 호스트가 받지 않는 줄은 diff
  밖으로 거부됩니다.
- **거부됨.** 댓글 권한이 없으면(읽기 전용 토큰, 저장소가 댓글을 허용하지 않는
  계정) 호스트가 거부하고, 메시지가 그것이 이유라고 알려 줍니다.
- **bitbucket.org** 풀 리퀘스트는 브라우저에서 열립니다 — 앱에 아직 그 페이지가
  없습니다 — 그래서 그곳의 줄 댓글은 여전히 웹사이트에서 답니다.
- **diff가 없는 파일**(바이너리이거나 호스트가 포함하지 않을 만큼 큰 파일)에는
  댓글을 달 줄이 없습니다.

## 댓글 쓰기

페이지의 모든 입력란 — 아래쪽의 댓글, 스레드 안의 답글, 줄에 다는 댓글 — 은 같은
Markdown 편집기입니다. **작성 / 미리 보기** 탭, GitHub 단축키를 갖춘 서식 도구
모음, Enter로 이어지는 목록, 그리고 화면에 이미 있는 사람과 풀 리퀘스트로부터의
**@** / **#** 자동 완성. 답글 입력란은 클릭하면 도구가 나타나며, 이제 Enter가 새
줄을 시작하므로 ⌘/Ctrl+Enter로 보냅니다. 자세한 내용과 제한은
[댓글 쓰기](writing-comments.md)에 있습니다.

## 댓글이 표시되는 방식

댓글은 Markdown으로 쓰이므로, 일반 텍스트로 보이는 댓글은 `**`, `- [ ]`, 코드 펜스로
가득합니다. 설명, 대화, 리뷰 스레드(대화 탭과 파일 탭)는 Markdown으로 그려집니다:
제목, 목록과 작업 목록, 표, 인용, 펜스가 가리키는 언어로 강조된 코드 블록, 링크와
이미지. 이슈 페이지도 텍스트를 같은 방식으로 그립니다. 텍스트 속 `#123`, `AB#123`,
`!123`, `@user`는 여전히 링크가 되며, 카드가 있던 곳에는 [카드](#123이나-ab123이-무엇에-관한-것인지)도 붙습니다.

![렌더링된 댓글: 표, 자리 표시자 뒤에 보류된 다른 사이트의 이미지, 강조된 코드 블록](../../screenshots/pr-rendered-comment.webp)

그리기의 출처:

| 호스트 | 렌더링하는 주체 |
|---|---|
| GitHub, GitHub Enterprise Server | GitHub 자체(`body_html`): 멘션과 참조는 웹사이트처럼 링크되고, 이미지는 GitHub의 이미지 프록시를 거치며, 비공개 첨부 파일은 서명된 주소를 가집니다 |
| GitLab, Forgejo, Azure DevOps, Bitbucket Data Center | 앱이 댓글의 Markdown으로 그립니다. 상대 링크는 저장소 안을 가리키며, GitLab에서는 GitLab과 마찬가지로 `/uploads/…`가 프로젝트 안을 가리킵니다 |

댓글은 다른 사람의 콘텐츠이므로 담을 수 있는 것이 좁고, 내 파일보다도 좁습니다:
명시된 태그 목록, `https:`, `http:`, `mailto:`만 쓰는 링크와 이미지, 스크립트·프레임·
폼·SVG·인라인 스타일 없음, 그리고 앱 안에서는 절대 열리지 않는 링크(브라우저로
갑니다). 작업 목록의 체크박스는 보이지만 클릭할 수 없습니다: 여기서 체크해도 호스트에서는
아무것도 바뀌지 않기 때문입니다.

**다른 사이트의 이미지는 클릭을 기다립니다.** 이미지를 불러오는 것은 그 뒤의 사이트가
내 IP 주소와 댓글을 읽은 시각과 함께 볼 수 있는 요청입니다 — 댓글을 달 수 있는 사람이면
누구나 거기에 추적 픽셀을 둘 수 있습니다. 그래서 저절로 불러오는 것은 호스트 자체의
이미지뿐입니다: github.com에서는 그 첨부 파일, `*.githubusercontent.com`(이미지 프록시
포함), 그 에셋. 다른 호스트에서는 호스트 자체의 주소. 그 밖의 이미지는 *example.net의
이미지 — 클릭하여 불러오기*를 보여 주고, 클릭하면 그 이미지 하나만 불러옵니다.
**설정 → 보안 → 댓글에서 다른 사이트의 이미지 불러오기**로 이를 끌 수 있습니다.
[보안](security.md#댓글의-이미지)을 참고하세요.

**미리 보기는 게시될 내용을 보여 줍니다.** 이 페이지와 이슈 페이지에서는 모든 댓글
입력란의 **미리 보기** 탭이 텍스트를 같은 방식으로 그립니다: 같은 프로필, 같은 줄바꿈,
같은 보류된 이미지 — 외부 이미지 링크를 붙여 넣어도 쓰는 동안에는 불러오지 않습니다.
새 풀 리퀘스트와 새 이슈 대화 상자는 앱의 평소 Markdown 미리 보기를 그대로 씁니다.

**너무 길거나 너무 복잡하면 텍스트로 보여 줍니다.** Markdown은 앱 창에서 렌더링되며,
어떤 텍스트는 크기에 비해 렌더링 비용이 훨씬 큽니다. **32,000자**를 넘는 댓글이나
렌더러를 멈추게 하도록 짜인 댓글(한 문단에 짝이 맞지 않는 `_`나 `*` 수천 개, 또는 한
줄에 32단계를 넘는 `>`나 목록 기호)은 *긴 댓글이라 일반 텍스트로 표시합니다.* 또는
*여기서 렌더링하기에는 너무 복잡해 일반 텍스트로 표시합니다.* 아래에 링크가 있는 일반
텍스트로 보입니다. 그래도 렌더링에 실패한 댓글은 스스로 같은 방식으로 돌아갑니다:
페이지의 나머지는 영향을 받지 않습니다.

하지 않는 일:

- **편집할 때는 쓴 그대로의 텍스트가 보입니다.** **편집**은 여전히 Markdown을 열고,
  저장한 편집은 페이지가 풀 리퀘스트를 다시 읽을 때까지 앱이 그립니다(GitHub에서는 그
  뒤로 GitHub가 그립니다).
- **GitHub의 비공개 첨부 파일은 만료됩니다.** GitHub는 비공개 이미지의 주소에 몇 분
  동안만 서명합니다. 페이지를 한동안 열어 둔 뒤 더 이상 불러오지 못하는 이미지는
  **새로 고침**으로 돌아옵니다.
- **앱이 직접 그리는 GitHub의 상대 경로 이미지**(페이지가 다시 읽기 전, 앱에서 보낸
  답글)는 github.com의 저장소 주소 아래에서 찾으므로, GitHub가 두는 곳과 다를 수
  있습니다.
- GitHub 댓글의 **동영상**은 플레이어가 아니라 파일 링크로 보입니다.
- 앱이 직접 그릴 때(다른 호스트) **GitHub 전용 확장**은 없습니다: 이모지 단축 코드,
  Mermaid 다이어그램, 알림 스타일이 없고, 수식은 텍스트로 남습니다.
- **코드는 펜스가 언어를 밝힐 때만 강조됩니다.** 언어를 추측하면 페이지의 모든 블록에
  모든 문법을 돌려야 합니다.
- 커밋 탭의 **커밋 메시지**는 일반 텍스트로 남습니다: git은 Markdown을 렌더링하지
  않고, 호스트도 마찬가지입니다.

## 내 댓글 편집과 삭제

이미 보낸 댓글의 오타나 더 이상 맞지 않는 의견을 고치려면 예전에는 브라우저로 가야
했습니다. 이제 내 댓글의 머리글 끝에 **편집**(연필)과 **삭제**(휴지통)가 있습니다:
대화 댓글, 리뷰 스레드 댓글과 답글에, 대화 탭과 파일 탭 모두에서. 이슈 페이지에도
GitHub와 Forgejo의 댓글에 대해 있습니다.

![편집됨으로 표시되고 머리글 끝에 편집과 삭제가 있는 내 댓글](../../screenshots/comment-editor.webp)

무엇이 “내 것”인지는 페이지가 직접 정합니다. 페이지는 불러올 때마다 이 저장소의
호출이 누구로 로그인하는지(활성 프로필이 아니라 연결된 프로필)를 호스트에 묻습니다.
대부분의 호스트는 작성자를 로그인 이름으로 부르며, 대소문자를 구분하지 않고
비교합니다. Azure DevOps는 작성자를 표시 이름으로 부르는데, 두 사람이 같은 이름을 쓸 수 있으므로
그곳에서는 이름을 비교하지 않습니다: 작성자 ID가 계정의 ID와 일치하거나, **또는**
작성자의 고유 이름(계정 이름, 보통 이메일 주소)이 대소문자를 구분하지 않고 계정의
것과 일치하면 그 댓글은 내 것입니다. 둘 다 한 사람에게만 속합니다. 두 번째는 연결이
알려 주는 것과 다른 작성자 ID를 다룹니다. 둘 다 비교할 수 없으면 어떤 댓글에도 동작이
표시되지 않습니다. 앱이 당신이 누구인지 알 수 없으면
(사용자 스코프가 없는 토큰, 또는 호스트가 응답하지 않음) 역시 어떤 댓글에도 표시되지
않으며, **새로 고침**이 다시 묻습니다. 그래도 결정은 호스트가 합니다: 댓글 변경을
허용하지 않는 계정은 거부되고, 메시지가 그렇다고 알려 줍니다.

- **편집**은 같은 Markdown 편집기에서, 작성한 그대로의 텍스트로 댓글을 그 자리에서
  엽니다. **저장**(또는 ⌘/Ctrl+Enter)으로 보내고, **취소**나 **Esc**로 닫으며, 무언가
  바꿨다면 먼저 묻습니다. 텍스트 앞뒤의 빈 줄만 지우고, 들여쓴 코드와 끝의 공백 두
  칸 줄바꿈은 입력한 그대로 둡니다. 새 텍스트는 바로 보이고, 페이지는 풀 리퀘스트를
  다시 읽습니다. 풀 리퀘스트 페이지에서 저장하지 않은 편집은 **‹ ›**로 넘어가거나 탭을 바꿔도 풀 리퀘스트에
  남고, 풀 리퀘스트를 닫을 때는 먼저 묻습니다. 이슈 페이지는 아무것도 보관하지 않으며, 탭을
  닫기 전에 묻는 것이 없습니다.
- **삭제**는 항상 먼저 묻고, 그 질문이 무슨 일이 일어나는지 알려 줍니다: 서버가 모든
  사람에게서 댓글을 지우며, 되돌릴 수 없습니다. 되돌릴 방법이 없으므로 실행 취소
  항목도 없습니다.

답글이 있는 **스레드의 첫 댓글**(리뷰 스레드, 또는 다른 사람이 답한 대화 댓글)을
지우는 것은 호스트마다 다르며, 확인 창이 어느 경우인지 알려 줍니다. 그중 둘은 호스트가
문서화하지 않았고, 그렇다고 말해 줍니다.

| 호스트 | 답글이 있는 스레드의 첫 댓글 |
|---|---|
| GitHub | 답글은 남아야 하지만, GitHub 문서에는 나와 있지 않습니다. 스레드는 답글 입력란을 유지합니다: 첫 댓글이 사라지면 답글은 GitHub의 GraphQL API를 통해 스레드 자체로 보내지며, 스레드는 아직 남아 있는 답글로 찾습니다. 그것이 실패하면(오래된 Enterprise Server, GraphQL이 거부하는 토큰, 이 계정이 답할 수 없다고 GitHub가 말하는 스레드) 스레드는 대신 **GitHub에서 답글 달기**를 제공합니다. GitHub에서 진행 중인 리뷰가 있으면 GitHub가 답글을 그 리뷰 안에 넣을 수 있습니다: 그때는 토스트가 그렇다고 알리고, 그 리뷰를 그곳에서 제출할 때까지 아무도 답글을 보지 못합니다 |
| GitLab | 그 노트만 사라지고, 스레드와 답글은 남습니다 |
| Azure DevOps | 삭제됨으로 표시되어 숨겨지고, 스레드와 답글은 유지되어야 하지만, Azure 문서에는 나와 있지 않습니다 |
| Bitbucket Data Center | 거부됨: Data Center는 답글이 있는 댓글을 지우지 않습니다. 먼저 답글을 지우거나, 대신 편집하세요 |

일부 호스트는 댓글을 **편집됨**으로 표시합니다. 텍스트만의 날짜를 가진 것은 Azure
DevOps뿐입니다. GitHub, Bitbucket Data Center, Forgejo에서는 앱이 댓글의 생성 시각과
마지막 업데이트 시각을 비교하므로, 그곳의 표시는 근사치입니다(댓글을 건드리는 다른
어떤 일로도 붙을 수 있습니다). GitLab의 날짜는 스레드를 해결할 때도 바뀌므로 쓰지
않습니다.

하지 않는 일:

- **Forgejo 리뷰 댓글**(줄에 단 댓글)은 API로 편집할 수 없고, 일부 버전만 삭제할 수
  있으므로 두 동작 모두 표시하지 않습니다: 웹사이트에서 바꾸세요. 대화 댓글은 다른
  곳과 같이 동작합니다.
- **그 사이 누군가 바꿨을 때.** Bitbucket Data Center는 댓글의 버전을 확인합니다:
  페이지를 불러온 뒤 바뀐 댓글의 편집이나 삭제는 거부되고, **새로 고침**이 현재 것을
  보여 줍니다. 다른 호스트는 마지막 쓰기를 받아들입니다.
- **찾을 수 없음**: 호스트가 댓글을 찾지 못하면, 메시지가 삭제되었거나 이 계정에서
  볼 수 없을 수 있다고 알리고, 페이지는 풀 리퀘스트를 다시 읽습니다. 사라진 댓글에
  열려 있던 편집은 버려집니다.
- **bitbucket.org** 풀 리퀘스트는 브라우저에서 열리므로, 앱이 그 호출을 할 수는 있지만
  댓글을 편집할 페이지는 아직 없습니다.
- 풀 리퀘스트의 **설명**과 리뷰 요약은 댓글이 아니며, 여기서 편집하지 않습니다.

## `#123`이나 `AB#123`이 무엇에 관한 것인지

*fixes AB#4821*라고 적힌 커밋이나 *#312 참고*라고 적힌 댓글은 번호만 알려 줄 뿐,
그것이 무엇이었는지는 알려 주지 않습니다. 알아내려면 열어 봐야 했습니다. 이제
**참조를 가리키면** — 또는 Tab으로 이동하면 — 호스트가 그것에 대해 알려 주는 내용을
담은 작은 카드가 열립니다.

- 종류를 나타내는 아이콘과, 적힌 그대로의 참조;
- **제목**;
- **상태**(열림, 닫힘, 병합됨 — Azure DevOps에서는 작업 항목 자체의 상태, 예를 들어
  *Active*나 *Resolved*);
- Azure DevOps에서는 **작업 항목 유형**(Bug, User Story, Task…).

![댓글 속 작업 항목 참조의 카드: 유형, 제목, 상태](../../screenshots/reference-card.webp)

카드는 풀 리퀘스트 페이지(설명, 댓글, 리뷰 스레드, **커밋** 탭의 커밋 전체 메시지),
이슈 페이지, 커밋 세부 정보 패널의 제목에 있습니다. Azure DevOps의 **커밋** 탭에서는
커밋 제목에 있는 각 작업 항목(`AB#123`, 또는 그곳에서는 같은 항목인 `#123`) 옆에
제목도 회색으로 표시됩니다. Azure DevOps에서 `!123`은 그 풀 리퀘스트로 연결되며,
카드는 없습니다.

| 참조 | 호스트 | 읽는 곳 |
|---|---|---|
| `AB#123`, 그리고 Azure 저장소의 `#123` | Azure DevOps | 작업 항목, 요청 한 번에 최대 200개 |
| `#123` | GitHub, GitHub Enterprise Server | 이슈와 풀 리퀘스트, GraphQL 요청 한 번에 최대 50개. GraphQL이 실패하면 하나에 REST 요청 한 번 |
| `#123` / `!123` | GitLab | 이슈 / 머지 리퀘스트, 종류마다 요청 한 번 |
| `#123` | Forgejo | 이슈(풀 리퀘스트 포함), 하나에 요청 한 번, 한 번에 두 개씩 |

`#123`은 독립된 단어일 때만 셉니다: `org/repo#123`(다른 저장소), `&#39;`,
`#123abc` 같은 색, 링크의 `#issuecomment-…`는 건드리지 않습니다.

카드가 열리기 전에는 아무것도 묻지 않습니다. 열리면 가리키는 참조와 페이지에서 그와
가장 가까운, 아직 모르는 참조들을 한 번의 호출로 묻기 때문에, 다음 카드는 대개 바로
나옵니다. 응답은 앱이 실행되는 동안 메모리에 5분간 보관되며 디스크에는 저장하지
않습니다. 그 뒤에도 계속 표시되고 다음에 가리킬 때 다시 읽습니다. 보관은 프로필별입니다:
호출은 저장소가 [연결된](profiles.md) 프로필로 이루어지며, 다른 프로필은 다른 항목을 볼
수 있습니다.

드는 비용:

- **GitHub**는 GraphQL API로 요청 한 번에 최대 **50**개를 읽습니다 — 가리킨 것과 가장
  가까운 주변. 속도 제한이 아닌 다른 이유로 GraphQL이 실패하면(오래된 Enterprise
  Server, 거부되는 토큰) 앱은 요청 한 번에 이슈 하나를 읽는 REST API로 바꿉니다: 그때는
  처음 **10**개만 GitHub가 앱에 요구하는 대로 하나씩 차례로 묻고, 나머지는 모르는 채로
  남으며, 나중에 가리킬 때 묻습니다.
- **Forgejo**는 여러 이슈를 요청 한 번으로 읽을 수 없으므로 카드마다 요청이 하나씩
  듭니다: 한 번 가리킬 때 최대 **10**개를 두 개씩 묻습니다.
- GitHub와 Forgejo에서는 *속도를 줄이라*는 첫 응답(429, 403, GraphQL 자체의 속도 제한
  오류, 2차 제한, 또는 제한의 마지막 요청을 써 버린 응답)이 나머지를 멈추고 — 그때
  GitHub는 REST로 바꾸지 않습니다 — 그 참조들은 5분 동안 다시 묻지 않습니다.
- **Azure DevOps**는 요청 한 번에 작업 항목을 최대 200개 읽고 GitLab은 종류마다 요청
  한 번이므로, 그곳에서는 페이지 전체를 한 번에 묻습니다.

하지 않는 일:

- **Bitbucket**에는 카드가 없습니다: 앱이 그곳에서 이슈를 읽지 않으며, 링크는 예전처럼
  브라우저를 엽니다.
- **찾을 수 없거나 접근 권한이 없음.** 삭제된 이슈, 이 계정이 볼 수 없는 프로젝트의
  작업 항목, *Work Items (Read)* 스코프가 없는 Azure 토큰은 모두 똑같이 보입니다: 카드가
  그렇다고 알리고, 링크는 그대로 동작합니다. 요청을 제한하는 호스트, 연결할 수 없는
  호스트, 이 프로필에 계정이 없는 호스트는 각자의 메시지를 받습니다.
- **Azure DevOps 밖의 `AB#123`** — Azure Boards에 연결된 GitHub 저장소 등 — 은
  링크가 되지 않으므로 카드도 없습니다: 앱이 어느 조직의 것인지 알 수 없기 때문입니다.
- 풀 리퀘스트가 언제 병합됐는지 보내지 않는 **오래된 GitHub Enterprise Server의 병합
  상태**: 닫힘으로 보입니다.
- **그래프**의 커밋 행에는 카드가 나오지 않습니다.

## 제한

- **열린 풀 리퀘스트는 사이드바의 목록입니다.** GitHub, GitLab, bitbucket.org는
  처음 30개를 읽습니다. 그보다 많은 저장소는 그것만 보여 주고, 열림 개수는
  **30+**로 표시됩니다. Azure DevOps, Bitbucket Data Center, Forgejo는 모두
  읽습니다.
- **병합됨과 닫힘에는 한도가 있고**, 호스트에 더 있으면 탭에 **+**가 붙습니다
  (호스트 웹사이트에는 모두 나옵니다).

  | 호스트 | 읽는 범위 |
  |---|---|
  | GitHub, bitbucket.org, Forgejo | 최근 업데이트된 100개, 병합됨과 닫힘 **합쳐서** |
  | GitLab | 각각 최근 업데이트된 100개 |
  | Bitbucket Data Center | 서버의 *newest* 순서로 각각 100개 — API가 그것이 생성 순인지 업데이트 순인지 밝히지 않습니다 |
  | Azure DevOps | **지난 1년** 동안 끝난 것 중 각각 100개. API가 순서를 밝히지 않으므로, 100개를 넘으면 어느 것이 들어갈지는 서버가 정합니다 |

  이들의 검사는 읽지 않습니다. 끝난 풀 리퀘스트의 CI는 아무것도 결정하지 않고,
  행마다 요청이 하나씩 들기 때문입니다. 그래서 **CI 실패**는 이 탭들에 적용되지
  않습니다(칩도 숨겨집니다).
- **계정 없음**: 호스트에 닿는 토큰이 없으면 병합됨과 닫힘은 빈 목록 대신 그렇다고
  알려 줍니다(GitHub는 공개 저장소라면 여전히 읽을 수 있습니다).
- **검사**: GitHub와 Bitbucket Data Center는 목록에 함께 담아 줍니다. GitLab,
  Azure DevOps, Forgejo에는 페이지를 열 때 head마다 한 번, 그래프의 CI 배지와 같은
  캐시를 통해 묻습니다. bitbucket.org에는 없습니다.
- **리뷰어**: GitHub, GitLab, Forgejo, Bitbucket Data Center, Azure DevOps는 아직
  요청받은 사람을 알려 줍니다(Azure: 아직 투표하지 않은 사람. 팀은 제외).
  bitbucket.org의 목록은 알려 주지 않으므로, 그곳에서는 리뷰어 필터가 비어
  있습니다.
- **설명 검색**은 호스트의 목록에 설명이 담긴 경우에 동작합니다. bitbucket.org는
  빠뜨릴 수 있고, 그러면 제목, 브랜치, 번호만 검색합니다.
- **bitbucket.org와 Azure DevOps의 “나”**는 표시 이름으로 대조합니다. 이들의
  목록이 작성자를 그렇게 부르기 때문입니다.
- **Azure DevOps의 업데이트**는 풀 리퀘스트가 열린(또는 닫힌) 시각입니다. 목록에
  마지막 활동 시각이 없기 때문입니다.
- 넘기기 순서는 앱이 실행되는 동안 기억됩니다. 재시작 후에는 목록에서 연 풀
  리퀘스트도 대신 열린 풀 리퀘스트를 넘깁니다.
- **파일을 읽다가 한 번 fetch할 수 있습니다.** 풀 리퀘스트의 커밋이 이 클론에 없으면, 페이지는
  열 때와 **새로 고침** 때 원격에서 id로 가져옵니다. 댓글, 리뷰, 병합 뒤에는 가져오지 않으며,
  한 세션에서 풀 리퀘스트 버전마다 최대 한 번입니다(실패한 시도는 새로 고침을 기다립니다).
  객체만 쓰며 브랜치도 `FETCH_HEAD`도 만들지 않으므로, 도구 모음의 “… 전에 가져옴”은 바뀌지
  않습니다. 20초가 지나거나 전송이 15초 동안 1 KB/s 아래로 기어가면 포기하고, 비밀번호를
  묻지 않습니다. git의 프롬프트는 꺼 두고 Git Credential Manager에는 로그인 창을 열지 말라고
  지시하므로, 그것이 필요한 원격은 API로 넘어갑니다. ssh 원격은 당신의 ssh 설정을 그대로
  씁니다. 객체가 빠진 얕은 클론이나 부분 클론은 호스팅 API로 넘어갑니다.
- **한도를 넘는** 파일은 숫자와 함께 diff 없이 나열됩니다: 클론에서 읽은 diff는 바뀐 줄
  20,000줄 또는 8 MB, Azure DevOps에서 읽은 버전은 4 MB입니다. 한 번의 읽기는 diff 약
  150,000줄 또는 48 MB를 보관하며, 그 뒤의 파일은 **아직 불러오지 않음**이 되어 열 때
  읽습니다.
- git이 바이너리라고 하는 **UTF-16 파일**은 풀 리퀘스트당 50개, 버전당 2 MB까지 텍스트로 다시
  읽습니다. 그 이상은 바이너리로 보입니다.
- **이름 변경**은 `git diff -M`과 같은 방식으로 찾으므로(기본 유사도 50%), 호스팅 자체의
  짝짓기와 조금 다를 수 있습니다.
- **API를 통한 Azure DevOps**는 처음 100개 파일을 합쳐서 1분 안에 읽습니다. 1분이 지났을 때
  남은 파일은 **아직 불러오지 않음**이 됩니다. 제한을 받은 응답은 서버의 Retry-After까지 모든
  읽기를 멈춥니다. 변경이 20,000개를 넘는 풀 리퀘스트는 거기까지 나열되며, 탭이 그렇다고
  알려 줍니다.
