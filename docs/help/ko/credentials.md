# 자격 증명 헬퍼

GitHuttBr는 서로 다른 세 종류의 비밀을 다루는데, 사람들은 당연하다는 듯이 이것들을
하나로 여겨요.

| | 보관하는 곳 |
|---|---|
| 호스트 API 토큰 — PR, 이슈, CI 검사 | GitHuttBr가 [OS 키체인](security.md)에 |
| `git@…` 전송 | 시스템 ssh 에이전트를 통한 당신의 [SSH 키](ssh-keys.md) |
| **`https://` 전송** | **git 자신의 자격 증명 헬퍼** |

세 번째 것은 잘못되기 전까지는 누구도 기능이라고 생각하지 않다가, 일이 터지면
git에서 가장 흔한 두 가지 불만을 만들어 내요. *왜 또 물어보지?* 그리고 *왜 내가
폐기한 토큰을 아직도 보내지?*

`⌘K` → **자격 증명 헬퍼**.

![설정된 헬퍼, 호스트별 규칙, 그리고 평문 파일 경고](../../screenshots/credentials.webp)

## 지금 보고 있는 것

설정된 모든 `credential.helper` 가, 그것이 온 범위별로 — `system`, `global`, 그
다음 이 저장소 순서로 — 보여요. **헬퍼는 쌓여요.** git은 차례로 각각에게 묻고,
저장소 수준의 헬퍼가 전역 헬퍼를 대체하지 않아요.

각 항목은 당신의 컴퓨터를 상대로 확인돼요.

| 표시 | 뜻 |
|------|-------|
| **준비됨** | 헬퍼 프로그램이 존재하고 실행될 거예요 |
| **설치되지 않음** | 설정은 돼 있지만 프로그램이 없어요 — 모든 요청이 결국 다시 직접 입력하는 것으로 떨어져요 |
| **비밀번호가 평문 파일에** | `store` 헬퍼예요 (아래 참고) |

**특정 호스트를 위한 규칙**에는 `credential.<url>.*` 섹션이 나열돼요. 이 규칙은
일치하는 URL에 대해 일반 설정보다 우선하고, "왜 이 호스트만 다르게 동작하지"에
대한 답인 경우가 많아요.

## 하나 고르기

| 헬퍼 | 비밀번호가 가는 곳 |
|--------|------------------------|
| `osxkeychain` | macOS 키체인 — 암호화되고 사용자별로 분리돼요 |
| `manager` | Git Credential Manager (Windows, 크로스 플랫폼) |
| `wincred` | Windows 자격 증명 관리자 |
| `libsecret` | 리눅스 시크릿 서비스 (GNOME Keyring, KWallet) |
| `cache` | 메모리에 15분간. 디스크에는 아무것도 남지 않아요 |
| `store` | **홈 디렉터리의 평문 파일. 암호화되지 않아요** |

GitHuttBr는 이 컴퓨터에 실제로 설치된 것만 제시하고, 당신의 OS에 맞는 것을
표시하며, 나머지는 흐리게 처리해요.

**범위가 중요해요.** *모든 저장소에* 는 전역 설정에 쓰는 것이고 거의 언제나
이쪽을 원하실 거예요. *이 저장소에만* 은 다른 곳으로 인증하는 별난 저장소를 위한
선택이에요.

## `store` 헬퍼와 `~/.git-credentials`

`store` 는 `https://user:password@host` 형태의 줄을 `~/.git-credentials` 에
평문으로, 어떤 종류의 암호화도 없이 써요. 당신 권한으로 실행되는 것이라면 무엇이든
읽을 수 있어요. 스크립트든, 어떤 의존성의 postinstall이든, 무엇이든요.

그 파일이 있으면 이 화면이 그 사실을 알리고 항목 수를 세어 줘요. 내용을 보여 주는
일은 절대 없어요 — 개수 자체가 요점이고, 보여 주려고 내용을 읽는 것은 똑같은
실수일 테니까요.

파일을 발견했는데 의도한 게 아니었다면, 여기서 제대로 된 헬퍼를 고르고, 그 파일을
지운 뒤, 한 번 다시 인증하세요.

## 저장된 자격 증명 잊기

토큰이 폐기되거나 교체되면 헬퍼는 계속 옛것을 건네주고, 모든 푸시는 아무것도
알려 주지 않는 401로 실패해요. **잊기**는 설정된 헬퍼에게 그 호스트에 대한 항목을
지우라고 요청해요 — `git credential reject`, 즉 git 자신이 문서화한 경로예요.

그 과정에서 읽는 것은 아무것도 없어요. GitHuttBr는 살아 있는 비밀번호를 표준 출력에
찍어 낼 명령인 `git credential fill` 을 결코 호출하지 않아요.

다음 푸시에서 한 번 묻고, 헬퍼가 새 답을 저장해요.

## 푸시가 쓰는 계정

푸시 URL은 각각 따로 확인합니다. 쓰기 범위는 토큰의 기능일 뿐입니다. 저장소 멤버십, 브랜치 규칙, 특정 파일을 바꿀 권한은 확인하지 않습니다. 공개 읽기는 자격 증명 없이도 성공할 수 있습니다.

![원격 로그인 확인](../../screenshots/remote-sign-in.webp)

푸시는 여러 방식으로 로그인할 수 있습니다: 프로필의 토큰, 프로필에 연결된 GitHub CLI
로그인, git 자체의 헬퍼, 원격 URL에 남은 비밀번호, SSH 키. 거부되었다면 먼저 그중
무엇이 쓰였는지 알아야 합니다. 사이드바에서 원격을 우클릭하고 **로그인 확인…**을
고르세요(명령 팔레트에서는 *원격 로그인 확인*). 확인은 푸시와 같은 방식으로 자격
증명을 정한 뒤, 그것에 대해 호스트에 묻습니다.

| 보여 주는 것 | 출처 |
|----------|--------------------|
| 출처와 그 뒤의 [프로필](profiles.md) | 푸시가 따르는 것과 같은 우선순위 — 저장소에 연결된 프로필, 없으면 활성 프로필, 없으면 git의 헬퍼 |
| 계정 | 호스트 자체의 답(`/user`)이며, 설정에 입력한 것이 아닙니다 |
| 범위 | GitHub의 `X-OAuth-Scopes` 헤더, GitLab이 자기 토큰에 대해 주는 설명 |
| 허용하는 것 | 쓰기 관련 토큰 범위(GitHub의 `repo`, GitLab의 `write_repository`)와, GitHub에서는 `.github/workflows`를 바꿀 수 있는지 |

호스트가 거부하는 자격 증명(만료되거나 폐기된 것), 더 이상 로그인되어 있지 않은 연결
계정, 원격 URL에 평문으로 저장된 비밀번호도 표시합니다.

**한계.** GitHub의 세분화된 토큰은 권한을 나열하지 않으므로, 푸시할 수 있는지는 푸시를
시도할 때까지 알 수 없음으로 나옵니다. Forgejo는 계정은 알려 주지만 토큰의 권한은
알려 주지 않습니다. Azure DevOps와 Bitbucket은 출처와 프로필만 보여 줍니다. SSH 원격은
확인하지 않지만, [SSH 키](ssh-keys.md)에 에이전트가 가진 것이 나옵니다. 확인은 git의
헬퍼에 조용히 묻습니다: 로그인 창이 필요한 헬퍼는 아무것도 없는 것으로 칩니다.

## 원격 URL에 저장된 비밀번호

오래된 클론이나 위키에서 붙여 넣은 URL은 주소 안에 자격 증명을 담고 있을 수 있습니다:
`https://user:token@git.example.test/team/app.git`. **URL의 비밀번호가 항상
우선합니다:** git은 그것을 보내고 어떤 헬퍼에도 묻지 않습니다 — 저장소
[프로필](profiles.md)의 토큰에도, GitHub CLI에도, git 자체의 저장소에도. 토큰이 유효한
동안은 괜찮고, GitHuttBr도 그대로 둡니다: **묻지 않고 URL에서 비밀번호를 제거하는 일은
절대 없습니다.** 토큰이 폐기되거나 만료되면 그 저장소 하나의 fetch, pull, push가 모두
*Invalid username or token*이나 *Authentication failed*로 실패하고, 같은 프로필의 다른
저장소는 동작합니다. 게다가 토큰은 저장소의 `.git/config`에 평문으로 남아 있습니다.

![원격 URL에서 저장된 토큰 제거하기](../../screenshots/remote-url-token.webp)

GitHuttBr는 각 원격의 fetch와 push URL을 읽고 세 곳에서 알려 줍니다.

| 위치 | 보이는 것 |
|-------|--------------|
| 실패한 fetch, pull, push | 원격의 URL에 저장된 비밀번호가 있다고 오류가 설명하며, **URL에서 제거…**를 보여 줍니다 |
| 사이드바 | 원격 행에 눈에 띄지 않는 열쇠 아이콘: 그 URL에는 프로필의 토큰보다 우선하는 비밀번호가 있습니다. 같은 동작이 우클릭 메뉴에도 있습니다 |
| **로그인 확인…** | 원격이 비밀번호를 출처로 보여 주며, 같은 버튼이 있습니다 |

이 동작은 먼저 묻습니다. 그 원격의 모든 URL — fetch URL과 비밀번호가 든 각 push URL
— 에서 비밀번호를 빼고, `.git/config` 외에는 아무것도 쓰지 않습니다. 그다음은 다른
무엇이 로그인할 수 있는지에 달려 있습니다.

| 제거한 뒤 | fetch와 push가 쓰는 것 |
|---------------|-------------------------|
| 저장소의 프로필에 그 호스트용 토큰이나 연결된 계정이 있음 | 그 토큰 — 확인 창은 더 말하지 않습니다 |
| 프로필 토큰은 없지만 git 자체의 헬퍼에 그 호스트의 로그인이 있음 | 헬퍼의 로그인 |
| 둘 다 없음 | 없음: 토큰을 추가할 때까지 fetch와 push는 실패합니다. 확인 창이 먼저 그렇다고 알리고, 설정 → 연동을 여는 **먼저 토큰 추가**를 제안합니다 |

실패한 작업에서 시작했다면 **다시 시도**를 제안합니다.

**실행 취소는 일부러 없습니다.** 되돌리면 비밀을 파일에 평문으로 다시 쓰게 되고, 그것이
바로 이 동작이 막으려는 일입니다. 예전 토큰이 아직 동작할 수 있다면 서버에서
폐기하세요: 저장소 폴더를 읽을 수 있는 것이라면 무엇이든 읽을 수 있었습니다.

**한계.**

- 사용자 이름도 사라집니다(`https://git.example.test/…`). `git remote set-url`을 직접
  실행할 때처럼, 확인 창이 그렇다고 알려 줍니다. URL에 사용자 이름이 필요한 서버 —
  프로필에 사용자 이름이 없는 Bitbucket Data Center 토큰 — 에서는 **원격 저장소
  편집…**으로 다시 넣어야 합니다.
- 사용자 이름만 있는 경우(`https://user@host/…`)는 표시하지 않습니다: git이 여전히
  헬퍼에 그 사용자의 비밀번호를 물으므로, 저장된 비밀은 없습니다.
- SSH URL은 건드리지 않습니다: `git@host:…`와 `ssh://git@host/…`는 ssh가 쓰는 로그인
  이름이지, 자격 증명이 아닙니다.
- 원격 헬퍼의 접두사(`persistent-https::https://…`, `gcrypt::…`)는 유지하고, 그 뒤의
  URL은 다른 URL처럼 읽어서 정리합니다.
- **모호한 URL은 제거를 제안하지 않습니다.** 호스트가 어디서 시작하는지 해석하는
  방식마다 다를 때 — 주소에서 `?`나 `#` 뒤에 오는 `@`, 또는 인코딩되지 않은 `/`가 든
  비밀번호 — 잘못된 `@`에서 자르면 원격이 다른 서버를 가리키게 됩니다. 그런 URL은
  가린 채로만 보여 주고, 열쇠 아이콘은 직접 고칠 수 있도록 **원격 저장소 편집…**을
  엽니다.
- 읽고 바꾸는 것은 `.git/config`뿐입니다. `url.<base>.insteadOf` 규칙으로 다시 쓰인
  URL이나 전역 설정에 정의된 원격은 살피지 않습니다 — 그리고 원격 이름을 바꿔도
  `insteadOf` 규칙이 더하는 비밀번호를 저장소 설정에 복사하는 일은 없습니다.
- 비밀번호는 메인 프로세스를 떠나지 않습니다: 원격 URL은 창, URL 복사 메뉴, 편집 대화
  상자에 비밀번호 없이 전달됩니다. 보여 준 URL 그대로 편집 대화 상자를 저장하면 아무것도
  바뀌지 않고 비밀번호도 남습니다. **호스트나 경로를 바꾸면 비밀번호는 사라집니다**.
  입력한 URL이 그대로 기록되기 때문입니다. 주소를 유지한 채 비밀번호를 제거하는 것은
  이 동작뿐입니다.

## 알아 둘 만한 한계

- **이건 git의 저장소지 GitHuttBr의 것이 아니에요.** 여기를 바꾸면 터미널의 동작도
  바뀌어요 — 그게 요점이지만, 바꾸기 전에 알아 둘 만한 사실이에요.
- **시스템 수준 헬퍼는 보이기만 하고 편집할 수 없어요.** 관리자만 쓸 수 있는
  설정 파일에 있으니까요.
- **GitHuttBr는 헬퍼가 무엇을 갖고 있는지 나열할 수 없어요.** 비밀을 넘겨주지 않고
  그걸 알려 주는 자격 증명 API는 없어서, 이 대화 상자는 설정을 보고하고 요청에
  따라 지우는 일만 해요.
- **GitHuttBr에 준 토큰은 별개예요.** 한쪽을 폐기해도 다른 쪽은 그대로예요. 키체인
  쪽은 [보안](security.md)을 보세요.
- **프로필의 토큰은 저장소 훅의 환경에 들어가지 않습니다.** 훅이 보는 것은 그 git
  명령이 도는 동안만 유효한, 비공개 엔드포인트용 코드뿐입니다 — git-lfs처럼 일부러
  묻는 훅에는 충분합니다. [git 실행 중 프로필의 토큰](security.md#git이-실행되는-동안의-프로필-토큰)을 참고하세요.
