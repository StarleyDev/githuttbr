# 拉取请求页面

一个繁忙的仓库同时开着二十个拉取请求。侧边栏会列出它们，但每个只占一行，能说明的
很少：哪个是谁的，哪些在等你，哪些变红了。想弄清楚，就得一个个打开、阅读、返回、
再打开下一个。**拉取请求页面**在一屏之内回答这些问题；打开一个拉取请求后，
**‹ ›** 让你无需返回就能跳到同一列表的下一个。

![搜索“pix”的拉取请求页面：匹配处高亮，你自己的标为“你”，一个 CI 失败，一个草稿](../../screenshots/pull-requests.webp)

## 打开方式

- 侧边栏 **拉取请求** 标题上的 **列表图标**（*查看全部拉取请求*）。
- 命令面板（⌘K）中的 *拉取请求…*，或 **工具 → 拉取请求…**。

与 wiki 和 [CI 运行](ci-runs.md) 一样，这个页面挂在仓库的标签页上。

## 标签

| 标签 | 包含的内容 |
|---|---|
| **打开** | 所有打开的拉取请求，包括草稿 |
| **草稿** | 只含标记为草稿的打开拉取请求 |
| **已合并** | 已合并的拉取请求，首次打开该标签时读取 |
| **已关闭** | 未合并就关闭的（被拒、被放弃），与已合并一起读取 |

打开和草稿旁边的数量来自侧边栏已有的列表。已合并和已关闭只在你打开其中一个时才请求，
每个会话一次；**刷新** 会重新请求。

## 筛选

| 筛选 | 保留 |
|---|---|
| **搜索** | 标题、描述、分支或编号包含所输入的每个词的拉取请求。`#482` 或 `482` 可找到该编号；匹配处在标题中高亮 |
| **作者** | 某一位作者——每位都附有其在本标签中的数量。**我** 排在最前 |
| **评审者** | 某一位被请求的评审者，或 **请求我评审** |
| **目标分支** | 合入该分支的拉取请求 |
| **我的** | *作者：我* 的快捷方式 |
| **等待我评审** | *评审者：请求我评审* 的快捷方式 |
| **CI 失败** | head 检查失败的拉取请求 |

筛选下方的一行说明本标签中显示了多少个拉取请求、哪些筛选已开启，并提供 **清除筛选**
一次全部去掉。

筛选按仓库保留，**只在应用运行期间有效**——离开页面再回来，它们仍是你离开时的样子。
重启后不保留是有意为之：一个“我的、CI 失败”的筛选一周后悄悄回来，会把你并没要求隐藏的
拉取请求藏起来。

### “我”是谁

“我”是这个仓库的调用在托管平台上登录所用的账户——仓库 [绑定](profiles.md) 的配置档，
否则是当前活动的配置档——并由托管平台本身给出。当令牌说不出自己属于谁（没有用户
权限范围），或者没有令牌时，不会提供 **我**、**我的** 和 **等待我评审**。

## 列表

| 列 | 显示内容 |
|---|---|
| **#** | 编号，并带有打开、草稿、已合并或已关闭的图标 |
| **标题** | 标题、*草稿* 徽章，以及仍被请求评审的人——是你时用强调色 |
| **作者** | 托管平台提供头像时显示头像，否则显示首字母；你自己的标为 **你** |
| **分支** | 源 → 目标 |
| **检查** | head 检查的汇总——`6/6`、`1 失败`、`2 运行中`；悬停查看计数 |
| **更新于** | 距上次变化多久；悬停查看日期 |

各行按最近活动排序。点击会打开拉取请求自己的页面（[托管与拉取请求](hosting.md)）。
在没有该页面的托管平台上，点击该行会在浏览器中打开拉取请求。

在 [fork 的检出](hosting.md#你在-fork-上游仓库中的拉取请求) 中，你在上游仓库的拉取请求也会列出，标为
*在 owner/repo*。

## 在拉取请求中浏览列表

![从筛选后的列表打开的拉取请求：‹ 1 / 4 › 以及它来自的筛选](../../screenshots/pull-request-nav.webp)

从该页面打开的拉取请求会在标题上方显示一条导航栏：

- **← 拉取请求** 返回列表，筛选保持你离开时的样子。
- **‹ k / n ›** 移到你打开它时所在列表的上一个或下一个拉取请求——即筛选后的列表，按其
  顺序，保持你点击时的状态。提示会写明每个箭头通往哪个拉取请求。
- **Alt+← / Alt+→** 用键盘做同样的事。可在 **设置 → 快捷键** 中重新绑定。光标在文本框
  中时（Option+← 在那里按词移动）以及终端拥有焦点时，它们不生效。

移动会就地替换页面，因此浏览十个拉取请求不会在标签页上留下十个图标；从列表打开另一行
也会替换它。

从 **其他任何地方**——侧边栏、通知——打开的拉取请求，会按页面的默认顺序（打开，无筛选）
浏览仓库中打开的拉取请求。若它也不在那个列表中，比如堆栈中已合并的一层，则只显示返回
列表的入口。

## 前往拉取请求的分支

要处理一个拉取请求，你需要检出它的分支——而在有成千上万个分支的仓库里，按名称在分支列表
中找到它才是慢的那一步。在拉取请求的页面上，**分支** 字段替你完成这件事：

- **分支名是一个链接。** 点击会检出该分支，并带你到仓库图中该分支的顶端。拉取请求的页面
  仍在标签页上保持打开。
- **只存在于服务器上的分支** 会先被获取——只获取这一个分支，而不是整个远程——然后检出为
  跟踪它的本地分支。你本地已有的分支会按原样切换过去——不会更新，所以想要拉取请求的最新
  提交时，请拉取。
- **你当前所在的分支** 改为标记为 *当前*。不会检出任何东西。
- 每个名称旁的 **复制按钮** 会把它放到剪贴板。
- **撤销**（⌘Z）会回到你原来所在的分支，并删除这次检出创建的本地分支——除非你之后
  在它上面提交过，那样它会保持不动。

页眉中也有同样的两个操作按钮：**前往源分支** 和 **前往目标分支**。它们对你当前所在的
分支同样有效——只是把你带到仓库。 开启 [图标颜色](themes.md#图标颜色) 后，页眉的每个按钮都有自己的颜色：刷新为蓝色，AI 评审为紫色，预览为青色，源分支为绿色，目标分支为橙色（在浏览器中打开仍为灰色）。

点击之前不会查询任何东西：打开拉取请求不会读取或获取任何分支。

它不做的事：

- **fork 的源分支** 位于另一个仓库，因此没有链接（复制按钮保留）。紧接在其下方提供的
  **在本地预览拉取请求…** 是在这里运行它的方式。目标分支仍是链接。
- **没有匹配的远程。** 分支会在 URL 为该拉取请求所在仓库的远程上查找。没有任何已配置的
  远程指向那里时，链接不做任何事，提示会说明原因。
- **已删除的分支。** 已合并的拉取请求常常把分支一起删掉了；此时获取会提示该分支已不在
  远程上，你仍停留在拉取请求页面。
- **本地更改。** 检出不具破坏性，因此没有确认——当你未提交的更改会被覆盖时，git 会拒绝
  检出。错误会列出是哪些文件；提交或贮藏它们后再点一次。
- **本窗口。** 检出发生在这个仓库的工作区中。当该分支已在另一个 [工作树](worktrees.md)
  中检出时，会改为打开那个工作树的标签页。

## 提交

侧边栏会说一个拉取请求有多少个提交，却从不说是哪些。逐个提交地评审——大多数拉取请求
本就该这样读——还得去浏览器。位于对话和更新之间的 **提交** 标签会列出它们：

- **最早的在前**，按它们被应用的顺序，归在各自编写的日期之下。一个经变基后不按日期顺序
  出现的提交，会另起一个日期，而不是被挪动。
- 每行有作者头像（托管平台提供时）、主题、作者、多久以前以及短 SHA。托管平台说明时，
  有两个父提交的提交会带 **合并** 徽章。
- 不止有主题的提交旁边的 **▸** 会显示其说明的其余部分。
- **复制** 把完整 SHA 放到剪贴板；**在浏览器中打开** 在托管平台上打开该提交——托管平台
  有对应页面时在拉取请求内打开（GitHub、GitLab、Bitbucket Data Center），否则在仓库的
  提交页面打开。

![提交标签：拉取请求的提交按日期分组，其中一个展开了完整说明](../../screenshots/pr-commits.webp)

**点击某一行**——或用 Tab 移到该行并按 Enter——会像在图中点击一样，在应用中打开该提交：
仓库视图、选中该提交、打开其详情。这在本克隆 **拥有** 该提交时有效。没有时，该行会如实
说明，而不是悄无声息地失败，并提供：

- **拉取 PR 分支以查看**——与 [前往分支](#前往拉取请求的分支) 相同的单分支获取，但不检出。若该提交
  随之而来，就会打开；若没有（之后被强制推送改写），提示消息会说明。
- **获取拉取请求的提交**——针对来自 **fork** 的拉取请求。它的分支位于另一个仓库，但大多数
  托管平台会在目标仓库中用一个专门的 ref 镜像拉取请求的 head——`refs/pull/N/head`（GitHub、
  GitHub Enterprise Server、Forgejo）、`refs/merge-requests/N/head`（GitLab）、
  `refs/pull-requests/N/from`（Bitbucket Data Center）。应用只获取这一个 ref，不带标签，
  放进应用自己的 ref `refs/githuttbr/pr/<remote>/N`，然后该提交会像其他提交一样打开：图中
  会把这个 head 画成一条没有标签的线。再次获取会把这个 ref 移到当时的 head。如果此后的强制
  推送把该提交排除在外，提示消息会说明。
- **在浏览器中打开**，用于无法获取的情况。

列表在你第一次打开该标签时读取，而不是随页面一起读取，并在每次 **刷新** 时重新读取。在它
到达之前，标签上的数量是托管平台为该拉取请求给出的数字。已合并和已关闭的拉取请求也以同样
方式列出提交。

它不做的事：

- **最多 250 个提交。** GitHub 本身为一个拉取请求最多只列出 250 个；应用在所有托管平台上
  都停在同一数字，并在还有更多时提示 *托管平台上还有更多*，附上指向托管平台上该拉取请求的
  链接。是哪 250 个，取决于托管平台列出它们的顺序——应用保留最先列出的，列表上方的那行会
  说明是哪些：

  | 托管平台 | 更长的拉取请求显示 |
  |---|---|
  | GitHub | **前** 250 个（GitHub 自身的上限） |
  | GitLab、Azure DevOps、Bitbucket Data Center、bitbucket.org | **最新的 250 个** |
  | Forgejo | 服务器先列出的那一端；其顺序没有文档说明 |
- **托管平台不镜像时的 fork head。** Azure DevOps 只发布合并结果，从不发布拉取请求自己的
  head，bitbucket.org 两者都不发布：在那里该行只提供浏览器。在事后发现并不镜像的其他托管
  平台上，获取会说明这一点。如果你需要的是 Azure 的合并结果，**在本地预览拉取请求…** 可以把
  它取进来。
- **获取的 head 会保留。** `refs/githuttbr/pr/…` 不是分支：没有可检出或推送的东西，带 prune
  的获取不会动它，git 会保留它的提交。也没有任何操作会删除它——关闭页面不会，
  [分支清理](branch-cleanup.md) 也不会。要去掉它们，请手动删除这些 ref：
  `git for-each-ref refs/githuttbr/pr` 会列出它们，`git update-ref -d <ref>` 删除一个。
- **名称中带有 `/` 的远程** 无法成为该 ref 名称中的一段，因此在那里获取会被拒绝。
- **已删除的分支。** 已合并的拉取请求常常把分支一起删掉了：获取会说明这一点。一旦源分支
  不存在，bitbucket.org 就不再列出任何提交。
- **压缩合并。** 压缩合并的拉取请求的提交从未进入目标分支，所以在其分支删除后，它们只存在
  于托管平台上。
- **作者** 按其提交中的名称显示。GitLab、Azure DevOps 和 Bitbucket Data Center 在没有
  登录的情况下不提供头像，而图片请求无法携带登录，所以这些行显示首字母。
- **Azure DevOps 上的长说明** 可能被截断：Azure 的列表会截短提交说明，应用显示它发来的
  内容。
- **bitbucket.org** 的拉取请求在浏览器中打开——应用还没有它们的页面——所以尽管应用能读取
  列表，在那里也到不了这个标签。

## 更新

你周一评审过的拉取请求，到周四已经有了变化。提交标签显示它现在在哪里，却不显示这期间发生了
什么：哪些提交随哪次推送而来，有没有人强制推送、改写了你已经读过的内容，以及代码 *与你看到的
版本相比* 是什么样子。位于提交和文件之间的 **更新** 标签回答这些问题——就像 Azure DevOps 自己
的 Updates 标签一样。

它列出对拉取请求的每次推送，**最新的在前**：

- **更新 1 — 创建** 是创建拉取请求时的那次推送；之后的每次推送依次编号。
- 每一项都显示 **何时**、**谁推送的**（托管平台提供时），以及 **新增的提交**——短 SHA、主题、
  作者。托管平台报告了某次推送从分支上移除的提交时，它们会以删除线列在 **移除的提交** 下。
- 强制推送或变基会被标为 **历史已改写**：你读过的提交可能已经没了，列出的提交可能是旧工作的
  新副本。在 Azure DevOps 上，把拉取请求移到另一个目标分支的推送会被标为 **目标已更改**。

![更新标签：按最新在前列出的推送，一次标为“历史已改写”的强制推送，一项标为新](../../screenshots/pr-updates.webp)

### 某次更新改了什么

**查看此次更新的更改** 会只针对那次推送打开文件标签：从上一次更新的 head 到这一次的差异——
对于更新 1，则在托管平台给出该起点时（Azure DevOps、GitLab），从创建时所针对的目标分支算起。
文件树和查看器都一样，外加一条横幅——*正在显示更新 3的更改（对比更新 2）*——以及回到整个拉取
请求的 **显示全部更改**。

![显示某次更新更改的文件标签，文件树上方有横幅](../../screenshots/pr-update-diff.webp)

只要可能，差异总是 **在本克隆中** 生成：两个 head 之间的 `git diff`，精确，且不询问托管平台。
缺少其中某个 head 时，应用会先从拉取请求的远程 **按提交 ID** 获取两者——不写入任何分支、标签或
ref；被强制推送取代的 head 已不在任何分支上，但大多数托管平台仍按 ID 提供它——然后在这里比较。
只有这次获取失败时才询问托管平台：

| 托管平台 | 托管平台的比较 |
|---|---|
| Azure DevOps | 带 `$compareTo` 的迭代更改——两次推送之间 |
| GitLab | 仓库比较，直接从一个 head 到另一个 |
| Bitbucket Data Center | 仓库比较——**从两个 head 的共同基点** 开始 |
| GitHub | Compare API（`base...head`）——**从两个 head 的共同基点** 开始 |
| Forgejo / Gitea | 无：其 API 没有两个提交之间的差异 |

从共同基点比较时，改写的差异并不是那次推送所做的事：它删除的内容不会显示，而目标分支此后收到
的更改可能看起来像是拉取请求的。历史被改写的更新以这种方式比较时，横幅会说明——*从共同基点
比较：此次推送删除的内容不会显示。* 什么都不行时，横幅会说明，并提出获取分支（或者，对于来自
fork 的，获取拉取请求的 head）后在这里比较。

行评论属于整个拉取请求的差异，所以只显示某一次更新时，行上没有 **+**；横幅会说明。把文件勾选为
已查看照常有效——它标记的是拉取请求中的文件。

### 自你上次查看以来的新内容

自你上次打开该标签以来推送的更新带有 **新** 徽章，标签本身也会显示数量：*更新 5 · 2 个新*。
打开标签会把它们标为已查看（你停留在标签上时徽章仍在，好让你看出哪些是新的）；标签打开时
**刷新** 又带来更多，**标记为已查看** 会清除它们。只打开拉取请求页面不会标记任何东西。第一次
打开某个拉取请求的更新标签时，没有任何内容是新的——没有更早的查看可供比较。

更新会随页面一起读取（为了那个数量），并在 **刷新** 时重新读取——而不是在你每次发布评论或评审
之后。

已查看的状态只保存在这台电脑上，按仓库和拉取请求分别保存，绝不发送给托管平台。

### 各托管平台

| 托管平台 | 更新来自哪里 | 推送者 | 移除的提交 | 能否检测改写 |
|---|---|---|---|---|
| Azure DevOps | 拉取请求的 **迭代**——Azure 对每次推送的自有记录 | 有 | 无（不报告） | 能：`forcePush` / `rebase` |
| GitLab | 合并请求的 **差异版本**；每个版本的提交由其 head 推算 | 无（版本不提供人名） | 有 | 能：之前的 head 已无法到达 |
| Bitbucket Data Center | 拉取请求的活动：**OPENED** 以及每个移动了源分支的 **RESCOPED** | 有 | 有，并带托管平台的总数 | 能：移除了提交的 rescope |
| GitHub | 从时间线的提交和强制推送 **推断**——见下文 | 仅强制推送 | 无 | 能：强制推送事件 |
| Forgejo / Gitea | 时间线中的 **push** 条目，第一条与拉取请求本身一起写入 | 有 | 无 | 能：强制推送条目 |
| bitbucket.org | 不可用 | — | — | — |

**GitHub 不记录普通推送**——只记录强制推送——所以更新是 **根据提交时间推断** 的。一次更新是两次
强制推送之间一串依次叠加的提交；不是叠加在前一个提交之上的提交，或比前一个晚了十分钟以上的
提交，会开始下一次更新。在拉取请求创建之后提交的内容不可能包含在创建时。因此，一次推送里相隔
一小时的提交会显示为 **拆成** 两次，而相隔几分钟的两次推送会显示为 **一次**；标签会说明分组只
是近似的。变基产生的新提交，时间线可能列在其强制推送之前，它们算作那次强制推送的。强制推送
前后的 head 是精确的，所以它的 **查看更改** 也是精确的。

### 限制

- **上限。** 列出最近的 100 次更新。GitHub 的时间线从最新一端读取，最多 500 项；Bitbucket Data
  Center 的活动（同样最新在前）最多 1,000 项；GitLab 的版本和提交各最多 300 项；Forgejo 的时间线
  最多 500 条，更长时取最新的。当上限截掉了 **创建时的那次** 时，编号就不再是托管平台的编号：标签
  会说明，并从最新一次往回数（*最新更新*、*更新（最新之前第 2 个）*）。
- **Azure DevOps** 不报告移除的提交；改为标记强制推送或变基。提交列表被 Azure 截短的迭代会单独
  读取（最多 500 个提交），仍不完整时更新会说明。
- **GitLab** 不提供推送者。head 已被改写掉的版本会单独读取以找出其提交——针对这类版本中最新的
  十个——每个会话一次：版本永远不会改变。
- **Forgejo 和 Gitea** 不列出强制推送的提交——只有它的两个 head，**查看更改** 比较的就是它们——
  而强制推送之后没有任何东西说明创建时包含什么，所以除非服务器记录了创建时那次推送本身，否则它
  保持为空。其 API 没有两个提交之间的差异，所以那种比较需要两个提交都在本克隆中。没有时间线
  API 的服务器会把所有提交显示在一次更新里。
- **按 ID 获取** 需要能按 ID 提供提交的托管平台。GitHub 对它仍保存的任何提交都可以；其他托管平台
  或普通的 git 服务器，可能会拒绝没有任何分支指向的提交——这时改用托管平台的比较。获取的提交在
  本克隆中没有 ref，git 会在适当时候回收它们。
- **Bitbucket Data Center 的比较** 读取服务器的结构化差异，并把它绘制为统一格式；非常大的文件
  可能被截断。
- 被改写的 head 可能已永久 **从托管平台消失**（Azure 和 GitLab 会保留；其他平台可能回收）。这时
  双方都无法比较，横幅会说明。
- **bitbucket.org** 的拉取请求在浏览器中打开，没有更新标签。

## 阅读文件

一个有两百个文件的拉取请求，按两百条完整路径来读很费劲。**文件** 标签的列表有与提交面板
相同的 **路径 / 树** 切换，而且这一选择在整个应用中通用。在 **树** 视图中，文件位于各自的
文件夹下（像 `src/main/ipc` 这样的一串是一行），每个文件夹显示其合计的 **+/−** 以及其中
已查看的文件数（*3/5*）。文件夹的复选框会把其中每个文件标为已查看，或全部取消；勾选只保存
在这台电脑上，绝不发送到托管平台。勾选会记住文件差异的版本：当一次推送改动了已查看的文件时，
它会重新显示为未查看，并带一个黄点（*查看后已更改*）。没有差异的文件（二进制、过大）只按
其状态和行数比较。 有评审讨论的文件旁会显示一个气泡计数（文件夹会把其中的计数相加），这样在长列表中有评论的文件会很醒目；过时的讨论也计算在内。点击文件夹，或在其上按 ←/→，即可折叠；↑/↓（或 j/k）逐个浏览屏幕上的
文件并打开各自的差异。折叠的文件夹按拉取请求记住，直到应用退出；在其中打开一个文件时，
通往它的路径会展开。树按名称排序，而不是按托管平台列出文件的顺序。

![树视图下的文件标签：文件夹带有合计改动和已查看数量，其中一个已折叠](../../screenshots/pr-files-tree.webp)

**图片。** 拉取请求添加、删除或修改的图片（png、jpg、gif、webp、bmp、ico、avif、svg）没有
可读的文本差异，所以标签改为显示图片——与提交中的视图相同：新图、旧图，或者前后并排以及
滑块对比。重命名的图片把基准上的旧路径与 head 上的新路径相比；在单次更新的差异中，比较该次
更新的两个 head。字节在提交位于本克隆时从这里读取（免费且快速），否则用仓库的配置文件从托管
平台读取。限制：超过 32 MB 的图片不预览；行评论不适用于图片（SVG 会在下方保留其文本差异和
评论）；存放在 **Git LFS** 中的图片从托管平台读取，因为克隆中只有它的指针——GitLab、Azure
DevOps 和 Forgejo 会解析它，而 GitHub 的 API 只给出指针，所以在那里标签会引导你去托管平台；
托管平台未给出合并基准时（此时退而使用目标分支的末端），会有一条提示说明“之前”可能包含目标
分支上后来的改动；而当克隆和托管平台都无法提供字节时，标签会如实说明，并提议获取拉取请求的
分支，或在托管平台上打开它。

![拉取请求修改的一张图片，前后并排](../../screenshots/pr-image-diff.webp)

**路径与编辑器。** 差异上方的栏有一个复制文件路径的按钮和一个 **⋯** 菜单；在列表中右键点击
文件或文件夹会打开同一个菜单。它可以复制路径、重命名文件的旧路径或文件夹路径；也可以在你的
[编辑器](editor.md)（或其他应用）中打开文件，或在文件管理器中显示它。后两项作用于**你的工作
副本**，而不是拉取请求中的版本：只有工作副本中存在的文件才可用（拉取请求删除的文件，或你的
分支没有的文件，会说明原因）；当检出的分支不是拉取请求的分支时，菜单会说明你将打开哪个分支
的文件。

**回来时。** 离开拉取请求去看仓库、另一个标签页或下一个拉取请求，回来时一切如你离开时一样：
同一个标签、同一个打开的文件、同样的滚动位置，以及所有未发送的文本——评论、回复、行评论、
编辑。这会一直保留，直到你关闭该拉取请求或退出应用；只保存在内存中，针对最近 50 个拉取请求
（超出时最早的位置会被放弃，其中的文本会转到你接下来打开的拉取请求页面）。关闭带有未发送
文本的拉取请求时会先询问。如果刷新发现草稿的位置已不存在——它回复的讨论、它编辑的评论、它
所在的文件——文本不会丢失：它会在页面顶部等你复制或丢弃。

### 差异从哪里来

评审的质量取决于它所读的差异。托管平台的 API 并不是好的来源：Azure DevOps 根本不发送差异，
只发送文件列表，每个文件都要下载两次再比较；GitHub 在 3000 个文件处截止，并省略大文件的补丁；
GitLab 把大差异标为*过大*，什么也不发送。所以在任何托管平台上，**文件**标签都**先读取这个
克隆**：

1. 它向托管平台询问拉取请求的两个提交——起点和 head。Azure DevOps、GitLab 和 Forgejo 给出
   合并基准；Bitbucket Data Center 给出其行评论所锚定的差异的基准；GitHub 只给出目标分支，
   此时它与 head 的合并基准在这里计算（没有提交时则借助 GitHub 的比较）。图片预览使用同样的
   两个提交。
2. 两者都在本地时，它们之间的 `git diff` 给出每一个文件，数量不设上限。这正是托管平台自己
   页面所比较的两个提交，所以这里的行号就是那里的行号，行评论会落在你放的位置。
3. 不在本地时，会**按 id** 从拉取请求的远程获取——只有对象，不创建也不移动任何分支——只在
   打开页面时获取一次（点击“刷新”时再获取），期间列表上方显示*正在获取拉取请求的提交…*。
   不按 id 提供提交的服务器（部分 Azure DevOps 和普通 git 服务器）会被悄悄跳过。
4. 到这时才使用托管平台的 API；对于它不提供差异的文件，会说明原因，而不是假装为空（见下文）。

稍后读取的文件——在*尚未加载*时打开的，或在**重试**之后的——会像其他文件一样加入列表：同样
的查看器，也可以在上面发表行评论。

在 Azure DevOps 上，API 路径在打开标签时读取前一百个文件，每次三个，总共在一分钟之内；其余的
在你逐个打开时读取。被限流的请求会让所有读取暂停到服务器要求的等待时间；仍然失败的会如实说明
并给出原因。文件是否为文本由其字节判断，而不是 Azure 的 *binary* 标志——Azure 也会把它加到
UTF-16 文件和部分非 ASCII 文本上。当托管平台列出的文件少于拉取请求实际包含的数量时（GitHub
在 3000 处截止），列表上方会有一行说明。

### 文件不显示差异时

| 它显示 | 原因 | 你可以做什么 |
|---|---|---|
| **二进制** | 其字节不是文本：图片、压缩包。UTF-16 和旧的单字节文本会被识别为文本。 | 在托管平台上打开。 |
| **过大，无法显示** | 超过 20,000 行改动或 8 MB 差异，或某个版本超过 4 MB。只要克隆读取过它，其 **+/−** 仍会计数。 | 在托管平台上打开。 |
| **尚未加载** | 超出单次读取保留的范围（约 150,000 行差异），或经由 Azure DevOps 的 API 时超出前一百个文件或一分钟。 | 打开时会加载；若没有，点击**加载差异**。 |
| **无法加载** | 读取失败——原因显示在下方。 | **重试**。 |
| **托管平台省略了它** | 托管平台的 API 没有发送差异，而本克隆中没有拉取请求的提交。 | **获取拉取请求以在本地查看**——按 id 获取提交，或从派生仓库获取拉取请求的 head——之后差异在这里生成。 |
| **只改了名称或模式** | 重命名或权限变更：内容相同。 | 内容上没有需要评审的。 |
| **编码改变了** | 同样的文本换了一种保存方式：增加或去掉了字节顺序标记，UTF-16 转成了 UTF-8。 | 确认这一改动是有意的——有些工具在意这一点。 |

在列表中，未读到差异的文件——尚未加载、无法加载、托管平台省略——显示 **—** 而不是
**+0 −0**，后者会被理解为“没有任何改动”。二进制文件和单纯的重命名显示其真实的 **+0 −0**；
而当托管平台本身计算了行数时（GitHub 即使对省略的补丁也会计算），会显示这些数字。

## 评论某一行

以前在这里可以回复评审讨论，却不能发起新的讨论，所以真正的评审仍然要去浏览器。在拉取请求的
**文件** 标签中，差异的任何一行都可以单独评论：

- **悬停在某一行上**，按下其行号上方出现的 **+**，或者 **直接点击该行**（结束文本选择的点击、
  或选中一个词的双击不算——那是在阅读）。右键菜单——或键盘上的上下文菜单键——也有
  *评论第 N 行*。
- **该行下方** 会打开一个输入框。写好后点 **评论**——或按 ⌘/Ctrl+Enter。**取消** 会关闭它；
  **Esc** 也会，若已输入内容会先询问。无论哪种方式，焦点都会回到那一行。
- 成功后，新讨论会出现在 **其所在行的下方**，以及对话标签的评审讨论中，其他人都会看到。

![在一条改动行下方撰写评论，以及另一行下方较早的讨论](../../screenshots/pr-line-comment.webp)

评论落在哪一侧取决于该行：

| 行 | 锚定到 |
|---|---|
| **新增**（绿色） | 文件的新版本，使用新行号 |
| **删除**（红色） | 旧版本，使用旧行号 |
| **未改动** | 新版本（按 GitLab 的要求，会同时发送两个行号） |

已有的讨论同样画在各自的行下方；在托管平台允许应用在讨论内回复的地方，还带有回复框（Forgejo
不允许）。只有当托管平台表示某个讨论仍属于当前显示的差异时，它才会画在某一行上；其余的留在
对话标签中，而不是放到猜测的行上：

| 托管平台 | 在最近一次推送之前写的讨论 |
|---|---|
| GitHub | 其行已改动则视为过时：仅在对话中 |
| GitLab | 针对较早的 head 写的：仅在对话中 |
| Azure DevOps | 由 Azure 跟踪到其行现在所在的位置 |
| Bitbucket Data Center | 其行已不存在则成为孤立讨论：仅在对话中 |
| Forgejo | Forgejo 不会说明评论已过时，因此按记录的行号显示——推送之后那一行可能已是别的代码 |

在所显示的 hunk 之外的行上的评论，在所有托管平台上都只出现在对话标签中。

已输入但未发送的评论会像主评论框中的文本一样留在拉取请求里：**‹ ›**、Alt+方向键或切换到别的
标签页都会让它保留在原处，回来时它又回到原来的行上（见上文*回来时*）。浏览其他文件不会丢失
它；要在另一行开始评论，先发送或取消第一条。

它不做的事：

- **一次一行，立即发布。** 没有行范围，没有可以先攒评论、稍后提交的待定评审，也没有建议修改。
  每条评论在你发送的那一刻作为独立讨论发布（在 Forgejo 上，因为它没有单条评论的接口，会作为
  只含这一条评论的评审发布）。
- **你正在看的差异。** 文件标签会记住其差异是在哪个提交（在 Azure DevOps 上是哪次迭代）读取的，
  评论会针对它发送。若此后拉取请求已有变化——一次推送、新的合并基准——评论不会发到现在拥有
  该行号的行上：它会以 *加载此差异后拉取请求已发生变化* 被拒绝，**刷新** 会显示新的差异。在
  GitHub 上则改为针对你读取的那个提交发布评论，若该行已改动，GitHub 会将其标为过时。托管平台
  仍不接受的行，会以超出差异范围为由被拒绝。
- **被拒绝。** 没有评论权限时（只读令牌、仓库不允许评论的账户），托管平台会拒绝，消息会说明
  这就是原因。
- **bitbucket.org** 的拉取请求在浏览器中打开——应用还没有它们的页面——所以那里的行评论仍需在
  网站上完成。
- **没有差异的文件**（二进制文件，或大到托管平台不予包含）没有可评论的行。

## 撰写评论

页面上的每个输入框——底部的评论、讨论内的回复、某一行的评论——都是同一个 Markdown 编辑器：
**编写 / 预览** 标签、带 GitHub 快捷键的格式工具栏、按 Enter 自动延续的列表，以及从屏幕上
已有的人和拉取请求中补全的 **@** / **#**。回复框在你点进去后才显示工具，并且由于 Enter
现在会换行，改用 ⌘/Ctrl+Enter 发送。[撰写评论](writing-comments.md) 中有详细说明和限制。

## 评论如何显示

评论是用 Markdown 写的，所以以纯文本显示的评论满是 `**`、`- [ ]` 和代码围栏。描述、对话和
评审讨论（在对话和文件标签中）都按 Markdown 绘制：标题、列表和任务列表、表格、引用、按围栏
指定的语言高亮的代码块、链接和图片。issue 页面也以同样方式绘制其文本。文本中的 `#123`、
`AB#123`、`!123` 和 `@user` 仍会变成链接，原本有 [卡片](#123-或-ab123-说的是什么) 的也仍有卡片。

![渲染后的评论：一个表格、一张被拦在占位符后面的其他网站图片，以及一个高亮的代码块](../../screenshots/pr-rendered-comment.webp)

绘制来自哪里：

| 托管平台 | 渲染者 |
|---|---|
| GitHub、GitHub Enterprise Server | GitHub 本身（`body_html`）：提及和引用像在网站上一样被链接，图片经过 GitHub 的图片代理，私有附件带着它们的签名地址 |
| GitLab、Forgejo、Azure DevOps、Bitbucket Data Center | 应用根据评论的 Markdown 绘制。相对链接指向仓库内；在 GitLab 上，`/uploads/…` 像 GitLab 一样指向项目内 |

评论是别人的内容，所以它能包含的东西很有限，比你自己的文件更有限：一份明确的标签列表，只允许
`https:`、`http:` 或 `mailto:` 的链接和图片，没有脚本、框架、表单、SVG 或内联样式，而且链接
从不在应用内打开（会交给你的浏览器）。任务列表中的复选框会显示，但不可点击：在这里勾选不会
改变托管平台上的任何东西。

**来自其他网站的图片要等你点击。** 加载一张图片就是一次请求，背后的网站能看到你的 IP 地址
和你阅读评论的时间——任何能评论的人都能在那里放一个跟踪像素。所以只有托管平台自己的图片会
自动加载：在 github.com 上是它的附件、`*.githubusercontent.com`（包括它的图片代理）和它的
资源；在其他托管平台上是它自己的地址。其他图片都会显示 *来自 example.net 的图片 — 点击加载*，
点击只加载那一张图片。**设置 → 安全 → 在评论中加载其他网站的图片** 可以关闭这一点；参见
[安全](security.md#评论中的图片)。

**预览显示将要发布的内容。** 在本页和 issue 页面上，每个评论框的 **预览** 标签都以同样方式
绘制文本：同样的规则、同样的换行、同样被拦下的图片——粘贴一个指向外部图片的链接，在你写作时
不会加载它。新建拉取请求和新建 issue 对话框保留应用普通的 Markdown 预览。

**过长或过于复杂的内容以文本显示。** Markdown 在应用窗口中渲染，有些文本的渲染开销远超其
大小所显示的。超过 **32,000 个字符** 的评论，或者构造得会卡住渲染器的评论（一个段落里成千上万
个不成对的 `_` 或 `*`，或一行里超过 32 层的 `>` 或列表标记），会以带链接的纯文本显示，标注为
*评论过长，以纯文本显示。* 或 *评论过于复杂，无法在此渲染，以纯文本显示。* 仍然渲染失败的评论
会自行以同样方式退回：页面其余部分不受影响。

它不做的事：

- **编辑时显示原始文本。** **编辑** 仍然打开 Markdown，保存后的编辑由应用绘制，直到页面重新
  读取拉取请求（在 GitHub 上之后由 GitHub 绘制）。
- **GitHub 的私有附件会过期。** GitHub 只为私有图片的地址签名几分钟；页面打开一段时间后不再
  加载的图片，用 **刷新** 即可恢复。
- **应用自己绘制的 GitHub 相对路径图片**（页面重新读取之前，从应用发出的回复）会在仓库位于
  github.com 的地址下查找，这可能不是 GitHub 会放置它的地方。
- GitHub 评论中的 **视频** 显示为文件链接，而不是播放器。
- 应用自己绘制时（在其他托管平台上）没有 **GitHub 特有的扩展**：没有表情短代码、没有 Mermaid
  图、没有提示框样式，公式保持为文本。
- **只有在围栏注明语言时才会高亮代码。** 猜测语言意味着要对页面上的每个代码块运行每种语法。
- 提交标签中的 **提交说明** 保持纯文本：git 不渲染 Markdown，托管平台也不渲染。

## 编辑和删除你的评论

已发送评论中的笔误，或不再适用的意见，以前得去浏览器里改。现在你自己的评论在标题末尾有
**编辑**（铅笔）和 **删除**（垃圾桶）：对话评论、评审讨论中的评论和回复，在对话和文件两个
标签中都有。issue 页面也有，适用于其在 GitHub 和 Forgejo 上的评论。

![你自己的评论，标为已编辑，标题末尾有编辑和删除](../../screenshots/comment-editor.webp)

什么算“你的”由页面自己决定：每次加载时，它都会询问托管平台，这个仓库的调用以谁的身份登录
（仓库绑定的配置档，而不是当前活动的那个）。大多数托管平台以登录名标识作者，比较时不区分
大小写。Azure DevOps 以显示名称标识作者，而两个人可能同名，所以在那里从不比较名称：当评论作者的 ID
与账户的 ID 一致，**或者** 作者的唯一名称（账户名，通常是电子邮件地址）与账户的唯一名称在
不区分大小写的情况下一致时，这条评论就是你的。两者都只属于一个人；后者用于覆盖作者 ID 与连接
报告的 ID 不同的情况。两者都无法比较时，所有评论都不显示这些操作。当应用无法判断你是谁时（令牌
没有用户权限范围，或托管平台没有响应），也没有评论显示它们；**刷新** 会再次询问。最终仍由
托管平台决定：它不允许修改评论的账户会被拒绝，消息会说明。

- **编辑** 会在原处打开评论，使用同一个 Markdown 编辑器，内容保持原样。**保存**（或
  ⌘/Ctrl+Enter）发送；**取消** 或 **Esc** 关闭，若你改动过会先询问。只会去掉文本前后的
  空行：缩进的代码和末尾两个空格的换行都保持原样。新文本会立即显示，页面会重新读取拉取
  请求。在拉取请求页面上，未保存的编辑在你用 **‹ ›** 继续浏览或切换标签页时会留在拉取请求里，关闭
  拉取请求时会先询问。议题页面不保留任何内容：那里在其标签页关闭前不会询问。
- **删除** 总是先询问，问题会说明会发生什么：服务器会为所有人删除该评论，且无法撤销。由于
  没有任何办法能找回它，也就没有撤销记录。

删除有回复的 **讨论的第一条评论**（评审讨论，或别人回复过的对话评论）因托管平台而异，确认
框会说明是哪种情况。其中两种托管平台并未写明，确认框也会如实说明：

| 托管平台 | 有回复的讨论的第一条评论 |
|---|---|
| GitHub | 回复应会保留；GitHub 的文档没有说明。讨论会保留回复框：第一条评论没了之后，回复会通过 GitHub 的 GraphQL API 发送到讨论本身，讨论则通过其中仍存在的回复来定位。如果失败（旧版 Enterprise Server、被 GraphQL 拒绝的令牌、GitHub 表示此账户无法回复的讨论），讨论会改为提供 **在 GitHub 上回复**。如果你在 GitHub 上有一个进行中的评审，GitHub 可能把回复归入其中：此时提示消息会说明，在你在那里提交该评审之前，没有人能看到这条回复 |
| GitLab | 只删除那条备注；讨论及其回复保留 |
| Azure DevOps | 应会被标为已删除并隐藏，讨论及其回复保留；Azure 的文档没有说明 |
| Bitbucket Data Center | 被拒绝：Data Center 不删除有回复的评论。请先删除回复，或改为编辑它 |

有些托管平台会把评论标为 **已编辑**。只有 Azure DevOps 单独为文本记录日期；在 GitHub、
Bitbucket Data Center 和 Forgejo 上，应用比较评论的创建时间和最后更新时间，因此那里的标记
只是近似（任何其他触及该评论的操作都可能使其出现）。GitLab 的日期在讨论被解决时也会变化，
因此不使用。

它不做的事：

- **Forgejo 的评审评论**（对某一行的评论）无法通过其 API 编辑，且只有部分版本能删除，因此
  两个操作都不显示：请在网站上修改。对话评论与其他地方一样可用。
- **期间有人改过。** Bitbucket Data Center 会检查评论的版本：对页面加载后已被改动的评论进行
  编辑或删除会被拒绝，**刷新** 会显示当前版本。其他托管平台以最后一次写入为准。
- **找不到**：托管平台找不到该评论时，消息会说它可能已被删除，或此账户看不到它，页面会重新
  读取拉取请求。针对已不存在的评论打开的编辑会被丢弃。
- **bitbucket.org** 的拉取请求在浏览器中打开，因此尽管应用能发出该调用，目前还没有可编辑其
  评论的页面。
- 拉取请求的 **描述** 及其评审摘要不是评论，不在这里编辑。

## `#123` 或 `AB#123` 说的是什么

一个写着 *fixes AB#4821* 的提交，或一条写着 *见 #312* 的评论，告诉你的是一个编号，而不是
它讲的是什么。想知道就得打开它。现在，**指向一个引用**——或用 Tab 移到它上面——会打开一张
小卡片，显示托管平台关于它的信息：

- 表示其类型的图标，以及原样书写的引用；
- 它的 **标题**；
- 它的 **状态**（打开、关闭、已合并——在 Azure DevOps 上是工作项自身的状态，例如
  *Active* 或 *Resolved*）；
- 在 Azure DevOps 上，还有 **工作项类型**（Bug、User Story、Task…）。

![评论中某个工作项引用的卡片：类型、标题和状态](../../screenshots/reference-card.webp)

卡片出现在拉取请求页面（描述、评论、评审讨论，以及 **提交** 标签中某个提交的完整说明）、
issue 页面，以及提交详情面板中的主题里。在 Azure DevOps 的 **提交** 标签中，提交主题里的
每个工作项（`AB#123`，或在那里指同一项的 `#123`）还会在旁边以灰色显示其标题。在 Azure
DevOps 上，`!123` 会链接到那个拉取请求，没有卡片。

| 引用 | 托管平台 | 读取自 |
|---|---|---|
| `AB#123`，以及 Azure 仓库中的 `#123` | Azure DevOps | 工作项，一次请求最多 200 个 |
| `#123` | GitHub、GitHub Enterprise Server | Issue 和拉取请求，一次 GraphQL 请求最多 50 个；GraphQL 失败时每个一次 REST 请求 |
| `#123` / `!123` | GitLab | Issue / 合并请求，每种类型一次请求 |
| `#123` | Forgejo | Issue（也包括拉取请求），每个一次请求，每次两个 |

`#123` 只在作为独立单词时才算数：`org/repo#123`（另一个仓库）、`&#39;`、像 `#123abc`
这样的颜色，以及链接中的 `#issuecomment-…` 都不受影响。

在卡片打开之前不会发出任何请求。打开时，你所在的引用以及页面上离它最近、尚未知道的引用会在
一次调用中一起查询，所以下一张卡片通常会立即出现。应用运行期间，答案在内存中保留五分钟，绝不
写入磁盘；之后仍会显示，并在下次悬停时重新读取。它们按配置档保存：调用以仓库
[绑定](profiles.md) 的配置档身份进行，换一个配置档可能看到不同的条目。

代价：

- **GitHub** 通过其 GraphQL API 一次请求最多读取 **50** 个——你所在的那个及其最近的相邻
  引用。当 GraphQL 因速率限制以外的原因失败（旧版 Enterprise Server、它拒绝的令牌）时，应用
  会退回到每次请求只读一个 issue 的 REST API：这时只请求前 **10** 个，按 GitHub 对应用的
  要求逐个进行；其余的保持未知，之后的悬停会再请求它们。
- **Forgejo** 无法在一次请求中读取多个 issue，因此每张卡片要一次请求：一次悬停最多请求
  **10** 个，每次两个。
- 在 GitHub 和 Forgejo 上，第一个表示 *请放慢* 的回应（429、403、GraphQL 自己的速率限制
  错误、次级限制，或用掉了限额中最后一次请求的回应）会停止其余请求——此时 GitHub 不会退回到
  REST——这些引用在五分钟内不会再被请求。
- **Azure DevOps** 一次请求最多读取 200 个工作项，GitLab 每种类型一次请求，所以在那里整个
  页面一次性请求。

它不做的事：

- **Bitbucket** 没有卡片：应用在那里不读取 issue，链接像以前一样打开浏览器。
- **找不到，或无权访问。** 已删除的 issue、此账户看不到的项目中的工作项，或缺少
  *Work Items (Read)* 权限范围的 Azure 令牌，看起来都一样：卡片会如实说明，链接仍然有效。
  正在限流、无法访问，或在此配置档中没有账户的托管平台会显示各自的消息。
- **Azure DevOps 之外的 `AB#123`**——比如连接到 Azure Boards 的 GitHub 仓库中——不会成为
  链接，因此没有卡片：应用不知道它属于哪个组织。
- 在不发送拉取请求合并时间的 **旧版 GitHub Enterprise Server 上的已合并状态**：会显示为
  已关闭。
- **图** 中的提交行不显示卡片。

## 限制

- **打开的拉取请求就是侧边栏的列表。** GitHub、GitLab 和 bitbucket.org 读取前 30 个；
  多于此数的仓库只显示这些，打开的数量显示为 **30+**。Azure DevOps、Bitbucket Data
  Center 和 Forgejo 会全部读取。
- **已合并和已关闭有上限**，当托管平台上还有更多时，标签会显示 **+**（其网站会列出全部）：

  | 托管平台 | 读取范围 |
  |---|---|
  | GitHub、bitbucket.org、Forgejo | 最近更新的 100 个，已合并和已关闭 **合计** |
  | GitLab | 各自最近更新的 100 个 |
  | Bitbucket Data Center | 按服务器的 *newest* 顺序各 100 个——其 API 不说明这指的是创建还是更新 |
  | Azure DevOps | 在 **过去一年** 内结束的拉取请求中各 100 个；其 API 不说明顺序，所以超过一百个时取哪些由服务器决定 |

  不读取它们的检查——已结束的拉取请求的 CI 已无关紧要，而且每行都要多一次请求——所以
  **CI 失败** 在这些标签中不适用（其按钮在那里隐藏）。
- **没有账户**：没有能访问该托管平台的令牌时，已合并和已关闭会如实说明，而不是显示空列表
  （GitHub 仍可读取公开仓库）。
- **检查**：GitHub 和 Bitbucket Data Center 在列表中直接带有检查。对 GitLab、Azure
  DevOps 和 Forgejo，会在页面打开时按每个 head 查询一次，使用与图中 CI 徽章相同的缓存。
  bitbucket.org 没有检查。
- **评审者**：GitHub、GitLab、Forgejo、Bitbucket Data Center 和 Azure DevOps 会给出
  仍被请求的人（Azure：尚未投票的人；团队不计入）。bitbucket.org 的列表不提供这一信息，
  所以那里的评审者筛选为空。
- **描述搜索** 仅在托管平台的列表包含描述时有效；bitbucket.org 可能省略描述，此时只搜索
  标题、分支和编号。
- **bitbucket.org 和 Azure DevOps 上的“我”** 按显示名称匹配，因为它们的列表就是这样
  称呼作者的。
- **Azure DevOps 上的更新于** 是拉取请求创建（或关闭）的时间：其列表没有最后活动时间。
- 浏览顺序只在应用运行期间记住；重启后，从列表打开的拉取请求会改为浏览打开的拉取请求。
- **读取文件可能会 fetch 一次。** 当拉取请求的提交不在本克隆中时，页面会在打开时以及点击
  **刷新**时按 id 从其远程获取——绝不会在评论、评审或合并之后获取，并且每个会话中每个拉取
  请求版本最多一次（失败的尝试会等待“刷新”）。它只写入对象：不创建分支，也不写 `FETCH_HEAD`，
  所以工具栏上的“… 前获取”不会变化。20 秒后，或传输连续 15 秒低于 1 KB/s 时，它就放弃，并且
  从不询问密码：git 的提示已关闭，Git Credential Manager 也被告知不要打开登录窗口，所以需要
  登录的远程会退回到 API。ssh 远程按原样使用你自己的 ssh 设置，只是不会打开 ssh 自己的密码
  短语窗口。当另一个 git 操作占用仓库（例如一次长时间的推送）超过五秒时，这一次会跳过获取而
  改用 API。获取进行期间你在工作区中做的改动不会丢失：完成后仓库会刷新。缺少对象的浅克隆或
  部分克隆会退回到托管平台的 API。
- **超出上限**的文件会带着数字列出，但没有差异：从克隆读取的差异为 20,000 行改动或 8 MB，从
  Azure DevOps 读取的每个版本为 4 MB。单次读取保留约 150,000 行或 48 MB 的差异；之后的文件为
  **尚未加载**，在打开时读取。
- git 视为二进制的 **UTF-16 文件**会重新按文本读取，每个拉取请求最多 50 个、每个版本最多
  2 MB；超出后显示为二进制。
- **重命名**按 `git diff -M` 的方式识别（默认 50% 相似度），可能与托管平台自身的匹配略有不同。
- **经由 API 的 Azure DevOps** 总共在一分钟内读取前一百个文件；一分钟用完时剩下的文件为
  **尚未加载**。被限流的响应会让所有读取暂停到服务器的 Retry-After。改动超过 20,000 处的拉取
  请求会列出到这个位置为止，标签会说明这一点。
