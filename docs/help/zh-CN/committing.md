# 提交

## 消息风格

在 **设置 → AI → 提交信息** 中，或直接在编辑框里挑一种；
编辑框会随之调整。风格属于配置档案所用的 AI：通用 AI，或该配置档案的自有
AI。

| 风格 | 长这样 |
|---|---|
| **Conventional** | `feat(api)!: add rate limiting`——标题前带一个 **类型 ▾** 按钮 |
| **Gitmoji** | `✨ add rate limiting`——带一个表情选择器 |
| **Gitmoji + Conventional** | `✨ feat(api): add rate limiting`——表情选择器*和* **类型 ▾** 按钮 |
| **工单** | `ABC-123: add rate limiting`——由分支名预填 |
| **纯文本** · **自动** | 你写什么就是什么；自动模式让 AI 来决定形态 |
| **原始人** · **俳句** | 就是字面上听起来的那个意思 |

在 Conventional 风格下，前缀放在标题前的 **类型 ▾** 按钮上（*feat(api)*，还没有时显示 *类型*），输入框里只保留它后面的文字；提交信息仍然得到完整的 `feat(api): …`。按钮列出各个类型，**无类型** 会去掉前缀。手动输入前缀同样可行；在输入框开头按 <kbd>Backspace</kbd> 会把前缀重新显示为文本，便于修改其作用域（scope）；输入框失去焦点时，它会重新收回到按钮上。

![由提交模板预填的编辑框](../../screenshots/commit-template.webp)

### Gitmoji

[Gitmoji](https://gitmoji.dev) 在主题前加一个表情，让历史一眼就能读懂：🐛 修复、
✨ 新功能、🔥 删除。两种 gitmoji 风格下，表情按钮都紧挨着主题输入框。它会打开
**全部 75 个官方 gitmoji**，可按表情、按 `:代码:`（gitmoji-cli 用户输入的那种）
或按你所用语言中的含义搜索。

**Gitmoji + Conventional** 让类型和表情保持同步。选一个类型，表情随之而来；改了
类型，表情也跟着变——除非表情是你亲手选的（比如给 `fix` 选了 🚑️），这种永远
不会被覆盖。

| 类型 | Emoji | 类型 | Emoji |
|---|---|---|---|
| `feat` | ✨ | `test` | ✅ |
| `fix` | 🐛 | `build` | 📦️ |
| `docs` | 📝 | `ci` | 👷 |
| `style` | 🎨 | `chore` | 🔧 |
| `refactor` | ♻️ | `revert` | ⏪️ |
| `perf` | ⚡️ | | |

AI 也按同样的格式书写。如果模型漏了表情，或用 `:shortcode:` 作答，主题会在填入
输入框之前被纠正。

其他工具写成 `:sparkles: add login` 的提交，会在图谱、提交详情和历史视图中
**显示**为 `✨ add login`。

限制：

- 选择器总是写入 **unicode** 表情，从不写 `:shortcode:`。
- shortcode 只在显示时转换。提交本身不会被改写，在历史中搜索时匹配的是提交时的
  原文。
- 只认 gitmoji：以其他表情开头的主题保持原样。
- 如果仓库的 `commit-msg` 钩子用标准 Conventional 预设运行 commitlint，开头的
  表情会被拒绝。这是钩子的规则，不是 GitHuttBr 的：请把 commitlint 配置为支持
  gitmoji，或在该仓库使用纯 Conventional。

## 用 AI 写提交信息

开启 AI 后，描述下方有 **✦** 按钮（悬停显示 *用 AI 生成*）。它读取已暂存的 diff，按上面选的风格写出摘要和描述。旁边一个单独的选择器写明由谁回答——*账户 · 模型*，即在 **设置 → AI → 按任务选择模型** 中为提交信息选定的组合——这样慢的本地模型或昂贵的模型都不会让你意外。

- 名称旁的 **▾** 列出已保存的账户，每个账户附带几个模型。所选的只用于
  **这一次生成**；设置不会改变。
- 运行时，✦ 会转动，同一行显示已用秒数和 **取消**；取消会停止请求本身，而不只是转圈。期间摘要和描述为只读，你输入的内容不会被回复覆盖。30 秒后，应用级的 *耗时比预期长* 提示（[AI](ai.md)）会让你选择继续等待，或把同一次生成转到另一个就绪账户；之后的 **重新生成** 就使用该账户。
- 新文本会 **替换** 原有内容，原有内容会被保留：**撤销** 和 **重新生成** 出现在同一行（悬停可见 *由 账户 · 模型 在 7 秒内生成*）。撤销会恢复你的摘要和描述。一旦你编辑文本或提交，两者都会消失。
- 你输入的描述，或 AI 写的描述，在切换到其他标签页再回来时仍会保留，和摘要一样——生成之后的 **撤销** 和 **重新生成** 也是如此。

![用 AI 生成及账户菜单](../../screenshots/commit-ai-generate.webp)

![生成的消息，账户旁边是“撤销”和“重新生成”](../../screenshots/commit-ai-generated.webp)

[编辑提交](commit-edit.md) 中有同样的按钮，基于那次提交自身的 diff 生成。

限制：

- 只发送已暂存的 diff，过大时会截断——绝不发送未暂存的更改或其他文件。
- 撤销只保留一步：连续生成中第一次生成之前的文本。撤销消失后，这份副本也随之消失。
- 取消不会退回提供方已为该请求消耗的 token。
- ▾ 列表显示所有已保存的账户，包括尚无密钥的账户；选择它会以该账户自身的错误
  失败。

## 编辑框替你做的事

- <kbd>↑</kbd> <kbd>↓</kbd> 可以调出你**最近用过的消息**。
- **共同作者选择器**会从仓库自己的贡献者中挑人，添加 `Co-authored-by:` 尾注。
- `commit.template` / `.gitmessage` 会**预填**消息，并剥掉注释行。
- 在合并、拣选（cherry-pick）或还原期间，消息会按 git 的做法**预先填好**。
- 草稿按仓库分别**保留**，所以切换标签页永远不会弄丢一条消息。

## 检查器

一个实时、不拦路的检查：标题长度、结尾的句号、非祈使语气或小写开头的标题、正文行过宽。它只给提示，从不设卡——它不会阻止你提交。长度就是标题旁的计数器，按 72 个字符的上限来看（*56/72*）：超过上限会变红，其提示信息建议以 50 为目标。其他提示列在描述下方。

## 修补

修补会用当前已暂存的内容重写上一个提交。GitHuttBr 会先把原有的消息显示出来，这样你是在编辑，而不是在重打一遍。

在提交图的某一行上，**修补提交…**对 HEAD 做的就是同一件事：加载完整的消息，把编辑框切换到修补模式并聚焦。已经推送过的 HEAD 仍然可以修补，但 GitHuttBr 会警告：更新远程将需要一次强制推送。

**撤销提交…**是它的孪生兄弟，面向尚未推送的 HEAD：mixed 重置到父提交，工作树的更改保留，消息回到编辑框里。首个提交有一条专门的路径，留下的是一个尚未诞生的分支，而不是毁掉那些文件。
