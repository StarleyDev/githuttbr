# 解决冲突

当一次合并、变基、拣选（cherry-pick）或还原停下来时，解决器会把整个步骤变成一屏。顶部的栏会告诉你**是什么**停了下来，以及**在什么和什么之间**——写的是「正在将 `feature` 合并到 `main`」，而不是干巴巴一句「冲突」——还有你进行到了哪里：*已解决 5 个文件中的 2 个*，以及所有文件里还剩多少处冲突。

![冲突解决器](../../screenshots/conflict-resolver.webp)

## 文件条

栏下方，这一步停下来的每个文件各有一个标签：

| 标签 | 含义 |
|---|---|
| 绿色带 ✓ | 已解决——已暂存，没有什么要再决定的 |
| 带描边 | 你当前所在的文件 |
| 红色数字 | 这个文件里还有多少个冲突块 |
| 一段文字 | 没有文本可合并的冲突：*一方已删除*、*双方都重命名了*、*一方添加了* |

已解决的标签排在前，未解决的排在后，每一组按名称排序，所以这一条从左往右读就是：左边是做完的，右边是剩下的。

**下一个文件 →** 会跳到下一个仍未解决的文件，把一个文件标记为已解决也会自动带你过去。栏里的**继续**在每个标签都变绿之前一直不可用；**中止**会先询问，并说明你会失去什么。

git 会在文件被暂存的那一刻忘掉它，所以「已解决」指的是 GitHuttBr 在这一步中看到的情况，再加上 git 在合并信息里列出的文件。打开解决器之前在终端里暂存的文件依然算数；而在变基中途重启之后，那一步里已解决的那一半可能就不算了。

## 为什么这里会冲突

文件标题栏里的**为什么会冲突**，会分别按两边列出：自两个分支分道扬镳以来，动过这个文件的那些提交——也就是 `git log --merge`，git 早就自带、却没人找得到的东西。

![来自两边、动过这个冲突文件的提交](../../screenshots/conflict-why.webp)

冲突标记告诉你哪些内容打了架。这里告诉你是谁改的、为什么改，而后者通常才是真正决定该怎么解的东西。这里什么都没有，说明两边都没有对这个确切路径提交过改动——这场冲突来自一次重命名或移动。

标题栏还会告诉你当前是第几处冲突，以及这个文件属于哪种冲突，这些都读自 git 自己的状态：*双方修改了相同的行*、*双方都添加了*。

## 三个栏

| 栏 | 是什么 |
|---|---|
| **我方** | 你原本所在的那一边，顶部显示这一边最近一次动过该文件的提交：sha、标题、作者、多久以前 |
| **基础** | 两边共同的出发点——共同祖先；如果是拣选或变基中的一步，则是正在应用的那个提交的父提交。每处冲突所替换掉的行带有底色 |
| **传入方** | 正在并进来的那一边，顶部的显示方式与我方相同 |

结果标题栏上的**显示基础**用来隐藏或显示基础栏，并会记住你的选择。没有基础时——双方都添加了这个文件——它会变灰。

所有栏都能调整宽度，结果标题栏上还有两个视图开关：

| 开关 | 作用 |
|---|---|
| **换行** | 让两侧栏里的长行折行，而不是横向滚动。结果的文本视图保持一行占一行——旁边的标记依赖这一点——所以它始终可以滚动 |
| **联动滚动** | 让各栏和结果一起滚动，纵向和横向都是。它们的行数不同，所以纵向位置按比例对齐 |

换行默认关闭，联动滚动默认开启，两者都会记住状态。

## 结果

结果就是文件即将被写入的样子。每处冲突都以一张卡片的形式留在原位，卡片上有四种答案：

| 答案 | 写进文件的是什么 |
|---|---|
| **用我方** | 你的行，只有你的 |
| **用对方** | 对方的行，只有对方的 |
| **两者** | 先是你的行，再是对方的 |
| **编辑** | 两者都放进去，在文本编辑器中打开并选中这处冲突，适合答案是「两者都要，但得调整一下」的时候 |

尚未作答的卡片会预览两边，每一行都标着 *← 我方* 或 *← 对方*，并编上选中后它会落到的行号，这样不用抬头就能做决定。在行很长的文件里，代码在下方横向滚动时，答案按钮始终留在视野里。文件标题栏上的**整个文件:我方 | 对方**会一次性回答所有冲突。

**以文本编辑**会把结果切换成可以自由输入的普通编辑器，标题栏显示文件的行数。一旦你输入过内容，卡片就不再能描述那里的实际内容，所以文本会一直保留，直到**重置选择**把一切恢复原状。

底部会统计这个文件还剩多少；**将*文件*标记为已解决**会写入结果并暂存它，在每处冲突都有答案之前不可用。

## 在文件中移动

打开一个文件会落在它的**第一个冲突**上，而不是文件开头。结果标题栏上的 ⌃ / ⌄ 箭头——或 <kbd>Alt+↑</kbd> / <kbd>Alt+↓</kbd>——会逐个跳到其余冲突，并把每个栏一起滚动到那里。

## 按行挑选

两侧栏依然可以按**行**、按**块**挑选，栏标题上的复选框则一次拿下**整整一边**——用于卡片没有提供的答案，比如你的两行加对方的一行。按行挑选的结果会立即反映在卡片上。

## 没有内容可合并的文件

有些冲突没有可比较的行：一方**删除**了另一方修改过的文件，或者双方把它**重命名**成了不同的名字。三个栏里有一个是空的，什么也说明不了，所以这些情况改用一张卡片——谁做了什么，附上每一边的提交、作者和时间。

![一方删除、另一方修改的文件](../../screenshots/conflict-deleted.webp)

| 情况 | 选项 |
|---|---|
| 一方已删除 | **保留文件**（含另一方所做的修改）、**删除文件**（会先询问），以及**查看我方的修改**——相对基础的 diff，让你知道删除会丢掉什么 |
| 双方都重命名了 | **保留**其中一个名字或另一个，或者**保留两个名称** |

git 不会记录被重命名的原文件与它的两个新名字之间的关联，所以卡片按内容来配对。无法判断时——同时有多个重命名，而且文件内容也改了——它会直说，新名字则作为各自的标签出现。

## 收尾

最后一个文件解决后，工作区不会让你再去找**继续**：一张卡片会汇总这些冲突是怎么回答的，让你编辑合并信息（预先填好 git 自己的信息），并直接在这里完成。

![所有冲突已解决，带合并信息和 rerere 开关](../../screenshots/conflict-done.webp)

- 汇总统计的是它看到你所做的选择：我方、对方、两者、手动编辑。在解决器之外解决的文件只算作一个文件，不算一个答案。
- **变基**的一步会保留被重放提交自己的信息，所以这里没有信息输入框。
- **记住这些解决方式 (rerere) 供下次使用**就是 git 的 `rerere.enabled`，与设置里的是同一个开关。git 只会记住它亲眼看到发生的冲突，所以在这里打开，从下一次冲突起才生效。
- **再次检查**会关闭解决器，停留在已暂存的结果上。

## 撤销

每一次解决——把文件标记为已解决、选用某一边、保留或删除文件、敲定一次重命名——都有对应的撤销项。撤销会把冲突恢复成 git 当初留下的原样：冲突标记、索引中的两边和基础、磁盘上的文件。**中止**是唯一无法撤销的操作，所以它会先询问。

## AI 协助

启用 AI 后，**用 AI 解决**会以文本形式往结果里提出一份合并方案。它绝不会自己应用任何东西：你来读、你来改、你来暂存。参见 [AI 功能](ai.md)。

## Xcode 项目文件

`project.pbxproj` 比 iOS 仓库里任何别的文件都更容易冲突，而且几乎从来不是因为
谁跟谁有分歧。它是一个扁平的对象字典，键是 24 位十六进制 id，所以添加一个文件
会写入四条记录：一个 `PBXBuildFile`、一个 `PBXFileReference`、所属分组
`children` 里的一行，以及目标构建阶段里的一行。两个人各加一个文件，就是落在同样
那几行上的八条记录。Git 看到的是碰撞；其实没有什么需要解决。

当冲突的文件是 `project.pbxproj` 时，冲突编辑器会把三个版本当作项目而不是文本
来读，并提出**按结构合并**：按 id 配对对象，取两边的所有新增，合并 `children`
和 `files` 数组，然后在真正分歧的地方停下。面板上方的横条会说明每一边加了什么，
以及还有什么——如果有的话——要你来定。

和 AI 提议一样，它只落在结果里，不会暂存任何东西。你在保存前先读一遍。

![Xcode 项目文件上，冲突面板上方的结构合并横条](../../screenshots/conflict-pbxproj.webp)

### 它拒绝做的事

**它绝不猜测你们都动过的设置。** 如果你把 `MARKETING_VERSION` 设成 `1.1`，
对方设成 `2.0`，那是一个决定，会以设置名、你的值、对方的值出现在横条里，而不是
在你背后被解决掉。它拿不准的对象会原样保留*你的*版本，好让半途而废的合并永远
不会落到磁盘上。

**只要三个版本中有任何一个解析不了，它就整份拒绝。** 一个 Xcode 打不开的
`project.pbxproj` 比手工合并代价更大，所以凡是它无法确凿读出的，都仍旧是普通的
文本冲突，并且会明说。

**它不会发现同一个 id 被分给了两个不同的对象。** 因为 Xcode 随机取 id，这很
罕见——但一旦发生，选哪一边都会悄悄丢掉某个人的文件，所以它选择报告而不是合并。

### 不要用 `merge=union`

针对这件事流传的偏方是在 [`.gitattributes`](attributes.md) 里写
`*.pbxproj merge=union`。别用。只要改动全是互不相干的新增，union 就能凑合；可一旦
两个人编辑同一个构建设置，它会把两行都写出来，产出一个 Xcode 拒绝打开的文件——
而那恰恰是你最不可能仔细读 diff 的时刻。按结构合并给你同样的便利，没有这个故障。

## 锁文件

`Podfile.lock`、`Package.resolved`、`yarn.lock` 和它们的同类，记录的是某个解析器
已经解好的依赖图。把一份解的一半缝到另一份解的一半上，得到的是一份没人解过的图：
它可能装不上；就算装得上，装的也是两个分支都没测过的东西。

所以当冲突的文件是锁文件时，横条会说明是哪个工具在管它，就地提供**保留我们的**和
**保留他们的**，并给出之后重新生成它的命令。在这里选一边不是折中——它就是全部方法，
而让它正确的是重新生成这一步。

![冲突面板上方的锁文件横条](../../screenshots/conflict-lockfile.webp)

三个面板依然在，因为偶尔你确实想读读改了什么：一个你认得的校验和、一个你预期中的
版本。这里想劝你别做的，是动手去编辑它们。

## 从一开始就避开它们

[冲突雷达](conflict-radar.md)会在你合并任何分支之前，先告诉你哪些分支将会冲突。

## 让 git 帮你记住（rerere）

对一个长期存在的分支做变基，你每次都会撞上同一个冲突。`rerere`——*reuse recorded resolution*，复用已记录的解决方案——就是 git 的答案：它记住你当初是怎么了结某个冲突的，并在下次出现一模一样的冲突时把那个答案重放一遍。

**设置 → Git 与同步 → 记住冲突的解决方案。** 它会把 `rerere.enabled` 写进你的全局 git 配置，所以命令行也会有同样的行为。

当 git 替你作答之后，解决器会明说这件事，而不是给你看一个空空如也的「没有冲突标记」界面，同时提供**忘掉这个解决方案**——它会丢掉那份记忆*并且*把冲突原样带回来，好让你换个方式了结它。

有两件事值得知道：

- **被重放的解决方案不会自动暂存**，除非你打开*自动暂存被重放的解决方案*。让它保持关闭：这次停顿的意义就在于，一个记住的答案在这一次特定的合并里可能是错的，而不看一眼就暂存，正是它混进提交的途径。

  这也是为什么被重放的文件**仍然留在「有冲突的文件」里**：git 写好了内容，但索引里它仍然处于未合并状态，只有暂存才能了结这一点。用解决器里的**按现状暂存**，或者列表里的**全部标记为已解决**，才能让它挪窝。
- **rerere 并不理解每一种冲突。** 添加/添加与删除/修改这两类冲突拿不到预映像，所以它们每次都会原样回来。设置里的计数是它实际记住的条数，而**全部忘掉**会清空它。
