# 安全与机密

Gitcito **没有后端**。唯一的网络请求发往你的 Git 托管方；如果你打开了 AI 功能，
还会发往你的 AI 供应商。

![安全设置](../../screenshots/settings-security.webp)

## 机密遮蔽

`.env*`、`*.pem`、`*.key`、`id_rsa`、`credentials.*` 这类文件里的值，在差异（对比）、
文件和追溯（blame）视图中会渲染成 `KEY=••••••`，这样屏幕共享或截图就泄露不了它们。
Apple 的签名材料也算：`*.mobileprovision`、`*.provisionprofile`、`*.p12`
以及 App Store Connect 的 `*.p8` 密钥。`*.cer` 不算——证书本就是公开的。

这**只影响显示**：它从不修改文件，也从不改变你暂存的内容。每个视图都有一个眼睛开关
可以显示原值。`.env.example`、`.sample` 和 `.template` 被当作模板，而不是机密。

![一个 .env 文件，所有值都被遮蔽，旁边是显示开关](../../screenshots/secret-masking.webp)

## 在你造成损失之前的防护

| 防护 | 触发时机 |
|---|---|
| **机密文件** | 提交看起来像凭据的东西时——附带一键*忽略并取消跟踪* |
| **大文件** | 提交超大的二进制对象时（阈值在 设置 → 安全 中） |
| **构建垃圾** | 提交 `xcuserdata/`、`DerivedData/` 或 `.DS_Store` 时——同样提供一键*忽略并取消跟踪* |
| **保护分支** | 直接向 `main`/`master` 提交，或强制推送它们时 |
| **已跟踪的机密** | 推送一个*跟踪着*机密文件的仓库时——每个会话警告一次 |

## 评论中的图片

拉取请求和 issue 的评论是别人写的，其中的一张图片就是你的电脑向作者所选网站发出的一次请求。
那个网站会得知你的 IP 地址以及你阅读评论的时间——一个跟踪像素只需要评论的权限就够了。

所以应用只会自动加载托管平台自己的图片：在 github.com 上是它的附件、
`*.githubusercontent.com`（包括 GitHub 在自身渲染中放在每张外部图片前面的代理）和它的资源；
在其他托管平台上是它自己的网址，通过 https。其他图片会显示一个注明其域名的占位符，只有在你
点击时才会请求——只请求那一张，一次。请求从不发送 `Referer`。

| 设置 | 作用 |
|---|---|
| **在评论中加载其他网站的图片**（默认关闭） | 任何网站的图片都无需点击即可加载，就像在托管平台的网站上一样 |

限制：

- **托管平台仍然能看到你。** 托管平台自己的图片——以及在 GitHub 上经过其代理的任何图片——
  都是发给托管平台的请求，而它已经知道这个账户在阅读该拉取请求。
- **`raw.githubusercontent.com` 和 `gist.githubusercontent.com` 无需点击即可加载。**
  任何人都能在那里放文件，所以图片是他们的——但提供它的是 GitHub，作者看不到你的 IP 地址，
  也看不到你何时阅读。
- **GitHub 的私有附件会过期。** 它们的签名地址只持续几分钟；页面上的 **刷新** 可以找回不再
  加载的那张。
- 这些页面上 **评论框的预览** 遵循同样的规则：粘贴的外部图片链接在你写作时不会加载。
- **仅限拉取请求和 issue 页面。** 仓库中 Markdown 文件、发布说明或 wiki 里的图片是你自己
  仓库的内容，照常加载。
- **链接不是图片。** 点击评论中的链接会像应用中的任何链接一样在浏览器中打开。

评论也无法让窗口卡死或崩溃：超过 32,000 个字符的评论，或构造得会让 Markdown 渲染器运行好几
秒的评论，会以纯文本显示。评论其余部分受到的限制见 [拉取请求](pull-requests.md#评论如何显示)。

## AppImage 与比它活得更久的路径

AppImage 从 `/tmp` 下的一个文件夹（`/tmp/.mount_…`）运行。这个文件夹只在应用打开期间存在，
每次启动都会换名字，而且位于任何本地用户都能写入的目录中。直到 4.37.1，AppImage 都可能把
这个文件夹里的路径写进两个比它活得更久的地方：`PATH` 中的 `gitcito` 链接（[CLI](cli.md)）
和仓库的 `diff.<name>.textconv` 设置（[属性](attributes.md)）。应用退出后，同一台机器上的
另一个用户可以用自己的程序重新创建这个文件夹，而你下一次运行的 `gitcito` 或 `git diff`
就会执行它。

现在 Gitcito 在 AppImage 下会拒绝这两种写入，启动时会对过期的 `gitcito` 链接发出警告（并提供
一条命令面板命令来移除它），还会在属性对话框中用一个 **移除** 按钮标出过期的转换器。它只能
看到你打开的仓库；要在别处找出过期的转换器，请在每个仓库中（以及加上 `--global`）运行
`git config --get-regexp 'diff\..*\.textconv'`，并删除所有指向 `/tmp/.mount_` 下的条目。
只有一个用户的机器不会受影响，但这些过期条目依然是无用的累赘。

## 操作系统钥匙串

令牌和[保险库](vault.md)条目用你的操作系统钥匙串加密（Electron 的 `safeStorage`），
而不是用设置文件里的某个密钥。

**在你点头之前，什么都不会碰钥匙串。** 在系统自己的权限对话框出现之前，Gitcito 会
先说明要存的是什么、它做不到什么（一个应用只能读回它自己创建的那条记录——你的其他
密码它够不着），以及拒绝也完全没问题：那样令牌只在本次会话的内存中存活，保险库保持
关闭，你也可以稍后在 **设置 → 安全 → 操作系统钥匙串** 里打开它。

全新安装在真正需要存东西之前，会发出**零**次钥匙串调用。

关闭期间，“集成”中的令牌输入框会提示这一点 — *仅保存到你退出 Gitcito 为止：系统钥匙串已关闭。* — 旁边有 **启用** 按钮。无论在那里还是在这里开启，本次会话中已输入的令牌也会一并保存，无需重新粘贴。

![钥匙串关闭时“集成”中的令牌输入框：仅保存到退出为止，旁边有启用按钮](../../screenshots/token-keychain-notice.webp)

在钥匙串关闭时 **移除** 的令牌会立刻消失——不再随任何请求发送——但只在 **本次会话**
有效：钥匙串关闭时无法写入加密存储，这次清除只保存在内存里，从不写入文件。在退出前重新
打开钥匙串，保存的副本就会在那时被删除；先退出的话，旧令牌会在下次启动时回来。在那之前，
提示会因此一直显示。要一步彻底删除已保存的令牌，请在钥匙串开启时清空它。

空白只会清除 Gitcito 给你看过的内容。如果钥匙串从一开始就是关闭的，已保存的令牌从不会被
解密或显示——字段是空的——所以只有你在那里输入后又清空的令牌会被移除；钥匙串开启后，
下面保存的那个依然在。

如果在钥匙串说明显示时窗口重新加载或崩溃，这个问题会被视为未回答——而不是拒绝——并在下次
需要保存令牌时再次询问。不会有任何东西去等待一个已经没人能回答的问题：设置会照常重新加载。

### 没有钥匙串的 Linux

在 Linux 上，钥匙串是一个密钥服务——GNOME Keyring 或 KWallet。如果一个都没在
运行，系统仍会“加密”，但用的是一个固定密码，每台机器都一样：令牌和密钥只是被
打乱了，并没有受到保护。设置 → 安全 会在钥匙串状态下方说明这一点——*没有正在
运行的钥匙串……*——这样“钥匙串”这个词就永远不会代表一种并不存在的保护。

为了不让任何新东西落进一个谁都能还原的存储里，没有钥匙串运行时你输入的令牌
**只保留到你退出应用为止**。令牌输入框会这样提示——*仅保留到你退出 Gitcito：
没有正在运行的钥匙串……*——而且没有重试按钮，因为重试没有用；只有钥匙串能解决。导入带凭据的设置文件时，也会在导入前给出同样的提示。
之前保存的令牌仍然可读——你永远不会被挡在外面——清除或替换其中一个，依然会把旧值
从磁盘上删除。两个局限：通用 AI 的密钥不会被移到它的共享位置（每个配置文件继续
读取自己的那份）；保险库仍然保存到基础存储，因为它没有仅限本次会话的模式。
安装或解锁一个钥匙串并重启 Gitcito，才能重新持久保存新令牌。

Gitcito 不轻信系统对它所得存储的说法。当系统这样称呼它、当系统根本叫不出它的名字、以及当它
加密的内容带着固定密码的标记返回时——无论系统怎么说——都把它算作基本存储。因此，即使钥匙串
悄悄退回到基本存储，新的令牌也不会落到磁盘上。

不再响应的钥匙串不会被无限期等待。在 Linux 上，一旦钥匙串在本次会话中响应过一次，它 10 秒
未回答的问题就算作 *没有钥匙串*：你保存的令牌会保留到退出为止，保险库保持关闭。会话中的第一个
问题——可能会弹出钥匙串自己的密码提示的那个——以及紧接在 Gitcito 说明之后的那个问题有两分钟，
这样阅读对话框时永远不会被打断。这样的超时之后的半分钟内，回答保持为 *没有钥匙串*，不再询问；
之后 Gitcito 会重新询问。macOS 和 Windows 在本地回答，从不设超时。

这个限制只针对那一个问题——*钥匙串在吗？* 回答了这个问题、之后在加密或解密时卡住的钥匙串
仍会被等待：保存设置和保险库会一直处于忙碌状态，直到它响应或 Gitcito 重启。

### 已保存的令牌无法读取时

如果你关掉了系统的钥匙串提示、钥匙串被锁定，或者令牌存储是由另一份 Gitcito（开发版、重新
签名的版本）写入的，Gitcito **无法读取你保存的令牌——也不会动它们**。设置 → 安全 会显示
*Gitcito 无法读取你保存的令牌*，这期间输入的令牌只在本次会话中保留（字段也会这样提示）。
它绝不会写到那个读不出来的存储上面：那样会用你刚输入的这一个替换掉所有已保存的令牌。

| 按钮 | 作用 |
|--------|--------------|
| **重试** | 再次读取存储——此时系统可能会请求访问钥匙串。一旦可以读取，这期间输入的令牌就会并入其中。 |
| **新建令牌存储** | 先询问。Gitcito 不再等待旧存储，而是只用本次会话的令牌新建一个存储。旧文件作为备份在旁边保留 30 天，然后被删除。适用于永久丢失的存储，而不是你关掉的提示。 |

## 导入设置

**设置 → 导入 / 导出** 可以在机器之间迁移设置、配置文件和主题。默认导出**不含
任何令牌或 API 密钥**，导入这样的文件也绝不会动你已保存的那些——文件里空白的
令牌表示“这个文件里没有”，而不是“删掉我的”。

### 选择导出哪些内容

备份和给同事的文件不是同一个文件。备份需要一切；给另一台电脑的文件不该带上那里不存在的
文件夹；给团队的文件既不该带上你的账户，也不该带上你的路径。所以 **导出设置** 会打开一个
对话框，列出与导入相同的四个部分（见下表），每个都标出它在这台电脑上的大小，并且只写入你
勾选的部分。没勾选的部分根本不在文件里——之后导入它时，另一台机器上的这部分保持原样。

![设置 → 数据 → 导出：选中了"另一台电脑"，绿色提示说明文件不含这台机器的任何路径，下方是将要写入内容的清单](../../screenshots/settings-export.webp)

部分上方的三个快捷方式会勾选常用组合。手动改动复选框时，会点亮与之匹配的快捷方式，或者
一个都不亮：

| 快捷方式 | 部分 | 用途 |
|----------|-------|-----|
| **完整备份** | 全部四个 | 恢复这台电脑或它的副本——与"导出"在有部分之前写出的文件相同 |
| **另一台电脑** | 配置文件与账户、应用偏好 | 在新机器上带上你的身份和喜好，但不带这台机器的文件夹和程序 |
| **给团队** | 应用偏好 | 共享的主题、快捷键和提交图设置——没有任何个人内容，也没有路径 |

部分下方的提示会说明文件是否点名了这台电脑的文件夹或程序：勾选了 **仓库** 或 **程序** 时为
琥珀色（在另一台机器上导入时会转换这些路径，或略过找不到的），没有它们时为绿色。没有
**程序** 的 **配置文件与账户** 也会略过 AI CLI 的路径——它们和配置文件存在一起，但指向的是
这台机器上的程序。

**凭据只随配置文件，而且只在你要求时。** 令牌和 API 密钥属于配置文件，所以只有勾选了
**配置文件与账户**，**包含 API 密钥、令牌与保险库密钥** 才可用；取消勾选这个部分，这个选项
也会随之清除。勾选凭据后，对话框会推荐 **用密码保护**（见下文），而不加密导出会再确认一次。

底部的框会在你按下 **导出…** 之前列出文件将包含的内容：多少个配置文件（带或不带凭据）、
配置文件图片、偏好、仓库和程序的路径、是否包含仓库笔记和 wiki 以及保险库、哪些部分被略过，
以及文件是否加密。哪些内容跟随哪个部分：

| 附加内容 | 跟随 | 条件 |
|-------|-----------|-----------|
| 配置文件图片 | 配置文件与账户 | 选择了图片作为头像的 |
| 保险库密钥 | 配置文件与账户 | 仅在勾选凭据选项时 |
| 仓库笔记和 wiki | 仓库与工作区 | 总是随该部分一起 |

局限：部分是完整的单位——不能单独挑选某个配置文件、某个仓库或某项偏好。没有 **配置文件**
的 **程序** 会带上终端、编辑器和默认应用，但不带 AI CLI 的路径（它们在配置文件里）。清单
只统计条目数量，不显示路径本身。而且缺少某个部分的文件无法把它还回来：恢复一个 **给团队**
文件只会恢复偏好。

### 选择导入哪些内容

一个设置文件里有两类东西：跟着*你*走的（配置文件、主题、快捷键），以及只在写出它的
那台机器上才有意义的（你的仓库所在的文件夹、终端的路径）。在一台新电脑上全部应用，
侧边栏就会塞满指向虚无的标签页。所以在你选好文件（如果有密码，再输入密码）之后，
会有一个对话框问你要带入哪几项。在你按下 **导入** 之前什么都不会生效；**取消**
则一切照旧。

![设置 → 数据 → 导入：四项，仓库未勾选，因为它们的文件夹在这里一个都不存在，路径转换已展开](../../screenshots/settings-import.webp)

| 项 | 包含的内容 |
|------|-----------------|
| **配置文件与账户** | 配置文件、Git 身份、集成链接、通用 AI 设置和配置文件图片——如果文件里有，还包括凭据和[保险库](vault.md) |
| **应用偏好** | 主题、语言、快捷键、布局、提交图和图标的颜色 |
| **仓库与工作区** | 标签页、工作区、收藏、别名、标签页图片、每个仓库使用的配置文件、扫描的文件夹，以及各仓库的笔记和 Wiki |
| **本机程序** | 终端、外部编辑器、默认应用以及 AI CLI 的路径 |

每一项都会显示文件里有多少条属于它的内容。没勾选的项在这台机器上原样保留。

**配置文件会与你的合并。** 来自另一台电脑的文件，很少会有这台电脑上的全部配置
文件——在 Linux 笔记本上新加的账户、只存在于 Mac 上的客户配置文件。所以
**配置文件与账户** 会把文件里的配置文件加到你的配置文件里，而不是替换整个列表。
导入之前，这一项会列出每个配置文件以及它将会怎样：

| 标签 | 含义 |
|-----|---------|
| **更新** | 两边都有这个配置文件：文件里的身份、AI 和配置文件图片替换你的，它的服务器加到你的服务器里 |
| **新增** | 只有文件里有：加在你的配置文件后面 |
| **保留** | 只有这台电脑有：原样保留 |

两个配置文件共享同一个 id 时就算“同一个”——每次安装的第一个配置文件都是如此。
没有 id 匹配时，就按名称匹配（忽略大小写和首尾空格），并且该配置文件保留
**这台电脑的 id**：绑定到它的仓库、当前激活的配置文件、它保存的凭据和配置文件图片都继续
关联着。激活的是哪个配置文件不会改变，**通用 AI** 也不会：这台电脑用来
回答的引擎和模型仍是它自己的。

**全部替换** 依然在，用于你想原样恢复的备份：只留下文件里的配置文件，只有这台
电脑才有的那些会以删除线标为 **已移除**。这时按下 **导入** 会再问一次，并点出
它们的名字——它们会连同保存的凭据和配置文件图片一起消失，而且无法撤销。选 **全部替换**
时，文件里激活的配置文件会成为当前激活的配置文件，文件里的通用 AI
也会替换这台电脑的通用 AI。

局限：匹配只按 id 或完全相同的名称——在一边改了名的配置文件会被当作新的，结果
两个都在。匹配上的配置文件会采用文件里的字段，但有三个例外，以免丢掉只有这台
电脑才有的东西：它的 GitHub Enterprise、GitLab 和 Bitbucket 服务器会**加到**
你的里面（两边都有的服务器以文件里的条目为准）；文件里留空的令牌会保留你的——但仅限
同一个实例，所以令牌绝不会被发往另一个 Forgejo、另一个 GitLab 签发方或另一个
Azure 组织；从这台机器的凭据助手借来的登录，仍然属于这台机器。

**默认勾选是根据你的磁盘做出的猜测。** 在显示对话框之前，Gitcito 会检查文件里的
仓库文件夹在这里是否存在。如果一个都不存在，说明文件来自另一台电脑：**仓库** 和
**程序** 初始不勾选，各自附上原因——程序的路径会列出来，让你看出它们属于别处。
如果存在，就是同一台电脑（比如恢复的备份），全部初始勾选，并有一条绿色提示说明。
完全没有仓库的文件则改为按程序路径判断：只有当每个路径在这里都存在时，**程序**
才会初始勾选。

如果检查本身失败了，就不做任何猜测：**仓库** 和 **程序** 初始不勾选、也不给结论，
一个 **重新检查** 按钮会再问一次磁盘，并且在检查成功之前 **仓库** 无法导入。其他
项可以。

**转换路径。** 在一个文件夹缺失的文件上勾选 **仓库**，就会展开一个 **转换路径**
框。左边是文件里这些仓库共同所在的文件夹（`/home/you/code`）；右边是这个文件夹在
这台电脑上的位置，根据你的主文件夹预先填好（`/Users/you/code`）。两边都可以编辑——
猜测可能是错的；Gitcito 找不到共同文件夹时，会把两边都留空让你填写。你输入时，
一个进度条会统计现在有多少仓库在这里找到了文件夹，并列出其中几个——绿色为已找到，
红色为仍缺失。替换时，仓库的别名、标签页图片和配置文件，以及它的笔记、Wiki 和
保险库条目都会一起带过去，什么都不用手动重新设置。

底部会做个总结——*导入 4 项中的 3 项 · 31 个文件夹*（扫描根目录和上一次克隆用的
文件夹也算在内，所以说的是文件夹而不是仓库）——在至少勾选一项之前，**导入**
保持不可用。

**转换什么都没找到时，导入同样不可用。** 勾选了 **仓库**，而新前缀下一个文件夹
都没找到，此时导入会让你的仓库列表变空；请修正路径或取消勾选这一项。

转换的局限：

- 它只是**把一个前缀换成另一个**。在文件里位于其他文件夹下、或者在这里摆放方式
  不同的仓库，都找不到；没有逐个仓库的映射。
- 转换生效时，**只导入转换后有文件夹的仓库**。其余的被略过——不会作为失效的标签页
  加进来——对话框会告诉你有多少个。
- 程序永远不会转换：`/usr/bin/code` 在另一个系统上没有可靠的对应物。让这一项保持
  不勾选，然后在设置里选择它们。
- 清空任意一个前缀，就会按文件里原样的路径导入。

**导入进行中** 对话框无法关闭。如果后面的某一步失败了——仓库笔记、保险库、配置文件图片——
对话框会保持打开，指出是哪一步，**继续导入** 会从那里接着做，不会重写之前的步骤。

### 文件中的凭据

勾选了该选项导出的文件会带有凭据。合并配置文件时总是**添加**凭据：文件里的凭据
归到匹配的配置文件下，替换同一账户的凭据，其他所有已保存的凭据都保留——清掉它们
就和保留你的配置文件相矛盾了。当配置文件选的是 **全部替换** 时，这样的文件还会在
**配置文件与账户** 正下方显示这个选择：

| 选择 | 你已保存的凭据 |
|--------|------------------------|
| **添加到我的** | 文件里的凭据被添加，替换同一账户的凭据；其他的全部保留 |
| **全部替换** | 变得和文件里完全一致——文件里没有的每个已保存令牌和 API 密钥都会被删除 |

这个选择随配置文件一起生效：**配置文件与账户** 未勾选时，不会导入或删除任何凭据。
未勾选该选项导出的文件，不管你勾什么，都没有凭据可提供。按下 **导入** 时，**全部
替换** 会再问一次，说明文件里没有的每个已保存令牌和 API 密钥都将被删除；在那里
**取消** 会让对话框保持原样。

**全部替换需要钥匙串。** 钥匙串关闭或不可用时，旧令牌会留在加密存储里，并在下次
启动时回来，所以 Gitcito 会拒绝：它会说明原因，什么都不导入。已保存的令牌无法读取
期间（见上文）也是如此：一旦能读取，它们就会回来。**添加到我的** 依然可用，并在本次会话中
保留文件里的令牌。

**局限：** 凭据属于某个配置文件。被导入移除的配置文件，无论你选哪一项，都会带走它
保存的令牌。

### 用密码保护导出

勾选了凭据的导出，对捡到文件的人来说就和令牌本身一样有价值——同步文件夹、忘在某处的 U 盘、
邮件附件。导出对话框中的 **用密码保护** 会用与[安全分享](secure-share.md)相同的加密方式
（scrypt 派生的密钥和 AES-256-GCM）加密文件，没有密码就读不出其中任何内容——甚至读不出它
是否带有凭据。

这是可选的，勾不勾凭据都能用，而且密码没有最小长度。你要输入两次，并勾选表示你明白密码
无法找回；导入这个文件时会要求输入密码——在设置中是一个对话框，首次运行时则在欢迎步骤
里——输错了会再问一次。

![设置 → 数据 → 导出：用密码保护的文件，已确认无法找回的警告](../../screenshots/settings-export-password.webp)

| | 无密码 | 有密码 |
|---|---|---|
| **谁能读取** | 任何拿到文件的人 | 只有知道密码的人 |
| **改动一个字节** | 照常读取 | 像密码错误一样被拒绝 |
| **可在哪里打开** | 任何版本 | 认识加密格式的版本 |

**无法找回。** 密码不保存在任何地方——既不在文件里，也不在这台机器上——也没有服务器可问。
忘了它，文件就丢了；请从仍保有这些设置的机器上重新导出。

局限：旧版本打不开加密的导出，而且它自己也不知道——它会报告设置已导入，却什么都没改。请用
会询问密码的版本导入受保护的文件。对拿到文件又有时间猜测的人来说，短密码依然很弱；scrypt
密钥让每次尝试变慢，但并非不可能。密码保护的是文件，而不是正在运行的应用：为导出收集凭据
时，它们会像以往一样在内存中解密。

## 设置文件

设置文件和加密的令牌存储都是整体写入的：先在旁边写一个只有所有者能读的新文件，再替换过去，
所以崩溃或同时发生的两次保存都不会留下半个文件。如果设置文件是指向别处的符号链接（比如一个
dotfiles 仓库），写入会去往链接的目标，链接本身保持不变。Gitcito 从不替换这个链接。指向
尚不存在的文件的链接会穿过它写入，从而创建该文件——前提是它的文件夹存在。如果连文件夹也
不在，保存就会失败，并只用一条消息说明：链接和它指向的地方都不会被改动，这期间做的修改只
保留到 Gitcito 关闭。恢复那个文件夹，或让链接指向一个存在的位置，下次保存就能成功。

旧版本留在设置文件里的明文令牌绝不会因为一次保存而丢失：它们会留在文件中，直到 Gitcito 把
它们载入加密存储（打开设置就会这样做），除非你自己清除了其中某个。

只有两件事会写入它：保存你的设置，以及 Gitcito 载入设置（启动时或打开设置时）——旧的明文令牌
正是在这时被移入加密存储，或者含密码的服务器地址被清理。没人要求的查找——fetch 解析它的
令牌、AI 调用查找它的密钥、一张配置文件图片——只会读取，所以永远不会覆盖到一次保存之上。
在设置至少载入过一次之前，保存也会被拒绝：在那之前，应用手里只有默认值。

在设置文件里仍有明文令牌的 **旧安装上的代价**：在设置被打开一次之前（或应用重启并载入它们
之前），每次需要令牌的查找都会重新解密存储，需要已保存令牌的配置文件图片会等待。查找不会
移动任何东西，所以这期间你清除的令牌会保持清除。

存在但无法解析的文件（一次失败的手动编辑、一块损坏的磁盘）**绝不会**被默认值替换：Gitcito
会说明文件已损坏，并且不再继续启动——在那个界面上，任何快捷键或菜单命令都无法覆盖保存它。

![设置文件损坏时的启动界面，带有 重试 和 将损坏的文件移到一旁并重新开始 按钮](../../screenshots/settings-damaged.webp)

你可以修复数据文件夹中的 `gitcito-settings.json` 后按 **重试**，或者按 **将损坏的文件移到
一旁并重新开始**：文件会被重命名为 `gitcito-settings.json.corrupt-<date>`（绝不删除，所以你
仍能从中恢复内容），加密令牌存储的副本会保存在它旁边，Gitcito 会像首次运行一样启动，并附上
一条说明文件去了哪里的提示。对于符号链接的设置文件，被重命名的是链接的目标，因此损坏的副本
会留在你的 dotfiles 中，就在首次保存随后穿过链接写入的新设置文件旁边。副本会最先生成：如果
写不进去，就什么都不移动，界面会说明这一点并显示要检查的数据文件夹——因为没有副本就重新
开始，会让你保存的第一个令牌删掉旧配置文件的令牌。修好阻止写入该文件夹的问题（权限、磁盘
已满）后按 **重试**。

如果文件在 Gitcito 运行时坏掉（在它底下被手动编辑），保存会停止，Gitcito 会提示一次：重启
之前无法保存设置，这期间做的修改会丢失。

文件存在但一时 *读不了*——被另一个程序（例如杀毒扫描）占用——会重试大约两秒。如果仍然
失败，或因其他原因载入失败，Gitcito 会说明它无法启动、文件没有被改动，并提供 **重试**；
它不会说文件已损坏。

### 已知局限

它们都需要不寻常的条件，列在这里是为了不让任何人感到意外：

- **设置文件里仍有令牌的非常旧的安装。** 如果在已保存的令牌解锁后关闭钥匙串，或者在某个 AI
  密钥仍以旧的明文格式保存时拒绝钥匙串，那份明文副本可能在下次保存时丢失，重启后令牌就没了。
  从这样的版本升级后，请在钥匙串开启的情况下打开一次设置，令牌就会永久移入加密存储。
- **同一窗口中保存与失败的重新载入交错。** 在一次保存中输入的令牌，如果这次保存抢在一次
  随后失败的重新载入之前完成，那么在设置再次载入前无法从该窗口清除；请重新打开设置并清除它。
- **文件夹缺失的符号链接设置文件。** 令牌存储会在设置文件写入失败之前写入，所以在文件夹回来
  之前，两者是不同步的。恢复那个文件夹（挂载磁盘、克隆 dotfiles）后再保存一次。

## Git 运行期间配置文件的令牌

当一个[配置文件](profiles.md)用它的令牌为 clone、fetch、pull 或 push 登录时，令牌不会进入
任何其他程序能读到的地方：不进 `.git/config`，不进命令行（任何本地用户都能读取进程列表），
也不进 git 命令的 **环境**——git 启动的每个钩子、过滤器和 LFS 进程都会继承这个环境，husky 或
lefthook 脚本运行的每个 npm 包也一样。

取而代之的是，Gitcito 为每次操作打开一个自己的私有端点——一个只有你的用户能进入的文件夹中的
套接字（在 Windows 上是随机命名的命名管道）——并只为那一台服务器注册一个凭据助手。当 git
请求登录时，助手会连接上来，用一个专为这次操作生成的随机代码证明它属于这次操作，说明 git 在
询问哪个主机和仓库，然后收到登录信息。端点会响应这次操作的每个请求——git 可能会多次询问：
为了 LFS、在重定向之后、为它启动的每个进程——并在 git 退出时关闭并删除。转储自身环境的钩子
找到的是代码，而不是令牌。

它仍然做不到的：

- **操作运行期间，钩子仍然可以询问。** 那个代码在 git 的环境里，因为助手是 git 启动的程序，
  而 git 会把同样的环境交给它启动的每个程序。一个按助手协议编写的钩子，可以在 git 退出之前
  用这个代码请求登录——git-lfs 的 `pre-push` 钩子正是这样拿到登录信息的。这比放在变量里的
  令牌小得多——不会有东西无意中读到它，转储或崩溃报告里只会出现一个 git 退出后就没用的
  代码——但它仍是一个缺口。
- **它只为打开它的那台服务器应答。** 端点会拒绝任何其他主机、明文 `http` 请求、服务器基础
  路径之外的路径，以及嵌套在其下的服务器（与根路径上的 GitLab 并存、位于 `/bitbucket` 的
  Data Center）——即使代码正确也一样。推送到多个 URL 时，每台服务器各有一个端点，每个只持有
  该服务器的登录信息。在内部嵌套了另一台服务器的服务器下，嵌套服务器的代理可能路由给自己的
  路径也会被拒绝：路径中的任何 `;`（Tomcat 会丢弃 `;params`）、以点结尾的路径段，以及大小写
  不同或作为前缀出现的嵌套基础路径名（`/Bitbucket/`、`/bitbucketx/`）——所以外层服务器上名字
  以嵌套服务器路径开头的群组，也拿不到它的令牌。
- **例外挡不住服务器自己那一侧的重定向。** 检查针对的是 git 询问的路径。如果外层服务器自己
  把请求重定向到嵌套服务器的路径，或者在 git 发出登录信息后由代理把它改写到那里，任何客户端
  都看不到。
- **通过 `git -c` 继承来的登录会被搁置一旁。** 通过 `GIT_CONFIG_PARAMETERS` 传下来的凭据助手
  （或可能添加助手的 `include`）——应用是从 git 别名或由另一个 git 启动的——在操作期间会被
  移除，因此它既不会被交给配置文件的令牌去保存，也不会以无人的名义被询问。其他所有继承来的
  `-c` 设置都会保留。
- **服务器地址必须按 git 读取的方式书写。** Gitcito 按标准 URL 规则命名服务器，git 按它自己的
  规则：国际化域名（`bücher.example`）、数字简写（`127.1`、`0x7f.0.0.1`）、压缩或映射的 IPv6
  地址，或主机中的编码字符，对两者来说是不同的服务器。涉及配置文件时，这样的地址会被拒绝并
  给出提示，而不是交给机器自己的登录。大小写和显式写出的默认端口（`:443`）都没有问题。
- **早于 2.26 的 Git** 只把凭据条目匹配到精确地址，而不是服务器基础路径下的所有内容。以无人
  的名义询问时，应用会在那一条命令期间关闭整个主机的助手；用令牌登录本来就需要 git 2.31。
- **不要运行你不信任的钩子**，即使已经用配置文件登录也一样。刚克隆的仓库可能通过 husky 这类
  在 `npm install` 时安装钩子的工具带来钩子；无论从 Gitcito 还是从终端，git 都会运行
  `.git/hooks` 里的东西，而钩子能做的远比读取一个令牌更糟。
- **缩小令牌的权限范围。** 一个只能写入你正在处理的仓库的令牌，对任何拿到它的人来说价值都
  小得多。
- **SSH 远程不受影响**——不涉及令牌；改由 [SSH 代理](ssh-keys.md)应答。

## 安全地分享

[安全分享](secure-share.md)可以把设置、保险库条目或整个工作区导出成一个**加密包**
——只有你勾选了那个选项，机密才会被包含进去。

## 反馈问题

错误上的 **反馈问题** 会打开一个预先填好的 GitHub issue——而打开它这一步就已经把文本发送给
GitHub 了，在你决定发布之前。所以消息会先被清理：写在 URL 里的凭据、令牌、你的主文件夹（以及
其中的用户名）、私有服务器和仓库路径、仓库所绑定的配置文件名称、电子邮件和 IP 地址都会被
替换。`github.com` 之类的公共主机会保留，文件名和 git 自己的消息也会保留。

**局限：** 句子中单独出现的服务器名靠形状识别——带点、小写。单个词的主机名（`gitserver`）
只有在 Gitcito 自己写的消息中才会被识别，而顶级域名拼写得像文件扩展名（`.sh`、`.md`）的
服务器会被当作文件名保留。无论如何，发布前请读一遍这个 issue：清理识别的是已知的形状，而不是
一切私密内容。

## 留在磁盘上的东西

设置文件、操作日志、头像缓存和加密的令牌存储只有你的账户能读取（在 macOS 和 Linux 上）。带有
`user:password@` 或 `?token=` 保存的服务器地址——来自一次导入或旧版本——在被读取、导入或保存
时会去掉这部分。提交头像缓存不保存电子邮件地址，只保存按每次安装加盐的哈希。

这些文件每个都是整体写入的：先在旁边写一个新文件，再替换过去，所以崩溃或同时发生的两次保存
都不会留下半个文件——否则 Gitcito 只能把它当作无法读取。令牌存储的备份只有在其中每个令牌也都
在当前存储中时才会提前删除；其他备份都保留 30 天。

## Linux 软件包：沙箱与 AppArmor

Chromium 的沙箱需要非特权用户命名空间。Ubuntu 24.04 及更高版本会拒绝任何没有允许它的
AppArmor 配置的程序使用它，而两个 Linux 软件包的处理方式不同：

| 软件包 | 会发生什么 |
|---------|--------------|
| `.deb` | 安装 `/etc/apparmor.d/gitcito`，这是一个为 `/opt/GitHuttBr/gitcito` 准备、允许用户命名空间的配置。应用在沙箱中运行。 |
| AppImage | 没有配置。它的启动器会尝试 `unshare -Ur true`，失败时就用 `--no-sandbox` 启动应用——在 Ubuntu 24.04+ 上每次启动都是如此。发生这种情况时，Gitcito 会在控制台输出中打印一条警告。 |

要在沙箱中运行 AppImage，请改装 `.deb`，或者给 AppImage 一个允许 `userns` 的专属 AppArmor
配置（或者在整台机器上设置 `sysctl kernel.apparmor_restrict_unprivileged_userns=0`，这会对
所有程序关闭该限制）。

**`.deb` 配置的局限。** 它是允许 `userns` 的 `flags=(unconfined)`，并附着在可执行文件的路径
上。同一个可执行文件以 `ELECTRON_RUN_AS_NODE=1` 启动时，也会作为普通 Node 运行——`gitcito`
命令、内置的 diff 转换器和 Gitcito 的凭据助手都是这样工作的，所以这个开关无法关闭，否则会弄坏
它们。合起来，这意味着任何本地程序都可以把 Gitcito 的可执行文件当作一个被允许创建用户命名
空间的 Node 解释器来用——与通过其他带配置的程序绕过 Ubuntu 限制的已知手法属于同一类缺口。它
不会让任何人获得超出自己账户的权限；它削弱的是 Ubuntu 额外加上的一层内核加固。AppArmor 无法
区分同一个可执行文件的两种模式，所以只要 CLI 还共用它，就不可能有更窄的配置；为 CLI 单独提供
一个辅助二进制文件已在路线图上。不想要这一点的管理员可以在 `/etc/apparmor.d/local/gitcito`
中添加一条拒绝规则，代价是失去沙箱。
