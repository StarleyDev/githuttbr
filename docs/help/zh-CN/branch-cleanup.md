# 分支清理

你检出的每个拉取请求都会留下一个本地分支。PR 被合并，服务器删除了它的分支，本地的那个却
留了下来——永远留着。评审几百次之后，分支列表里大多是死分支，要找到还活着的，就得滚过
所有这些。

分支清理会列出那些工作已经安全地存在于别处的本地分支，勾选不会丢失任何东西的那些，并在一个
可以撤销的步骤中删除它们。“别处”指的是你上次获取时的远程跟踪分支，以及默认分支。

![清理对话框：已消失、已合并和已压缩合并的分支被勾选，只存在于此的工作被保留](../../screenshots/branch-cleanup.webp)

## 如何使用

1. 工具 → **清理本地分支…**（或 <kbd>⌘K</kbd>）。
2. 如果上次获取已经很久了，先按 **拉取并清理**。在执行带 prune 的获取之前，服务器已删除的
   分支在这里看起来仍然活着。
3. 如果你的团队用压缩方式合并拉取请求，按 **检查压缩合并**（见下文）。
4. 检查勾选，然后点 **删除**。只有一次确认，说明有多少分支会被删除，并列出每个含有别处
   找不到的提交的分支。

删除是一次操作，只有一条撤销记录：**撤销** 会在每个被删分支原来指向的那个提交上重新创建
它，并恢复其上游（`branch.<name>.remote` 和 `.merge`）。如果此后在另一个提交上出现了同名
分支——同一个 PR 又被检出——撤销不会动它，而是把被删的那个恢复在它旁边，命名为
`<name>-restored-<short sha>`，并会说明。

成功消息和撤销记录会列出每个分支及其原来指向的提交（`feature/x (was abc1234)`），格式与
`git branch -D` 的输出相同：撤销历史只在应用打开期间存在，而这一行足以手动重建分支。

## 分支为何被列出

| 标签 | 含义 |
|---|---|
| **已消失** | 该分支跟踪的上游已被服务器删除——这是拉取请求合并后常见的痕迹。 |
| **已合并** | 它上面的每个提交都已在默认分支中。工具提示会说明是哪个副本包含它——只有你的本地副本包含时显示 `main (local, not pushed)`。 |
| **已压缩合并** | 由 **检查压缩合并** 找到：它的内容在默认分支中，它的各个提交却不在。 |
| **陈旧** | 在你选定的月数内（默认 3 个月）没有提交。只有勾选 **同时列出陈旧分支** 时才会列出。 |
| **N 个提交只存在于此** | 不在任何远程跟踪分支上、也不在默认分支中的提交。删除分支会把它们一起删掉。 |
| **尚无提交** | 它恰好指向默认分支的顶端——可能是创建后从未使用。 |

“已合并”既相对于默认分支的远程副本（`origin/main`）衡量，也相对于你的本地副本衡量——一个
一个月没人拉取的本地 `main` 也藏不住此后的合并。

## 压缩合并

压缩合并会把拉取请求的改动作为一个新提交放到 `main` 上；分支自己的提交永远不会到达。在 git
看来，这样的分支像是被放弃的工作：**已消失**，并带有 *N 个提交只存在于此*。

当列出了带有自己提交的已消失分支时，**检查压缩合并** 会问另一个问题：把这个分支合并进
`main` 会改变什么吗？它会为所有这些分支在内存中运行一次 `git merge-tree`——不检出，也不动
索引——合并后 `main` 的树完全不变的分支会得到 **已压缩合并** 标签，并像已合并的分支一样被
勾选。确认会说明它们的内容在 `main` 中，而提交不在。

删除的那一刻，检查会在锁的保护下再执行一次：不再通过检查的分支会被拒绝，而不是被删除。

## 哪些会被勾选，哪些永远不会

打开对话框时勾选的是：**已消失或已合并** 且 **没有自己提交** 的分支——检查之后还包括已
压缩合并的。**选择已消失 + 已合并** 会恢复这个选择。

永远不会替你勾选、也永远不会被 **全选当前显示** 选中的：带有只存在于此的提交的分支。请逐行
勾选；确认随即变成红色，并列出它及其提交数。只是陈旧的分支，以及位于默认分支顶端的分支，
也不会被勾选。当选择中包含列表未显示的行——被筛选隐藏，或排在前 400 行之后——确认会说明有
多少。

删除时，每个分支只接受确认中显示的那个确切数量的独有提交。如果那时某个分支的提交更多了——
或者在 **重做** 时，它在撤销之后又多了一些（比如 prune 删掉了远程副本）——它会被拒绝并保留，
重做会如实报告，而不是声称成功。

永远不会列出、即使要求也会被删除操作拒绝的：

- 当前分支；
- 在任意工作树中检出的分支，或正在某个工作树中变基的分支；
- 默认分支；
- [受保护的分支](repo-settings.md)，包括来自 [仓库配置](repo-config.md) 的 `release/*`
  这类模式。

远程上什么都不会改变。这只删除本地分支。

## 限制

- **在你检查之前，压缩合并对 git 是不可见的。** 不执行 **检查压缩合并**，压缩合并的分支
  会显示为 **已消失**，带有 *N 个提交只存在于此*，且不会被勾选。
- **压缩检查可能漏判。** 它回答的是“这些内容已经在 `main` 里了吗？”。如果 `main` 后来又
  改了同样的行，或者合并时编辑过压缩提交，合并就会改变一些东西，分支便保持未勾选。它永远
  不会以丢失内容的方式错误地回答“是”：按定义，内容就在 `main` 里。和
  [冲突雷达](conflict-radar.md) 一样，它会写入由 `git gc` 清理的松散树对象。
- **未获取的远程是过时的。** “已消失”来自上次获取。不执行 **拉取并清理**，一小时前在服务器
  上删除的分支看起来仍然活着，刚完成的合并也还不在 `origin/main` 中。
- **陈旧只是一个日期。** 三个月没动静并不能说明工作是否安全，所以陈旧的行永远不会被勾选。
- **“别处”是上次获取时的远程跟踪引用**，而不是此刻的服务器——也不包括标签。只被某个标签
  保留的提交算作独有，而位于别人远程分支上的提交不算。
- 独有提交的计数到 500 就停止，显示 *500+*。确认中的总数是下限——*至少 N*——因为堆叠的分支
  会共享提交。
- 撤销会恢复分支及其上游，但不恢复它的 reflog 或其他 `branch.<name>.*` 设置。
- 列表很长时，对话框显示前 400 行；其余的可通过筛选找到。**选择已消失 + 已合并** 作用于
  每一行，无论是否显示。
