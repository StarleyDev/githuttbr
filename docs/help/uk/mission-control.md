# Центр керування

Двадцять репозиторіїв, і питання завжди те саме: який із них зараз мене потребує?

Центр керування відповідає на нього. Усі репозиторії **активного робочого
простору** на одному екрані, впорядковані за тим, що справді вимагає уваги:

1. **Заблоковані** — ребейз чи злиття, що зупинилися на півдорозі, конфлікти,
   репозиторій, який узагалі не читається.
2. **Потребують синхронізації** — спершу коміти, які треба забрати, потім ті,
   які треба відправити.
3. **У роботі** — незакомічена робота, невідстежувані файли.
4. **Чисті** — тихі, унизу, там, де їм і місце.

## Що каже рядок

Кожен рядок читається зліва направо, а стовпці вирівняні по всьому списку, тож
лічильники порівнюються, як у таблиці:

| Стовпець | Що показує |
|---|---|
| **Репозиторій** | Назва, група, гілка та її upstream — або **немає upstream** бурштиновим: таку гілку не надішлеш помилково, але вона й не синхронізується |
| **Останній коміт** | Тема й автор: чим репозиторій займався востаннє, без його відкриття |
| **Локально** | Конфлікти · ↓ до отримання · ↑ до надсилання · в індексі · змінені · невідстежувані · stash. Наведіть, щоб побачити, що рахує кожен |
| **Хостинг** | Відкриті запити на злиття — ті, що чекають на **ваше** рев’ю, бурштиновим — і CI для HEAD. Клацніть лічильник, щоб відкрити сторінку **Запити на злиття** цього репозиторію, або **CI**, щоб відкрити його запуски |
| **Реліз** | Найновіший тег, досяжний з HEAD, і скільки комітів з’явилося після нього — **актуально**, якщо жодного. Колір лічильника залежить від того, наскільки відстає реліз: сірий до 5 комітів, жовтий до 20, червоний далі, у чотирьох діапазонах, які можна змінити — разом із власними кольорами — в [**Налаштування → Теми → Кольори нотатки про реліз**](themes.md#кольори-нотатки-про-реліз) |
| **Активність** | Спарклайн комітів за 14 днів і їхня кількість |
| **Час** | Скільки минуло від останнього коміту й від останнього **fetch** |

Наведіть на значок стану, щоб побачити, чому рядок стоїть тут —
«до надсилання: 2 · без коміту: 1».

Вік fetch тут тому, що читання цієї сторінки ніколи не робить fetch: лічильник «до
отримання» свіжий лише настільки, наскільки свіжий останній fetch. Якщо гілка з
upstream не робила fetch день або довше, чи ніколи, вік стає бурштиновим — зробіть
fetch, перш ніж вірити нулю. Час бере сам git, тож `git fetch` у терміналі теж
рахується.

![Налаштування → Git і синхронізація: оновлення Mission Control поруч з автоматичним fetch](../../screenshots/settings-git-sync.webp)

У вузькому вікні лишаються всі стовпці, а таблиця прокручується вбік усередині
своєї рамки.

**Відкрити** в кінці рядка показує сам репозиторій — його граф, — навіть якщо його
вкладка востаннє показувала список запитів на злиття, відкритий лічильником PR.

Розгорніть рядок (шеврон або <kbd>space</kbd>), щоб побачити, які саме коміти
чекають на відправку і які файли брудні.

## Як працювати зі списком

- Пігулки статусу вгорі — це **фільтри**: клацніть «3 заблоковані», щоб побачити
  лише їх. **Відкритих PR: N** і **CI з помилкою: N** фільтрують так само, як і
  **PR чекають на ваше рев’ю: N** у рядку нижче.
- Сортуйте за **терміновістю**, **назвою** або **активністю**.
- **Позначте кілька репозиторіїв**, щоб зробити для них фетч, або підтягніть лише
  ті, що відстали (кнопка сама їх порахує).
- **Fetch застарілих: N** з’являється, коли гілки з upstream не робили fetch день або
  довше, і виконує fetch лише для них — тих, де «до отримання» може бути хибним.
- Поки панель відкрита, вона оновлюється кожні 30 секунд — це змінюється в
  **Налаштування → Git і синхронізація → Оновлення Mission Control**, щонайменше
  30 секунд. Поки сторінку закрито, нічого не виконується.

| Клавіша | Дія |
|---|---|
| <kbd>↑</kbd> <kbd>↓</kbd> або <kbd>j</kbd> <kbd>k</kbd> | Пройтися списком |
| <kbd>Enter</kbd> | Відкрити цей репозиторій |
| <kbd>f</kbd> / <kbd>p</kbd> | Зробити для нього фетч / пул |
| <kbd>space</kbd> | Розгорнути його |
| <kbd>/</kbd> | Перейти до фільтра |

## Це подання, а не вкладка

Перемикає його індикатор поруч із назвою робочого простору; клацання на будь-якій
вкладці повертає вас до роботи. Він ніколи не додає власної вкладки і належить
тому робочому простору, в якому ви є, — перемкніть робочий простір, і отримаєте
панель саме для нього.

Бік git — **локальний**: кілька команд git на репозиторій, без fetch. Стовпець
**Хостинг** — єдина частина, яка звертається до хоста. Він питає хост кожного
репозиторію про відкриті запити на злиття та CI для HEAD — від імені профілю
цього репозиторію і тихо: хост без токена чи прив’язки для цього профілю просто
нічого не показує, і вікно входу ніколи не відкривається. Репозиторій, уже
відкритий у вкладці, не коштує жодного запиту: бічна панель уже має його запити
на злиття.

Обмеження, щоб правильно читати цифри:

- Хости опитуються **не частіше ніж раз на 5 хвилин** для кожного репозиторію
  (раніше, якщо HEAD зсунувся або запуск CI ще триває), хоч би яким був інтервал
  оновлення, — ліміт API хоста спільний з рештою застосунку. **Оновити** питає
  знову одразу.
- Лічильник показує **30+**, коли перша сторінка від хоста прийшла повною; на
  сторінці списку є всі.
- Стовпець релізу — це найновіший тег, **досяжний з HEAD**, а не найновіший тег у
  репозиторії. Тег, створений на коміті, який уже є в HEAD, з’являється протягом
  двох хвилин.

Фетч завжди відбувається лише тоді, коли ви про це попросили.
