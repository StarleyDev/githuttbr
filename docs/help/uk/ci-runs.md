# Запуски CI

Ви зробили push і тепер чекаєте: перейти в браузер, знайти репозиторій, відкрити
Actions, знайти свій запуск, відкрити завдання, що почервоніло, прокрутити лог до
кінця. **Запуски CI** ставлять це коло поруч із кодом. Одна сторінка каже, як
останнім часом ішли справи в кожного workflow, перелічує запуски віддаленого
репозиторію від нових до старих і відкриває запуск, що впав, одразу на зламаному
тесті — з файлом і рядком, за одне клацання від редактора. Кнопки, щоб запустити
його знову або зупинити, — на картці.

Сторінка звертається до власного API хостингу з токеном, який ви вже дали
GitHuttBr. На вашій машині нічого не запускається — для цього є
[Локальний CI](local-ci.md).

## Як відкрити

**Інструменти → Запуски CI…** або *Запуски CI* у палітрі команд (⌘K). Сторінка
відкривається у вкладці репозиторію, як вікі та аналітика, і читає віддалений
репозиторій `origin` — або перший віддалений, якщо `origin` немає.

## Що показує сторінка

| Частина | Що це |
|---|---|
| **Картки workflow** | Одна картка на workflow: що його запускає, частка успішних серед останніх 10 завершених запусків (зелений від 90 %, бурштиновий від 70 %, червоний нижче), ці запуски кольоровими квадратиками — найстаріший ліворуч, тож найновіший стоїть поруч із «зараз», — середній час і або найдовше завдання, або підсумок останнього запуску. Клацніть картку, щоб перелічити лише запуски цього workflow; клацніть ще раз, щоб показати всі |
| **Усі гілки / поточна гілка** | Кожен запуск на віддаленому репозиторії або лише запуски гілки, на якій ви зараз |
| **З помилкою / Виконуються** | Швидкі фільтри з кількістю запусків, яку залишить кожен. Вони рахують те, що залишили інші фільтри, тож число — це саме те, що покаже клацання |
| **Фільтр** | Звужує завантажені запуски за заголовком, workflow, гілкою, автором, комітом або подією |
| **Картка запуску** | Заголовок коміту (або назва workflow), далі гілка, workflow і номер запуску, що його запустило (push, pull request, розклад, вручну…), хто запустив і коміт — клацніть коміт, щоб скопіювати його. Якщо запуск належить до pull request’а, **PR #n** відкриває сторінку цього pull request’а. Праворуч: у якому він стані, скільки тривав і як давно |
| **Запуск, що триває** | *Виконується · крок 3 з 5*, смуга прогресу й час на цей момент. Крок — це крок завдання, що виконується; на хостингу без кроків (GitLab, Forgejo) замість них рахуються завдання |
| **Тест, що впав** | Запуск, що впав, відкривається сам, найновіший, із тестом, який називає його лог: завдання, тест, перший рядок помилки та **шлях:рядок** — клацніть його або *Відкрити в редакторі*, щоб потрапити на цей рядок. Те саме читання, що й у [вкладці Перевірки](hosting.md#вкладка-перевірки) pull request’а |
| **Завдання** | Під ним кожне завдання зі станом і тривалістю, згруповане за стадіями там, де хостинг має стадії (GitLab, Azure). *Кроки й лог* відкриває кроки завдання та кінець його логу — у завдання, що впало, ця кнопка є завжди, в інших з’являється під час наведення на завдання |
| **Кроки** | Кожен крок завдання зі станом і тривалістю — їх повідомляють GitHub, Azure та Forgejo; у GitLab кроків немає |
| **Лог** | Кінець логу завершеного завдання, з кольорами. Завантажуються лише останні 512 КБ — там, де помилка, — і сторінка каже, якщо початок пропущено |

Поки на сторінці щось стоїть у черзі або виконується, список опитує хостинг кожні 15
секунд, а разом із ним — завдання відкритого запуску й кожного, що триває; звідти й
береться лічильник кроків, а тривалості цокають щосекунди. Якщо дві хвилини
відповідей не приносять нічого нового — наприклад, запуск чекає схвалення
деплою, — опитування сповільнюється до разу на хвилину й знову пришвидшується, щойно
щось зрушить. Список, де все завершилося, нічого не питає, доки ви не натиснете
«оновити», і нічого не запитується, поки вікно приховане.

Запуск, який хостинг надсилає без заголовка, — кожен пайплайн GitLab, запланована
збірка Azure — називається за темою свого коміту, якщо коміт є в графі: вона
безкоштовно читається з вашого локального репозиторію; інакше — за номером.

## Перезапуск, скасування, запуск

| Кнопка | Видно, коли | Що відбувається |
|---|---|---|
| **Перезапуск помилок** | Запуск упав або скасований | Знову запускаються лише завдання, що не пройшли |
| **Перезапуск** (↻) | Запуск завершено, на GitHub — на картці під час наведення | Знову запускається кожне завдання |
| **Відкрити у браузері** | Під час наведення на картку | Запуск на сайті хостингу |
| **Скасувати** | Запуск у черзі або виконується | Спершу питає: завдання, що тривають, перериваються, а їхня робота втрачається |
| **Запустити workflow** | Хостинг дозволяє запустити вручну | Виберіть workflow і гілку; він стартує так, ніби гілку запушили, і за кілька секунд з’являється у списку |

Що дозволяє кожен хостинг:

| Хостинг | Список і завдання | Кроки | Лог | Перезапуск усього | Перезапуск помилок | Скасування | Запуск вручну |
|---|---|---|---|---|---|---|---|
| **GitHub** (і Enterprise Server) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ — workflow потрібен тригер `workflow_dispatch` |
| **GitLab** (і self-managed) | ✓ — пайплайни, завдання за стадіями | — | ✓ | — | ✓ (*Retry*) | ✓ | ✓ — запускає `.gitlab-ci.yml` на гілці |
| **Azure DevOps** | ✓ — збірки, завдання за стадіями | ✓ (таски) | ✓ | — | ✓ | ✓ | ✓ — будь-яке визначення збірки репозиторію |
| **Forgejo / Gitea** | ✓ на серверах з API запусків Actions | ✓ | ✓ коли сервер віддає його токену | — | — | — | — |
| **Bitbucket** | — | | | | | | |

## Значки в графі

Той самий CI з’являється маленьким значком поруч із кожним комітом у графі:
зеленим, червоним або годинником, поки триває. Наведіть на нього, щоб побачити
завдання; клацніть, щоб відкрити сторінку хостингу. Значки беруться з:

| Хостинг | Джерело |
|---|---|
| GitHub | Check runs коміту — будь-який CI, що звітує в GitHub, не лише Actions |
| GitLab | Статуси коміту, куди входить кожне завдання пайплайна. Ручне завдання (наприклад, деплой) не залишає значок висіти на годиннику |
| Azure DevOps | 100 останніх збірок репозиторію, зіставлених за комітом |
| Forgejo / Gitea | Зведений статус коміту — Forgejo Actions і будь-який зовнішній CI |
| Bitbucket Data Center | Статуси збірок коміту |

Кожна відповідь запам’ятовується — включно з «тут немає CI», — і про коміт питають
знову, лише коли його відповідь могла змінитися: кожні 45 секунд, поки він
виконується, кожні 10 хвилин після завершення й дедалі рідше для коміту, у якого CI
ніколи не було. Так жвавий граф вкладається в погодинний ліміт хостингу.

## Обмеження

- **Картки знають лише запуски, які перелічила сторінка.** Це останні 50 запусків за
  чинного фільтра гілок — у рідко запускуваного workflow може бути менше десяти
  квадратиків, а перемикання на поточну гілку перераховує кожну картку. Найдовше
  завдання з’являється, коли сторінка прочитала завдання якогось завершеного запуску
  (досить того, що впав і який вона відкриває); доти картка каже, чим закінчився
  останній запуск.
- **Тест, що впав, читається з тексту логу.** Розпізнаються Vitest, Jest і pytest;
  будь-який інший ранер, помилка збірки або обрізаний лог показують лише список
  завдань. Шлях, який ранер записав поза робочою копією, відкрити не можна.
- **PR #n залежить від того, що повідомляє хостинг.** GitHub указує pull request лише
  для запусків із того самого репозиторію, не з форка; GitLab — для пайплайнів merge
  request’ів, Azure — для PR-збірок. У запусків Forgejo посилання немає.
- **Лог — це кінець, і лише після завершення завдання.** GitHub і Forgejo віддають
  лог завдання лише після його завершення; поки воно триває, сторінка показує, як
  просуваються його кроки, а не його вивід. GitLab і Azure віддають лог завдання,
  що триває, на цей момент — відкрийте його знову, щоб прочитати більше.
- **Токену потрібен доступ до CI.** Детальному (fine-grained) токену GitHub потрібен
  *Actions: read*, щоб перелічувати, і *Actions: write*, щоб перезапускати,
  скасовувати чи запускати; класичному — `repo`. Токену GitLab потрібен `read_api`,
  щоб перелічувати, і `api` для кнопок. Токену Azure потрібен *Build: read* (і
  *Build: read & execute* для кнопок); без нього сторінка й значки лишаються
  порожніми, а не видають помилку.
- **Значки Azure сягають лише 100 збірок назад.** У старішого коміту значка немає,
  хоча сторінка запусків CI і далі перелічує його збірку.
- **Перезапуск в Azure — це «повторити ті, що впали».** Він працює на YAML-пайплайнах
  зі стадіями; класичний пайплайн може відмовити, і сторінка показує відповідь
  хостингу.
- **Запуск workflow не питає його вхідних параметрів.** Workflow GitHub або пайплайн
  GitLab з обов’язковими параметрами без типового значення хостинг відхилить зі
  своїм повідомленням.
- **Forgejo — лише читання й лише на свіжих серверах.** У старих серверів Forgejo та
  Gitea немає API для списку запусків; сторінка каже, що хостинг не підтримується, а
  значки в графі й далі працюють через статуси комітів. Репозиторій, якого токен не
  бачить, показується як помилка доступу, а не як «не підтримується».
- **У Bitbucket немає сторінки запусків.** У Data Center CI — зовнішня система
  (Jenkins, Bamboo…), що повідомляє лише статус, — цей статус і є значком у графі.
  Pipelines на bitbucket.org не підтримуються.
- **Один віддалений репозиторій.** Сторінка читає `origin`; запуски на іншому
  віддаленому репозиторії форка не перелічуються.
