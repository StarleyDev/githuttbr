# Помощник учётных данных

GitHuttBr имеет дело с тремя разными видами секретов, и люди вполне обоснованно
считают, что это одно и то же:

| | Кто хранит |
|---|---|
| Токены API хостинга — пул-реквесты, задачи, проверки CI | GitHuttBr, в [связке ключей ОС](security.md) |
| Транспорт `git@…` | Ваш [SSH-ключ](ssh-keys.md), через системный ssh-агент |
| **Транспорт `https://`** | **Собственный credential helper git** |

Третий никто не считает функцией — ровно до того момента, когда он ломается, и
тогда рождаются две самые частые жалобы в git: *почему он опять у меня
спрашивает?* и *почему он всё ещё отправляет токен, который я отозвал?*

`⌘K` → **Помощник учётных данных**.

![Настроенный помощник, правила для отдельных хостов и предупреждение о файле в открытом виде](../../screenshots/credentials.webp)

## Что вы видите

Каждый настроенный `credential.helper` — в той области, откуда он пришёл:
`system`, `global`, затем этот репозиторий. **Помощники складываются**: git
опрашивает их по очереди, и помощник уровня репозитория не заменяет
глобальный.

Каждый проверяется на вашей машине:

| Метка | Что означает |
|------|-------|
| **готов** | Программа-помощник существует и запустится |
| **не установлен** | Настроен, но программы нет — каждый запрос сводится к тому, что вы снова набираете пароль руками |
| **пароли в обычном файле** | Помощник `store` (см. ниже) |

**Правила для конкретных хостов** перечисляют секции `credential.<url>.*`. Они
перекрывают общую настройку для тех URL, которым соответствуют, и обычно
именно они отвечают на вопрос «почему вот этот хост ведёт себя иначе».

## Как выбрать

| Помощник | Куда попадает пароль |
|--------|------------------------|
| `osxkeychain` | Связка ключей macOS — зашифровано, для каждого пользователя отдельно |
| `manager` | Git Credential Manager (Windows, кроссплатформенный) |
| `wincred` | Диспетчер учётных данных Windows |
| `libsecret` | Служба секретов Linux (GNOME Keyring, KWallet) |
| `cache` | Память, на 15 минут. На диск ничего не пишется |
| `store` | **Обычный файл в вашем домашнем каталоге. Без шифрования** |

GitHuttBr предлагает то, что действительно установлено на этой машине, отмечает
подходящий для вашей ОС и делает остальные неактивными.

**Область имеет значение.** *Для всех репозиториев* пишет в вашу глобальную
конфигурацию — почти всегда именно это вам и нужно; *только для этого
репозитория* пригодится для того редкого репозитория, который
аутентифицируется где-то ещё.

## Помощник `store` и файл `~/.git-credentials`

`store` пишет строки вида `https://user:password@host` в `~/.git-credentials`,
открытым текстом, вообще без какого-либо шифрования. Прочитать его может всё,
что запускается от вашего имени: скрипт, postinstall какой-нибудь зависимости,
что угодно.

Если такой файл существует, эта страница сообщает об этом и считает записи. Она
никогда их не показывает — весь смысл в счётчике, а прочитать содержимое, чтобы
его отобразить, было бы той же самой ошибкой.

Если вы нашли такой файл и не собирались его заводить: выберите здесь
настоящий помощник, затем удалите файл и один раз пройдите аутентификацию
заново.

## Как забыть сохранённые учётные данные

Когда токен отозван или заменён, помощник продолжает подсовывать старый, и
каждый пуш падает с 401, который ничего не объясняет. **Забыть** просит
настроенный помощник стереть свою запись для этого хоста — это
`git credential reject`, штатный документированный путь самого git.

По дороге ничего не читается: GitHuttBr никогда не вызывает `git credential
fill` — команду, которая напечатала бы действующий пароль в стандартный вывод.

Следующий пуш спросит вас один раз, и помощник сохранит новый ответ.

## Какую учётную запись использует пуш

Каждый URL для пуша проверяется отдельно. Scope на запись — это лишь возможность токена. Членство в репозитории, правила веток и право изменять конкретный файл не проверяются. Публичное чтение может работать без учётных данных.

![Проверка входа для удалённого репозитория](../../screenshots/remote-sign-in.webp)

Пуш может войти несколькими способами: токеном профиля, входом GitHub CLI,
привязанным к профилю, собственным helper’ом git, паролем, забытым в URL удалённого
репозитория, или SSH-ключом. Когда его отклоняют, сначала нужно понять, какой из них
использовался. Щёлкните правой кнопкой по удалённому репозиторию в боковой панели и
выберите **Проверить вход…** (или *Проверить вход для удалённых репозиториев* в
палитре команд). Проверка определяет учётные данные так же, как пуш, а затем
спрашивает о них хостинг:

| Показывает | Откуда это |
|----------|--------------------|
| Источник и [профиль](profiles.md) за ним | Тот же приоритет, что применяет пуш, — профиль, привязанный к репозиторию, иначе активный, иначе helper git |
| Учётную запись | Собственный ответ хостинга (`/user`), а не то, что было введено в настройках |
| Scopes | Заголовок `X-OAuth-Scopes` у GitHub; описание собственного токена у GitLab |
| Что они разрешают | Scopes токена, связанные с записью (`repo` на GitHub, `write_repository` на GitLab), а на GitHub — можно ли менять `.github/workflows` |

Она также отмечает учётные данные, которые хостинг отклоняет (истёкшие или
отозванные), привязанную учётную запись, из которой вышли, и пароль, хранящийся
открытым текстом в URL удалённого репозитория.

**Ограничения.** Детализированный токен GitHub не перечисляет свои права, поэтому
может ли он пушить, показывается как неизвестное, пока пуш не попробует. Forgejo
сообщает учётную запись, но не права токена. Azure DevOps и Bitbucket показываются
только с источником и профилем. Удалённые репозитории по SSH не проверяются, но
[SSH-ключи](ssh-keys.md) показывают, что держит агент. Проверка спрашивает helper git
молча: helper, которому нужно окно входа, считается пустым.

## Пароль, сохранённый в URL удалённого репозитория

Старый клон или URL, вставленный из вики, может нести учётные данные прямо в адресе:
`https://user:token@git.example.test/team/app.git`. **Пароль в URL всегда имеет
приоритет:** git отправляет его и не спрашивает ни одного helper’а — ни токен
[профиля](profiles.md) репозитория, ни GitHub CLI, ни собственное хранилище git. Пока
токен работает, это нормально, и GitHuttBr его не трогает: **он никогда не удаляет пароль
из URL, не спросив вас.** Как только токен отзывают или он истекает, каждый fetch, pull
и push этого одного репозитория падает с *Invalid username or token* или
*Authentication failed*, а другие репозитории того же профиля работают. И токен лежит
открытым текстом в `.git/config` репозитория.

![Удаление сохранённого токена из URL удалённого репозитория](../../screenshots/remote-url-token.webp)

GitHuttBr читает URL для fetch и push каждого удалённого репозитория и сообщает об этом в
трёх местах:

| Где | Что вы видите |
|-------|--------------|
| Неудачный fetch, pull или push | Ошибка объясняет, что URL удалённого репозитория содержит сохранённый пароль, с кнопкой **Удалить из URL…** |
| Боковая панель | Неброский значок ключа в строке удалённого репозитория: его URL содержит пароль, который важнее токена профиля. То же действие есть в его контекстном меню |
| **Проверить вход…** | Удалённый репозиторий показывает пароль как свой источник, с той же кнопкой |

Действие сначала спрашивает. Оно убирает пароль из всех URL этого удалённого
репозитория — URL для fetch и каждого URL для push, где он есть, — и не пишет ничего,
кроме `.git/config`. Что будет дальше, зависит от того, что ещё может войти:

| После удаления | Что используют fetch и push |
|---------------|-------------------------|
| У профиля репозитория есть токен или привязанная учётная запись для этого хостинга | Этот токен — подтверждение больше ничего не говорит |
| Токена профиля нет, но у собственного helper’а git есть вход для хостинга | Вход helper’а |
| Ни того ни другого | Ничего: fetch и push не работают, пока вы не добавите токен. Подтверждение говорит об этом заранее и предлагает **Сначала добавить токен**, что открывает Настройки → Интеграции |

Если действие запущено из неудачной операции, оно предлагает **Повторить**.

**Отмены нет — намеренно.** Отмена записала бы секрет обратно в файл открытым текстом,
а именно этому действие и мешает. Если старый токен ещё может работать, отзовите его на
сервере: его мог прочитать кто угодно, кто мог читать папку репозитория.

**Ограничения.**

- Имя пользователя тоже уходит (`https://git.example.test/…`), как при ручном
  `git remote set-url`; подтверждение говорит об этом. Серверу, которому оно нужно в
  URL, — токену Bitbucket Data Center без имени пользователя в профиле — нужно вернуть
  его через **Изменить удалённый репозиторий…**.
- Одно лишь имя пользователя (`https://user@host/…`) не отмечается: git всё равно
  спрашивает у helper’а пароль этого пользователя, так что ничего секретного не
  хранится.
- URL по SSH не трогаются: `git@host:…` и `ssh://git@host/…` называют логин, который
  использует ssh, а не учётные данные.
- Префикс удалённого helper’а (`persistent-https::https://…`, `gcrypt::…`)
  сохраняется; URL после него читается и очищается, как любой другой.
- **Неоднозначные URL не предлагаются к очистке.** Когда разборщики расходятся в том,
  где начинается хост, — `@` после `?` или `#` в адресе или пароль с незакодированным
  `/`, — разрез не по тому `@` направил бы удалённый репозиторий на другой сервер. Такой
  URL показывается только скрытым, а значок ключа открывает **Изменить удалённый
  репозиторий…**, чтобы вы исправили его вручную.
- Читается и меняется только `.git/config`. URL, переписанный правилом
  `url.<base>.insteadOf`, или удалённый репозиторий, заданный в вашей глобальной
  конфигурации, не проверяется — и переименование удалённого репозитория никогда не
  копирует в конфигурацию репозитория пароль, который добавляет правило `insteadOf`.
- Пароль никогда не покидает основной процесс: URL удалённых репозиториев попадают в
  окно, меню копирования URL и диалог изменения без него. Сохранение диалога изменения
  с показанным URL ничего не меняет и сохраняет пароль; **изменение хоста или пути его
  убирает**, так как введённый URL записывается как есть. Только это действие удаляет
  пароль, сохраняя адрес.

## Ограничения, о которых стоит знать

- **Это хранилище git, а не GitHuttBr.** Меняя его, вы меняете и поведение своего
  терминала — в этом и смысл, но знать об этом стоит заранее.
- **Помощники системного уровня показываются, но не редактируются.** Они живут
  в конфигурации, писать в которую может только администратор.
- **GitHuttBr не может перечислить содержимое помощника.** Ни один API учётных
  данных не отдаёт этого, не выдав сами секреты, поэтому диалог сообщает
  конфигурацию и стирает записи по запросу — и ничего больше.
- **Токен, который вы отдали GitHuttBr, — это отдельная история.** Отзыв одного
  не затрагивает другой; про сторону связки ключей см.
  [безопасность](security.md).
- **Токен профиля не попадает в окружение хуков репозитория.** Хук видит только код
  для частной точки доступа, действующий, пока идёт эта команда git, — достаточно для
  хука, который спрашивает намеренно, как это делает git-lfs. См.
  [токен профиля, пока работает git](security.md#токен-профиля-пока-работает-git).
