# Запуски CI

Вы сделали push и теперь ждёте: переключиться в браузер, найти репозиторий, открыть
Actions, найти свой запуск, открыть задачу, которая покраснела, прокрутить лог до
конца. **Запуски CI** ставят этот круг рядом с кодом. Одна страница говорит, как в
последнее время шли дела у каждого workflow, перечисляет запуски на удалённом
репозитории от новых к старым и открывает упавший запуск сразу на сломавшемся
тесте — с файлом и строкой, в одном щелчке от редактора. Кнопки, чтобы запустить его
снова или остановить, — на карточке.

Страница обращается к собственному API хостинга с токеном, который вы уже дали
GitHuttBr. На вашей машине ничего не запускается — для этого есть
[Локальный CI](local-ci.md).

![Страница запусков CI: карточка на каждый workflow с его последними запусками, фильтры «С ошибкой» и «Выполняются», прогресс идущего запуска и упавший запуск, открытый на сломавшемся тесте и его задачах](../../screenshots/ci-runs.webp)

## Как открыть

**Инструменты → Запуски CI…** или *Запуски CI* в палитре команд (⌘K). Страница
открывается во вкладке репозитория, как вики и аналитика, и читает удалённый
репозиторий `origin` — или первый удалённый, если `origin` нет.

## Что показывает страница

| Часть | Что это |
|---|---|
| **Карточки workflow** | Одна карточка на workflow: что его запускает, доля успешных среди последних 10 завершённых запусков (зелёный от 90 %, янтарный от 70 %, красный ниже), эти запуски цветными квадратиками — самый старый слева, так что самый новый стоит рядом с «сейчас», — среднее время и либо самая долгая задача, либо итог последнего запуска. Щёлкните карточку, чтобы перечислить только запуски этого workflow; щёлкните ещё раз, чтобы показать все |
| **Все ветки / текущая ветка** | Каждый запуск на удалённом репозитории или только запуски ветки, на которой вы сейчас |
| **С ошибкой / Выполняются** | Быстрые фильтры с числом запусков, которое оставит каждый. Они считают то, что оставили другие фильтры, так что число — это ровно то, что покажет щелчок |
| **Фильтр** | Сужает загруженные запуски по заголовку, workflow, ветке, автору, коммиту или событию |
| **Карточка запуска** | Заголовок коммита (или имя workflow), затем ветка, workflow и номер запуска, что его запустило (push, pull request, расписание, вручную…), кто запустил и коммит — щёлкните коммит, чтобы скопировать его. Если запуск относится к пул-реквесту, **PR #n** открывает страницу этого пул-реквеста. Справа: в каком он состоянии, сколько длился и как давно |
| **Идущий запуск** | *Выполняется · шаг 3 из 5*, полоса прогресса и время на данный момент. Шаг — это шаг выполняющейся задачи; на хостинге без шагов (GitLab, Forgejo) вместо них считаются задачи |
| **Упавший тест** | Упавший запуск открывается сам, самый новый, с тестом, который называет его лог: задача, тест, первая строка ошибки и **путь:строка** — щёлкните её или *Открыть в редакторе*, чтобы попасть на эту строку. То же чтение, что и во [вкладке Проверки](hosting.md#вкладка-проверки) пул-реквеста |
| **Задачи** | Под ним каждая задача с состоянием и длительностью, сгруппированная по стадиям там, где у хостинга есть стадии (GitLab, Azure). *Шаги и лог* открывает шаги задачи и конец её лога — у упавшей задачи эта кнопка есть всегда, у остальных появляется при наведении на задачу |
| **Шаги** | Каждый шаг задачи с состоянием и длительностью — их сообщают GitHub, Azure и Forgejo; у GitLab шагов нет |
| **Лог** | Конец лога завершённой задачи, с цветами. Загружаются только последние 512 КБ — там, где ошибка, — и страница говорит, если начало опущено |

Пока на странице что-то стоит в очереди или выполняется, список опрашивает хостинг
каждые 15 секунд, а вместе с ним — задачи открытого запуска и каждого идущего;
оттуда и берётся счётчик шагов, а длительности тикают каждую секунду. Если две
минуты ответов не приносят ничего нового — например, запуск ждёт одобрения
деплоя, — опрос замедляется до раза в минуту и снова ускоряется, как только что-то
сдвинется. Список, где всё завершилось, ничего не спрашивает, пока вы не нажмёте
«обновить», и ничего не запрашивается, пока окно скрыто.

Запуск, который хостинг присылает без заголовка, — каждый пайплайн GitLab,
плановая сборка Azure — называется по теме своего коммита, если коммит есть в
графе: она бесплатно читается из вашего локального репозитория; иначе — по номеру.

## Перезапуск, отмена, запуск

| Кнопка | Видна, когда | Что происходит |
|---|---|---|
| **Перезапуск упавших** | Запуск упал или отменён | Снова запускаются только задачи, которые не прошли |
| **Перезапуск** (↻) | Запуск завершён, на GitHub — на карточке при наведении | Снова запускается каждая задача |
| **Открыть в браузере** | При наведении на карточку | Запуск на сайте хостинга |
| **Отменить** | Запуск в очереди или выполняется | Сначала спрашивает: идущие задачи прерываются, а их работа теряется |
| **Запустить workflow** | Хостинг позволяет запустить вручную | Выберите workflow и ветку; он стартует так, будто ветку запушили, и через несколько секунд появляется в списке |

Что позволяет каждый хостинг:

| Хостинг | Список и задачи | Шаги | Лог | Перезапуск всего | Перезапуск упавших | Отмена | Запуск вручную |
|---|---|---|---|---|---|---|---|
| **GitHub** (и Enterprise Server) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ — у workflow должен быть триггер `workflow_dispatch` |
| **GitLab** (и self-managed) | ✓ — пайплайны, задачи по стадиям | — | ✓ | — | ✓ (*Retry*) | ✓ | ✓ — запускает `.gitlab-ci.yml` на ветке |
| **Azure DevOps** | ✓ — сборки, задачи по стадиям | ✓ (таски) | ✓ | — | ✓ | ✓ | ✓ — любое определение сборки репозитория |
| **Forgejo / Gitea** | ✓ на серверах с API запусков Actions | ✓ | ✓ когда сервер отдаёт его токену | — | — | — | — |
| **Bitbucket** | — | | | | | | |

## Значки в графе

Тот же CI появляется маленьким значком рядом с каждым коммитом в графе: зелёным,
красным или часами, пока идёт. Наведите на него, чтобы увидеть задачи; щёлкните,
чтобы открыть страницу хостинга. Значки берутся из:

| Хостинг | Источник |
|---|---|
| GitHub | Check runs коммита — любой CI, который отчитывается в GitHub, не только Actions |
| GitLab | Статусы коммита, куда входит каждая задача пайплайна. Ручная задача (например, деплой) не оставляет значок висеть на часах |
| Azure DevOps | 100 последних сборок репозитория, сопоставленных по коммиту |
| Forgejo / Gitea | Сводный статус коммита — Forgejo Actions и любой внешний CI |
| Bitbucket Data Center | Статусы сборок коммита |

Каждый ответ запоминается — включая «здесь нет CI», — и о коммите спрашивают снова,
только когда его ответ мог измениться: каждые 45 секунд, пока он выполняется, каждые
10 минут после завершения и всё реже для коммита, у которого CI никогда не было. Так
оживлённый граф укладывается в часовой лимит хостинга.

## Ограничения

- **Карточки знают только запуски, которые перечислила страница.** Это последние 50
  запусков при действующем фильтре веток — у редко запускаемого workflow может быть
  меньше десяти квадратиков, а переключение на текущую ветку пересчитывает каждую
  карточку. Самая долгая задача появляется, когда страница прочитала задачи
  какого-нибудь завершённого запуска (достаточно упавшего, который она открывает);
  до тех пор карточка говорит, чем закончился последний запуск.
- **Упавший тест читается из текста лога.** Распознаются Vitest, Jest и pytest;
  любой другой раннер, ошибка сборки или обрезанный лог показывают только список
  задач. Путь, который раннер записал вне рабочей копии, открыть нельзя.
- **PR #n зависит от того, что сообщает хостинг.** GitHub указывает пул-реквест
  только для запусков из того же репозитория, не из форка; GitLab — для пайплайнов
  merge request'ов, Azure — для PR-сборок. У запусков Forgejo ссылки нет.
- **Лог — это конец, и только после завершения задачи.** GitHub и Forgejo отдают лог
  задачи только после её завершения; пока она идёт, страница показывает, как
  продвигаются её шаги, а не её вывод. GitLab и Azure отдают лог идущей задачи на
  данный момент — откройте его снова, чтобы прочитать больше.
- **Токену нужен доступ к CI.** Детальному (fine-grained) токену GitHub нужен
  *Actions: read*, чтобы перечислять, и *Actions: write*, чтобы перезапускать,
  отменять или запускать; классическому — `repo`. Токену GitLab нужен `read_api`,
  чтобы перечислять, и `api` для кнопок. Токену Azure нужен *Build: read* (и
  *Build: read & execute* для кнопок); без него страница и значки остаются пустыми,
  а не выдают ошибку.
- **Значки Azure дотягиваются только до 100 сборок назад.** У более старого коммита
  значка нет, хотя страница запусков CI по-прежнему перечисляет его сборку.
- **Перезапуск в Azure — это «повторить упавшие».** Он работает на YAML-пайплайнах со
  стадиями; классический пайплайн может отказать, и страница показывает ответ
  хостинга.
- **Запуск workflow не спрашивает его входные параметры.** Workflow GitHub или
  пайплайн GitLab с обязательными параметрами без значения по умолчанию хостинг
  отклонит со своим сообщением.
- **Forgejo — только чтение и только на свежих серверах.** У старых серверов Forgejo и
  Gitea нет API для списка запусков; страница говорит, что хостинг не
  поддерживается, а значки в графе продолжают работать через статусы коммитов.
  Репозиторий, который токен не видит, показывается как ошибка доступа, а не как «не
  поддерживается».
- **У Bitbucket нет страницы запусков.** В Data Center CI — внешняя система (Jenkins,
  Bamboo…), которая сообщает только статус, — этот статус и есть значок в графе.
  Pipelines на bitbucket.org не поддерживаются.
- **Один удалённый репозиторий.** Страница читает `origin`; запуски на другом
  удалённом репозитории форка не перечисляются.
