# 認証情報ヘルパー

GitHuttBr は 3 種類の秘密情報を扱っていて、多くの人はそれらを 1 つのものだと思っています。
無理もありません。

| | 保管しているのは |
|---|---|
| ホストの API トークン — プルリクエスト、イシュー、CI のチェック | GitHuttBr が [OS のキーチェーン](security.md) に |
| `git@…` の通信 | あなたの [SSH 鍵](ssh-keys.md)。システムの ssh エージェント経由 |
| **`https://` の通信** | **git 自身の認証情報ヘルパー** |

3 つめは、うまく行かなくなるまで誰も機能だとは思いません。そして壊れると、git で最も
よくある 2 つの不満を生みます。*なぜまた聞いてくるのか* と、*なぜ失効させたトークンを
まだ送っているのか* です。

`⌘K` → **認証情報ヘルパー**。

![設定されたヘルパー、ホストごとのルール、平文ファイルの警告](../../screenshots/credentials.webp)

## ここに映っているもの

設定されているすべての `credential.helper` が、その由来のスコープごとに並びます —
`system`、`global`、そしてこのリポジトリです。**ヘルパーは積み重なります**。git は順に
すべてへ尋ねるので、リポジトリ単位のものがグローバルのものを置き換えるわけではありません。

それぞれはあなたのマシンに照らして確認されます。

| 印 | 意味 |
|------|-------|
| **利用できます** | ヘルパーのプログラムが存在し、実行できます |
| **未インストール** | 設定はされているのにプログラムがありません — 毎回の入力要求はすべて手入力に落ちます |
| **パスワードを平文ファイルに保存** | `store` ヘルパーです（下記参照） |

**特定のホスト向けのルール** には `credential.<url>.*` のセクションが並びます。これらは
一致する URL について通常の設定より優先され、「なぜこのホストだけ挙動が違うのか」の答えは
たいていこれです。

## 選び方

| ヘルパー | パスワードの行き先 |
|--------|------------------------|
| `osxkeychain` | macOS のキーチェーン — 暗号化され、ユーザー単位 |
| `manager` | Git Credential Manager（Windows、クロスプラットフォーム） |
| `wincred` | Windows 資格情報マネージャー |
| `libsecret` | Linux のシークレットサービス（GNOME Keyring、KWallet） |
| `cache` | メモリ上に 15 分間。ディスクには何も残りません |
| `store` | **ホームディレクトリの平文ファイル。暗号化なし** |

GitHuttBr は、このマシンに実際に入っているものを提示し、あなたの OS に合うものに印を付け、
残りをグレーアウトします。

**スコープは重要です。** *すべてのリポジトリで（グローバル）* はグローバルの設定へ書き
込みます。ほとんどの場合こちらが望みのものです。*このリポジトリだけ* は、別のところへ
認証する変わったリポジトリのためのものです。

## `store` ヘルパーと `~/.git-credentials`

`store` は `https://user:password@host` という行を `~/.git-credentials` へ、平文で、
いっさいの暗号化なしに書き込みます。あなたの権限で動くものなら何でも読めます。
スクリプトも、依存パッケージの postinstall も、何でもです。

そのファイルがあれば、このページはその旨を伝え、件数を数えます。中身を表示することは
ありません — 件数こそが要点であり、表示のために内容を読むのは同じ過ちだからです。

見つかって、それが意図したものでなかったなら、ここで本物のヘルパーを選び、ファイルを
削除して、もう一度だけ認証し直してください。

## 保存された認証情報を忘れさせる

トークンを失効させたり入れ替えたりすると、ヘルパーは古いものを渡し続け、プッシュは
何も名指ししない 401 で失敗し続けます。**忘れさせる** は、そのホストの項目を消すよう
設定済みのヘルパーへ依頼します — `git credential reject`、git 自身が文書化している
経路です。

その途中で何かを読み出すことはありません。生のパスワードを標準出力へ書き出してしまう
コマンド `git credential fill` を、GitHuttBr が呼ぶことは決してありません。

次のプッシュで一度だけ尋ねられ、ヘルパーが新しい答えを保存します。

## プッシュが使うアカウント

プッシュ URL はそれぞれ個別に確認します。書き込みスコープはトークンの能力を示すだけです。リポジトリのメンバーシップ、ブランチのルール、特定のファイルを変更する権限は確認しません。公開リポジトリの読み取りは認証情報なしで成功することがあります。

![リモートのサインイン確認](../../screenshots/remote-sign-in.webp)

プッシュのサインイン方法はいくつかあります: プロファイルのトークン、プロファイルに
紐づけた GitHub CLI のログイン、git 自身のヘルパー、リモート URL に残ったパスワード、
SSH キー。拒否されたときは、まずどれが使われたかを知る必要があります。サイドバーの
リモートを右クリックして **サインインを確認…** を選びます（コマンドパレットなら
*リモートのサインインを確認*）。確認はプッシュと同じ方法で認証情報を決め、それについて
ホストに問い合わせます。

| 表示されるもの | 出どころ |
|----------|--------------------|
| ソースと、その背後の [プロファイル](profiles.md) | プッシュと同じ優先順位 — リポジトリに紐づけたプロファイル、なければアクティブなもの、なければ git のヘルパー |
| アカウント | ホスト自身の回答（`/user`）。設定に入力したものではありません |
| スコープ | GitHub の `X-OAuth-Scopes` ヘッダー。GitLab が自分のトークンについて返す説明 |
| 許可される操作 | 書き込みに関わるトークンのスコープ（GitHub の `repo`、GitLab の `write_repository`）と、GitHub では `.github/workflows` を変更できるか |

ホストが拒否する認証情報（期限切れや失効）、サインインが切れた紐づけアカウント、
リモート URL に平文で保存されたパスワードにも印を付けます。

**制限。** GitHub のきめ細かいトークンは権限を一覧にしないため、プッシュできるかは
プッシュを試すまで不明と表示されます。Forgejo はアカウントを返しますが、トークンの
権限は返しません。Azure DevOps と Bitbucket はソースとプロファイルだけを表示します。
SSH のリモートは確認しませんが、[SSH キー](ssh-keys.md) にエージェントが持っている
ものが一覧されます。確認では git のヘルパーに黙って問い合わせます: ログインウィンドウ
が必要なヘルパーは、何も持っていないものとみなします。

## リモート URL に保存されたパスワード

古いクローンや、Wiki から貼り付けた URL は、認証情報をアドレスの中に持っていることが
あります: `https://user:token@git.example.test/team/app.git`。**URL のパスワードは
常に優先されます:** git はそれを送り、どのヘルパーにも問い合わせません — リポジトリの
[プロファイル](profiles.md) のトークンにも、GitHub CLI にも、git 自身のストアにも。
トークンが有効な間は問題なく、GitHuttBr もそのままにします: **確認なしに URL から
パスワードを削除することはありません。** トークンが失効したり期限切れになったりすると、
そのリポジトリだけ fetch・pull・push のすべてが *Invalid username or token* や
*Authentication failed* で失敗し、同じプロファイルのほかのリポジトリは動きます。しかも
トークンはリポジトリの `.git/config` に平文で残っています。

![リモート URL から保存済みトークンを削除する](../../screenshots/remote-url-token.webp)

GitHuttBr は各リモートの fetch と push の URL を読み、3 か所でそれを伝えます。

| 場所 | 表示されるもの |
|-------|--------------|
| 失敗した fetch・pull・push | リモートの URL に保存済みのパスワードがあることをエラーが説明し、**URL から削除…** を示します |
| サイドバー | リモートの行に控えめな鍵アイコン: その URL には、プロファイルのトークンより優先されるパスワードが含まれています。同じ操作は右クリックメニューにもあります |
| **サインインを確認…** | リモートはパスワードをソースとして示し、同じボタンを表示します |

この操作は先に確認します。そのリモートのすべての URL — fetch の URL と、パスワードを
含む各 push の URL — からパスワードを取り除き、`.git/config` 以外には何も書き込み
ません。その後どうなるかは、ほかに何がサインインできるかで決まります。

| 削除後 | fetch と push が使うもの |
|---------------|-------------------------|
| リポジトリのプロファイルにそのホスト用のトークンか紐づけアカウントがある | そのトークン — 確認はそれ以上何も言いません |
| プロファイルのトークンはないが、git 自身のヘルパーにそのホストのログインがある | ヘルパーのログイン |
| どちらもない | 何もない: トークンを追加するまで fetch と push は失敗します。確認は先にそう伝え、設定 → 連携 を開く **先にトークンを追加** を示します |

失敗した操作から始めた場合は **再試行** を示します。

**元に戻す操作は意図的にありません。** 元に戻すと秘密をファイルに平文で書き戻すことに
なり、それこそがこの操作で防ぎたいことです。古いトークンがまだ使える可能性があるなら、
サーバーで失効させてください: リポジトリのフォルダーを読めるものなら何でも読めた状態
でした。

**制限。**

- ユーザー名も消えます（`https://git.example.test/…`）。`git remote set-url` を手で
  実行したときと同じで、確認がそう伝えます。URL にユーザー名が必要なサーバー —
  プロファイルにユーザー名のない Bitbucket Data Center のトークン — では、
  **リモートを編集…** で戻す必要があります。
- ユーザー名だけ（`https://user@host/…`）には印を付けません: git はそのユーザーの
  パスワードをヘルパーに尋ねるので、秘密は何も保存されていません。
- SSH の URL には触れません: `git@host:…` と `ssh://git@host/…` は ssh が使うログイン
  名を示すもので、認証情報ではありません。
- リモートヘルパーのプレフィックス（`persistent-https::https://…`、`gcrypt::…`）は
  そのまま残し、その後ろの URL をほかと同じように読んで取り除きます。
- **あいまいな URL は削除を提案しません。** ホストがどこから始まるかについて解析方法の
  間で解釈が分かれる場合 — アドレス中の `?` や `#` の後にある `@`、またはエンコード
  されていない `/` を含むパスワード — 間違った `@` で切るとリモートが別のサーバーを
  指してしまいます。そうした URL は伏せ字でのみ表示し、鍵アイコンは手で直せるよう
  **リモートを編集…** を開きます。
- 読み取りと変更の対象は `.git/config` だけです。`url.<base>.insteadOf` ルールで
  書き換えられた URL や、グローバル設定で定義されたリモートは調べません — また、
  リモートの名前を変えても、`insteadOf` ルールが加えるパスワードをリポジトリの設定に
  コピーすることはありません。
- パスワードはメインプロセスの外に出ません: リモート URL はウィンドウ、URL のコピー
  メニュー、編集ダイアログにパスワードなしで届きます。表示された URL のまま編集
  ダイアログを保存しても何も変わらず、パスワードは残ります。**ホストやパスを変えると
  パスワードは消えます**。入力した URL がそのまま書き込まれるためです。アドレスを
  保ったままパスワードを取り除けるのは、この操作だけです。

## 知っておくべき制限

- **これは git の保管先であって、GitHuttBr のものではありません。** ここを変えると
  ターミナルの挙動も変わります — それが狙いですが、変える前に知っておく価値があります。
- **システムスコープのヘルパーは表示されるだけで、編集できません。** 管理者だけが書ける
  設定ファイルにあるからです。
- **GitHuttBr はヘルパーが持っている中身を一覧できません。** 秘密情報そのものを渡さずに
  それを見せる認証情報 API は存在しません。だからこのダイアログは設定を報告し、依頼が
  あれば消す、それだけです。
- **GitHuttBr に渡したトークンは別物です。** 一方を失効させても、もう一方には触れません。
  キーチェーン側については [セキュリティ](security.md) を見てください。
- **プロファイルのトークンは、リポジトリのフックの環境に入りません。** フックに見える
  のは、その git コマンドの実行中だけ有効な、非公開の接続先用のコードだけです —
  git-lfs のように意図して問い合わせるフックには十分です。
  [git 実行中のプロファイルのトークン](security.md#git-の実行中のプロファイルのトークン) を参照してください。
